# Deep container runtime

Build this image from the repository root with `--platform linux/amd64 --build-arg PPAP_APP_IMAGE=<verified amd64 app image>` and `-f deploy/deep/Dockerfile`. It adds verified Grok 1.0.70 and `setpriv`/`prlimit` to the existing application image. It does not add a Docker socket or Kubernetes permissions. The Dockerfile copies only `packages/agent/src` and links `/opt/agent/semantic` to the package's semantic tools and skill; the copied code must match the app revision used by the Controller. The root Docker context excludes `prototypes`, including research oracles, prototype tests and local experiment output, before either application or Deep image copies run.

The trusted Deep Controller runs as root to read authorized product input. `ContainerRuntime` starts each semantic guest as UID/GID 10001 with a fresh environment and closed inherited descriptors. The guest receives only run-local staged inputs, writable work, and a read-only short-lived model grant. The provider key stays in the trusted Controller process, which starts the loopback Responses gateway before accepting model work.

The product compiles one rule at a time through the existing compile entrypoint before staging any supplier documents. Each compilation directory is removed before the next run. Audit receives frozen plans or explicit compilation failures and cannot fall back to compilation. The rule-plan cache remains rule-specific; technical compilation identities include the current round. Each stage passes confirmed prior input tokens, output tokens and model requests to the grant gateway, which subtracts them from the whole execution allowance. A valid cache hit can use zero model requests; unknown usage still blocks success and is never retried automatically. Confirmed historical usage beyond the allowance prevents the next grant with `RESOURCE_LIMIT`.

For local readiness, run `python -m agent.readiness` inside the Deep container with its existing `PPAP_DEEP_CONTROLLER_SOCKET`. Exit 0 means the Controller replied and its runtime readiness check passed; exit 1 means unavailable, degraded, or no valid reply within one second. This is the Kubernetes readiness probe, not a liveness restart policy. It reads no business files, issues no grant, and calls no model. A socket file alone is not readiness. A passing probe does not prove provider access, free execution capacity, strong isolation, or a valid audit result. On failure, inspect existing Controller startup/cleanup errors and executable/gateway availability; do not replay an audit to diagnose readiness. Core readiness and Standard execution do not depend on this probe.

Runtime configuration fields are `state`, `gateway_socket`, `gateway_host`, `model`, `model_revision`, `app_revision`, and explicit `sandbox_profile` (`off` or `ppap`). Optional executable paths default to `/app/.venv/bin/python`, `/usr/local/bin/grok`, `/usr/bin/setpriv`, `/usr/bin/prlimit`, and `/app/.venv/lib/python3.12/site-packages`. `memory_mib` defaults to 1536 and `max_processes` to 256. The runtime rejects macOS and non-root or non-container Linux execution.

Start `local_gateway(socket_path, upstream, model, provider_key, input_tokens=..., output_tokens=..., requests=...)` as a context manager in the trusted Controller process before constructing the runtime. It binds an ephemeral `127.0.0.1` HTTP port for the guest and a root-only Unix socket for grant issue/revoke/usage. The provider upstream must use HTTPS; the guest's HTTP address is permitted only on loopback. The default grant lifetime and semantic execution timeout use `agent.execution.budget.DEEP_TOTAL_SECONDS`; the Worker transport adds 30 seconds for response handling. These values are not proof of an end-to-end cleanup deadline or aggregate process-tree limits. The gateway accepts only `POST /v1/responses`. Pass the configured product LLM key, base URL, and model to this in-process gateway; never pass the provider key to the guest.

On the current TKE 5.4 kernel, the Grok inner Landlock profile is unavailable. Set `sandbox_profile=off` explicitly for the approved container-only mode. This mode drops guest credentials and applies process, memory, file-size, and wall-time limits. It does not guarantee filesystem or egress isolation against hostile guest code. Do not label it gVisor or VM isolation.

Waiting for the single guest slot uses the same absolute execution deadline and cancellation signal as running the guest. A waiting caller can fail without waiting for the current guest to finish; it must not release that guest's slot or create a run directory. This does not establish a whole-process-tree cleanup deadline or an operating-system scheduling guarantee.

Within one Controller's runtime state, an existing journal returns the saved guest output and confirmed model usage without starting another guest. The output still passes through `SemanticRuntime` business validation; a journal entry alone is not a successful audit. An attempt without saved output is not automatically re-executed, including when provider completion is unconfirmed. A newly accepted submission has a separate execution identity. Recreating the runtime over the same retained state after a clean terminal is distinct from recovering a mid-run crash, losing the state volume, or moving to another node; those broader recovery guarantees are not established by the local journal.

Business results and optional evidence quality are separate. Missing or unresolvable citations do not change a completed PASS/NG or trigger model repair. The product marks the evidence gap, omits unusable source links and does not add a source/trace verification marker when citation validation is incomplete. Frozen identity, rule coverage and actual execution consistency remain required; references outside the authorized submission are rejected. The original result bundle is retained, not rewritten to fill the gap.

New Deep acceptance derives the execution revision from the shared, non-secret `DeepExecutionPolicy`: application SHA, effective model endpoint/model revision, sandbox profile, resource limits, pinned tools and the optional `PPAP_DEEP_EXECUTOR_REVISION` label. API, Worker and Controller use the same effective configuration; `RuntimeConfig` uses the same canonical policy rather than a second hash implementation. No manual digest copy or runtime connection is needed at acceptance. The real semantic runtime checks its own revision before any cache, guest or model work. A changed policy cannot execute an old round; an explicit new round adopts it. Old results and acceptance receipts remain readable and are not relabeled. The profile still requires an explicit supported runtime deployment; `off` does not promise strong isolation.
