## 1. 目的与定位

### 1.1 运行背景
实际产品使用中，DVP&R 的审核不是一次完成的，而是分三段：

```
① 规则入口（上游，不在本规则内）
   规则文件（OEM 审核规则、Tier1 模板规则）提前提交
   → 形成「规则集 + 数据字典 + 术语归一表 + 口径登记」
   → 规则的所有权与解释权在此环节确定

② 审核入口（本规则所在）
   某项目下「全部或部分」PPAP 待审文件被提交
   → 本规则判断：这一批文件现在能不能被可靠审核
   → 输出 通过 / 不通过 + 问题清单 + 责任方

③ 正式审核（下游，不在本规则内）
   按已定型的规则集逐条出符合性结论
```

由此产生四条约束，贯穿全文：

| 编号 | 约束 | 直接后果 |
| --- | --- | --- |
| 背景-1 | **预检对象是"批次"，不是"项目"** | 结论只覆盖本次提交的文件；不得对项目内未提交部分下任何结论 |
| 背景-2 | **部分提交时，"文件缺失"不等于"供应商漏交"** | 未声明范围前，不得判完整性缺失；只能登记"范围不可界定" |
| 背景-3 | **规则歧义已在规则入口处理完毕** | 本规则不重审规则文本、不裁定规则口径、不判断规则是否可用；规则侧一切问题按总纲 2.3 排除在判定范围之外，不得登记为本规则的问题 |
| 背景-4 | **DVP 与 DVR 只提交一端时，依赖双端的规则不可执行** | 该端依赖无法满足的部分按总纲 3.1 / 3.2 登记为 **`S04-S`**（对端未到·提交方应交件，配 `W01`、进整改单）；**唯一例外**：范围声明已明确本次只交一端 → 缺的那一端属 **`S01`**（本就不属本次范围）。二者都不产生级别、不参与通过判定 |

### 1.2 核心设计原则

> **预检只拦"结论不可靠"，不拦"结论为不符合"。**

| 情形 | 举例 | 归属 |
| --- | --- | --- |
| 该行该列为空 | 某样本 52 行「完成节点」全空 | 正式审核（不符合项） |
| 该值形式合规但实质违规 | 结果填 `合格`，而实测值超出试验要求 | 正式审核（不符合项） |
| 该列根本不存在 | 某样本无「完成节点」列 | 正式审核（结构不符合）；**同时**触发本规则完整性检查（依赖该列的规则不可执行） |
| 该值**无法确定是不是空** | 某样本用全角空格填满 7 列 × 52 行 | 预检（不归一化会判成"已填"） |
| 两份文件对同一事实取值不同 | 同一批次内同源 xlsx 与 pdf 的报告栏一有一无 | 预检（不知以哪份为准） |
| 同一字段出现两套写法且无法唯一归一 | 结果栏并存 `合格`/`OK`/`PASS`/`符合` | 预检（无法归一即无法判定） |
| 规则本身有两种执行方向 | 起止同日算不算违反"早于" | 不在预检范围（规则侧；已确认"允许相等"，见 13.1，直接按口径执行） |

### 1.3 与正式审核的边界

| 维度 | 本预检规则 | 正式业务规则审核 |
| --- | --- | --- |
| 问的问题 | 这一批文件**能不能审** | 这一批文件**审下来合不合格** |
| 判的对象 | 可定位性、可判定性、自洽性 | 逐条业务规则的符合性 |
| 输出 | 通过 / 不通过（阻断、警告） | 符合 / 不符合（含不符合项清单） |
| 对"空值"的态度 | 只要能确定它确实为空，就放行给正式审核 | 判为不符合 |
| 对"业务枚举"的态度 | 只检查能否唯一归一，不判值对错 | 判值是否在枚举内 |
| 对"防造假"的态度 | 只检查证据是否可读、是否自相矛盾到无法判定 | 判是否造假、是否闭环、是否合规 |
| 失败后果 | 打回整改 / 提交方补正，**不进入**正式审核 | 出具不符合项报告，驱动供应商整改 |

**推论（必须写进报告）**：预检通过 ≠ 文件合规，只表示"可以开始审"；预检不通过 ≠ 文件不合格，只表示"现在审出来的结论不可信"。

### 1.4 本规则不做的三件事

1. 不给出 R1–R7、R-01–R-15 任何一条的符合性结论。
2. 不做防造假判定（设备校准超期、物理时长不足、照片场景不符、不合格未闭环、公式重算、语义错配等）。
3. 不重审规则文本、不评价规则合理性、不裁定规则口径（总纲 2.3）。

## 2. 范围与非目标

### 2.1 范围内

- 接收本次批次的待检查文件集与范围声明。
- 以整个批次为标准化对象，进行数据正确性、完整性、一致性检查。
- 识别批次内哪些文件属于 DVP&R、哪些不属于，防止对非本项表单套用规则（判定为**顺序流程**，见 7.2 COM-09；**非本项表单是剔除 + `S01` 状态，不是阻断**）。
- 自主推断批次内跨文件、跨工作表、跨端的关联项（DVP ↔ DVR、同源多载体、家族件与报告号映射）。
- 输出 Markdown 预检报告，含批次级、文件级、工作表级、字段可得性级、端级结论与责任方。

> **不在范围内**：规则集与数据字典的版本可追溯性、规则引用字段是否在字典内、已确认 / 未确认口径是否下发或被触发、规则自身是否自相矛盾、字段整批不可得等规则侧事项，一律按总纲 2.3 排除。本规则**不接收规则集与字典版本标识**，不得因规则侧原因产出任何结论。

### 2.2 非目标

- 不负责 OCR、表格抽取、文档解析等底层实现，不规定解析工具或技术路线。
- 不评价供应商能力，不评分，不打分卡。
- 不输出程序可直接消费的 Schema。
- 不覆盖项目内未提交的 PPAP 项与文件。
- 不替代任何一项 PPAP 的正式审核。

### 2.3 批次边界规则
| 编号 | 规则 | 不满足时 | 落地检查项 |
| --- | --- | --- | --- |
| BT-1 | 批次须有**范围声明**：项目标识 + 本次提交的 PPAP 项清单 + 每项的文件清单 + 是全部还是部分提交 | **已作出但缺关键要素**（致范围不可判）→ 阻断；**完全未声明** → 按总纲 4.2 推定部分提交，记 `W01`，**不阻断** | `COM-01` / `W01` |
| BT-2 | 范围声明须与实到文件**逐条对应**（名称、数量、版本标识） | 阻断 | `COM-01` |
| BT-3 | 同一文件在批次内出现**多个版本**（如 `X_继峰`、`X_继峰 - 错误`、`X_继峰-线框被遮挡` 并存）且无版本说明 | 阻断（无法确定以哪份为准；实测存在同族系 5 份仅差后缀的同名文件） | `COM-02` |
| BT-4 | 部分提交时，报告的"适用范围"须写明本次覆盖的项与文件，且不得对未提交部分下任何结论 | 属**报告自检项**：不产生问题实例、不计数、不新增编号，按 5.1 重出报告即可 | 无（报告自检，不进问题清单） |
| BT-5 | 若项目级应提交清单已登记，本批次应为其子集；出现清单外文件 | 登记为 `S01` 范围外（不参与判定、不产生级别） | `COM-10` |
| BT-6 | 依赖双端的规则，两端须同批提交；仅一端时该规则本批次不可执行 | **按是否已声明范围分两态**：① 范围声明**含双端**而只到一端，或**未声明**（4.2 推定部分提交）→ 缺端记 **`S04-S`**（`src=SUB`，DVP 与 DVR 均可由提交方自行编制），配 `W01` 写明缺哪一端，**进整改单**；② 范围声明**已明确只交一端** → 缺端记 **`S01`**（本就不属本次范围），无整改动作。两态均不计通过、不计不通过，在"字段可得性矩阵"中标注并在适用范围中说明 | 无（状态项，不设检查项） |

> **BT 是规则条文编号，不是检查项编号。** 报告的"检查项编号"字段只允许 `COR-xx / COM-xx / CON-xx` 三类（5.3），一律填上表"落地检查项"列的值；不得在报告中写 `BT-01` 这类编号。`BT-1` 与 `BT-2` 同落 `COM-01`，同一事实只记 **1 条** `COM-01`，不因同时违反两条而计两次（6.5）。`BT-4` 不产生问题实例，仅在报告自检时纠正。`BT-6` 不设检查项，按 `S04-S` 或 `S01` 状态登记（分界见该行）。

> **编号说明**：批次边界规则统一用 `BT-` 前缀（Batch Trigger），与 5.3 的问题实例编号 `B-xx`（阻断）/ `W-xx`（警告）严格区分，两者不得混用——整改单回传时仅凭 `B-xx` 无法判断语义，正是 v1.0 的缺陷。

## 3. 术语

| 术语 | 说明 |
| --- | --- |
| 批次 | 本次提交的文件集合。预检的判定对象，不等于项目全集 |
| 范围声明 | 提交方对"本批次包含项目内哪些 PPAP 项、哪些文件、是全量还是部分"的说明 |
| 规则集 | 上游已定型的规则集合（含判定条件、值域、触发条件） |
| 数据字典 | 上游已定型并维护的字段级标准，含字段编码、归属端、数据类型、值域、共性/差异标记（见附录 C） |
| 归属端 | 字段属于 DVP 端、DVR 端，或两端都有 |
| DVP | 设计验证计划。承载"要做什么试验、按什么标准、什么时候做" |
| DVR | 设计验证报告。承载"实际做没做、实测值多少、结论如何、谁出的报告" |
| DVP&R | DVP 与 DVR 合一的表单，同一行左侧为计划区、右侧为报告区 |
| 表头树 | 被审模板的分层表头结构：3 个具名区块（版本状态栏 / 试验计划栏 / 试验报告栏）+ 1 个同级标识行，各含二级表头（见附录 B） |
| 区块 | 表头树的顶层分区 |
| 数据行 | 承载一条试验记录的行 |
| 整行合并行 | 横向贯通整表的合并行，通常是分组标题（如"一、总成性能"），不参与数据行判定 |
| 延续轮次行 | 序号/试验项目/试验要求/试验标准四项全空但「试验类型」有值，属上一试验的追加轮次 |
| 家族件 | 一份计划或报告覆盖多个件号的场景 |
| 借用 | 试验项目沿用其他车型或前一阶段已有结果，不重新开展 |
| 同源对 | 内容同出一份原始文件的 xlsx 与 pdf |
| 假填充 | 单元格填入全角空格、不换行空格等不可见字符，视觉有内容、语义为空 |
| 占位符 | `/`、`N/A`、`NA`、`-`、`—`、`无`、`XX`、`XXX有限公司`、`详见报告` 等代替真实值的写法 |
| 归一 | 把同一字段的各种写法映射到数据字典规定的标准取值 |
| 状态 · 范围外 | `S01`：该对象**本就不属**本次提交范围（如 R1 部分提交下计划端本不在范围），或该文件不属本项类目。判据与「交没交」无关，不产生级别 |
| 状态 · 对端未到 | `S04`：属本次范围、**在可及证据集内不存在**（`SRC-1` 提交件 ∪ `SRC-2` 受控提供源，总纲 3.2.1；如已声明计划端却只交报告一端）。**分两子型**：`src=SUB` → `W01` + **`S04-S`**；`src=CUS`（如客户图纸、规范）→ 仅 **`S04-C`**、**不配 `W01`**、不进缺件数。不产生级别 |
| 状态 · 规则不适配 | `S02`：规则侧成因导致该项在本类目上无判定依据。预检不评，不产生级别 |
| 状态 · 移交 | `S03`：该判断属正式审核（超差、合规、有效性、造假、PV 约束违约事实），预检只登记不判 |
| 责任方 | 问题应由谁处理：供应商（材料侧）/ 提交方 / 技术支持（解析侧）。**不设规则侧** |
| 字段可得性 | 按 DVP 端 / DVR 端分别汇总字段是否存在、是否可定位、是否可归一；不涉及规则可执行性判断 |

> **`S04` 分两子型（总纲 3.2，v0.7 新增）**：判前必先核「可及证据集」（`SRC-1` 提交件 ∪ `SRC-2` 受控提供源）；对端在集内已存在的**必须正常比对、不记 `S04`**。集内没有时按 `src` 落 `S04-S`（能自行补出，配 `W01`）或 `S04-C`（只能向甲方索取，**禁配 `W01`**、不进缺件数、进七章 7.2b）。`src` 查《00-A》§4.3，查不到记 `S02`。**本分则全文凡记 `S04` 之处一律按本子型标注。**
> **`S05`（受控模板缺结构）继承总纲**：本分则凡判 `B05` 之处，须先按总纲 **3.1 三分界**与 **5.2 两问**确认成因——查《PPAP-00-A》**§4.4 客户受控模板登记表**：该（客户 × 类型）登记**有**受控模板、且**模板本体也没有该列** → 记 **`S05`**（状态，**不阻断**、不配 `B`/`W` 码、不进缺件数、进报告七章 **7.2c**）；登记**无**（不限定表单格式）或**模板有而文件没有** → 仍记 `B05`。**本分则的 3.1 状态词表不列 `S05`**——它的定义、边界与取证要求只在总纲 3.1 / 3.3 / 5.2 维护，避免同一概念在多处分别表述。**`B`/`W` 原因码取值与判定严格程度逐字未改。**　**枚举优先级**：本分则凡用列举方式写状态码的地方——**判定结果取值、状态登记清单、六章装填白名单、「必须按 3.1 拆为…」之类的执行要求**——`S05` **都在其列**（分「已核对」/「待核」两种形态）。**若某处枚举文本仍只列到 `S04-C`，以本条为准**，不得因该处漏列而拒绝登记 `S05`。理由：v0.9 把 `S05` 加进总纲 3.1 之后，各分则的枚举没有同步扩，若按枚举字面执行，`S05` 会**有判据、无落点**——判出来了却装不进状态登记清单，等于这一档不存在。

## 4. 输入契约

### 4.1 必选输入

#### 4.1.1 本次批次文件集

- 某项目下全部或部分的 PPAP 待审文件，可能只有 1 份，也可能是多文件集。
- 本项典型载体：`.xlsx`（多工作表、合并单元格、隐藏列、行底色）、`.pdf`（文本可提取但框线可能被遮挡），并可能混入**非 DVP&R 表单**（须识别并剔除）。
- 文件命名通常含零件信息、车型、阶段或版本后缀，命名与内容标识的一致性属一致性检查项。

#### 4.1.2 范围声明

见 2.3 BT-1。缺此声明时，完整性判定没有基准，判阻断。

#### 4.1.3 不接收的输入（本版变更）

按总纲 2.3，本规则**不再接收规则集与数据字典的版本标识**，也不校核其可追溯性。原有"版本不可追溯即判阻断"的条款一并废止：该事项属规则运营，不在预检判定范围内。

若规则集实际不可用，本规则**不产出任何结论**，直接返回「未执行」并说明原因，不得降级为"不通过"，也不得打回供应商。

### 4.2 可选输入

| 可选输入 | 本项的真实来源 | 不可用时的处理 |
| --- | --- | --- |
| 值域字典 | 数据字典中的字段值域；部分客户模板内另附字典页（如定义 `质量等级`、`状态`、`外观属性`、试验结果） | 无字典时只报"存在多种写法"，不判哪种为准 |
| 字段同义词表 | 附录 C.2（汇总了实测的 28 个字段中英双语、折行、斜杠写法） | 无同义词表时表头识别命中率下降，易误判"列缺失" |
| 填写要求说明 | 部分客户模板附「填写要求」页（如明确允许 `DV/PV` 合写、说明某类项可申请取消） | 无此说明时无法解释部分"看似缺填"的行 |
| 申报阶段声明 | 提交方显式声明：DV 计划 / PV 计划 / DVR 报告 / 合并版 | 无声明且无法从文件名与报告区填充度推断时判阻断 |
| 项目级应提交清单 | 上游已登记的项目 PPAP 项清单 | 无此项时不做范围外检查（`COM-10` 不适用） |

### 4.3 解析责任边界

- 文件解析、表格抽取、图文理解由外部业务系统或模型层负责；本规则不规定解析工具或技术路线。
- 本规则只使用解析后的可判定内容做判断，并提出"必须能取到哪些信息"的要求（见 4.4）。
- **不得依赖框线检测推断列边界**：实测已有样本的表格线被图形覆盖，框线不可作为结构依据。
- 无法获得可判定证据时，记录为"文件无法解析"类问题，**不是一个可跳过的步骤**。
- 局部不可解析（单元格文本被截断、内嵌图模糊、被遮挡）须定位到具体单元格并记为局部不可解析，不得据此推断整份文件不可解析。

### 4.4 缺失输入的降级策略

| 缺失项 | 降级方式 | 级别 |
| --- | --- | --- |
| 范围声明 | **按总纲 4.2 推定部分提交**（不做全量推断）；完全缺失记 `W01`，**不判 `B02`** | 警告 `W01` |
| 申报阶段 | 允许按文件名关键词 + 报告区填充度推断，须写明推断路径与置信度；置信度为低时不得替代缺失记录 | 推断不足则阻断 `B02` |
| 字段同义词表 | 允许按表头语义相似度识别，须列出被识别为同一字段的候选写法 | 警告 `W03` |
| 值域字典 | 只报"多写法并存"，不裁定权威值 | 警告 `W03` |
| 项目级应提交清单 | 不做范围外检查（`COM-10` 不适用） | 不记录 |

## 5. 输出契约

### 5.1 总体结论

仅有两种结果，外加一种非结论返回值：

| 总体结论 | 判定条件 | 后续处理 |
| --- | --- | --- |
| **通过** | **无阻断项**（警告项可以存在） | 本批次可进入正式审核；警告项全部随报告移交 |
| **不通过** | 存在任一阻断项 | 按责任方分别处理，不得进入正式审核；**须给出原因码** |
| 未执行 | 规则集实际不可用，或本批无任何待审文件 | 不产出通过 / 不通过，由规则运营补齐后重跑 |

**警告不拦截。** 任一警告项的存在都不改变结论；但警告项必须 100% 列入报告第五章，逐条列明，不得合并、不得概括为"其余若干"。

**原因码**：不通过时必填，一个阻断项一个码（`B01`~`B06`），含义与边界见总纲 5.2，本分则不再重复。

报告首段必须同时给出**适用范围**：项目标识、本次覆盖的 PPAP 项、文件数、是否部分提交。通过结论同样要带适用范围，避免被当作项目级结论转发。

### 5.2 报告形式

- Markdown 报告，可追溯、可读、便于人工整改。
- 证据须落到最小颗粒度：文件 → 工作表 → 单元格（PDF 落到页码 + 页内区域）。
- 当前不要求程序可直接消费的 Schema。

### 5.3 问题记录字段

| 字段 | 说明 |
| --- | --- |
| 编号 | `B-xx`（阻断）/ `W-xx`（警告），便于整改对照；状态项不编号，在"状态登记"表中以序号列示 |
| 类型 | 数据不规范 / 文件无法解析 |
| 细分类型 | 正确性 / 完整性 / 一致性（**不再设"规则可执行性"**） |
| 检查项编号 | `COR-xx` / `COM-xx` / `CON-xx`（第 7 节），用于回归比对 |
| 原因码 | 阻断项必填 `B01`–`B06`；警告项填 `W01`–`W06`；状态项填 `S01`–`S03` 或 `S04-S` / `S04-C` |
| 文件位置 | 文件 → 工作表 → 行列地址；跨文件问题列**全部**位置 |
| 证据链 | 原值（不可见字符须显式标注）+ 位置 + 推断依据 + 关联项 |
| 影响 | 具体说明会让哪一条规则、以何种方式失真（写"导致结果栏无法归一，该列全部判为不可判定"，不写"影响审核"） |
| 严重级别 | 阻断 / 警告（状态项记 `S01` / `S02` / `S03` / `S04`，不填级别） |
| 责任方 | 供应商 / 提交方 / 技术支持（**不设规则侧**） |
| 置信度 | 高 / 中 / 低，须说明依据（实测证据=高；同类推断=中；仅结构推断=低） |
| 整改方向提示 | 给责任方的可执行动作，不含本规则的代做 |

### 5.4 结论颗粒度

| 颗粒度 | 输出要求 |
| --- | --- |
| 批次级 | 总体结论、原因码、适用范围、阻断清单、警告清单、状态登记、责任方分布 |
| 文件级 | 每个文件是否存在问题、阻断数、警告数、最高级别 |
| 工作表级 | **必需**：一个工作簿可含多张 DVP&R 表（实测存在单文件 2 张、6 张的情况），须逐表给结论 |
| 字段可得性级 | 逐字段标注是否**存在 / 可定位 / 可归一**；无此字段的记 `B05`（结构缺失）或 `W02`（有列无值）。**不输出规则符合性结论，也不输出规则可执行性判断** |
| 端级 | DVP 端与 DVR 端的字段可得性；双端未齐时按 `S04-S`（未声明 / 声明含双端）或 `S01`（已声明只交一端）登记缺的那一端 |

### 5.5 明确不输出的内容

- 任何**业务规则**的符合性结论（该规则是否合规、不符合项数）。批次级"通过 / 不通过"是预检自身的结论，不在此禁令内，但不得表述为对业务规则的符合性判断。
- 任何防造假结论（过期、造假、敷衍、错配、未闭环）。
- 任何评分、打分卡、排名、通过率。
- 任何"建议修改业务标准/阈值/枚举"的表述。
- 对未提交 PPAP 项的任何结论。

## 6. 执行流程

### 6.1 接收批次与范围确认

1. 接收批次文件集与范围声明。
2. 核对范围声明与实际文件（2.3 BT-1 至 BT-5；问题分别记 `COM-01` / `COM-02` / `COM-10`）。
3. 逐文件确认是否可访问、内容是否可获得。
4. 逐文件判定**是否属于本项审核对象**（按 7.2 COM-09 的**顺序**判定：表头特征 → 表号或标题佐证 → 归属不可判 → 非本项剔除），非本项表单剔除并登记 `S01`。
5. 识别同源对、家族件、同事物多版本，写入证据链备查。

### 6.2 规则可执行性：本分则不设

按总纲 2.3，规则侧问题不在预检范围内，本节原内容（规则集版本确认、规则 × 字段可得性矩阵、执行状态三值、口径缺口 A/B 类处理）一并废止。对本规则的直接影响：改为输出「字段可得性矩阵」而非「规则可执行性矩阵」；不再判「本批次不可执行」，字段结构上不存在的记 `B05`、端未提交的按 `src` 记 `S04-S`（已声明只交一端的记 `S01`）；不再区分口径缺口 A / B 类。

### 6.3 检查需求映射

先列出正式审核需要哪些数据前提，再逐项核实本批次能否提供。本项的数据前提按**用途**分为六组（前五组为字段组，第六组为结构前提，不含字段）：

| 组 | 前提字段 | 用途 |
| --- | --- | --- |
| 文档受控 | 表号、版本号、修订日期、修订部门/姓名、修订内容、顺序号 | 归属与版本确认 |
| 受试标识 | 零件/总成名称、适用车型、零件/总成编号、供应商名称、质量等级 | 受试对象确认与对齐 |
| 试验定义 | 序号、试验项目、试验要求、试验标准/方法、试验类型、完成节点、试验地点 | 行识别与可判定性 |
| 计划与样本 | 数量、状态、外观属性、计划开始、计划结束 | 区间逻辑与 PV 约束触发 |
| 报告 | 试验实际开始日期、试验实际结束日期、实际试验结果、试验报告编号、备注 | 判定与归一 |
| 结构前提 | 主表头、次表头、二级父表头归属、数据行边界、合并区归属、分组标题行 | 取数基础（不含字段） |

> **归属端不在本表定义。** 字段属于 DVP 端、DVR 端还是双端，**以附录 C.1 为唯一来源**；本表与附录 C.1 表述不一致时以 C.1 为准。`EXE-04` 与所有"端是否齐备"的判断只允许引用 C.1，不得引用本表。
>
> 结构前提组不参与"按端统计覆盖情况"——主表头、数据行边界没有 DVP / DVR 之分，其归属端在 C.1 中不出现。

**允许隐含获取的前提**

| 前提 | 隐含来源 | 置信度处理 |
| --- | --- | --- |
| 供应商名称 | 表头、盖章、文件名、同批次其他文件 | 中；须注明推断路径 |
| 零件/总成编号 | 文件名或同批次其他 PPAP 文件 | 中 |
| 适用车型 | 文件名与表内车型简写 | 低（占位车型如 `W0X` 不可当作真实值） |
| 申报阶段 | 文件名关键词 + 报告区填充度 | 中；推断不足即阻断，不得直接采用推断结论 |

### 6.4 三维度检查

三维度**并列**执行。任一维度出现**阻断项**即不通过；**警告项不参与结论判定**（见 8.2）：

> 三维度始终全量执行；`EXE` 组不属本分则判定范围（总纲 2.3），不存在短路条件。

- 数据正确性 → `COR-xx`（7.1）
- 数据完整性 → `COM-xx`（7.2）
- 数据一致性 → `CON-xx`（7.3）

三维度共用同一份取数前提。判定前须先固定三件事：① 表头树已还原到二级归属；② 每个规范字段已按名称定位到列；③ 数据行边界已确定（已剔除整行合并的分组标题行、表内说明行、会签栏，并已处理垂直合并继承与延续轮次行继承）。**三项未固定时，三个维度都不得开始判定**——否则"某字段全空"这类结论只是取数失败的表现，不是数据缺陷。

### 6.5 汇总判定

1. 汇总全部问题，去重：同一根因在多文件重复出现时合并为 1 条 + 位置清单，**不逐文件重复计数**。
2. 同一事实落入多个类型时取最高级别，并在证据链注明"同时构成 X 类问题"。
3. 标注编号、类型、位置、证据链、影响、级别、责任方、置信度。
4. 给出批次级、文件级、工作表级、规则项级、端级结论与适用范围。
5. 按 8.3 出总体结论；按 8.4 归集责任方。

### 6.6 输出报告

按第 9 节模板输出 Markdown 报告，须明确：是否通过、适用范围、不通过原因、问题清单、责任方与整改方向、本规则不执行修复与复检、不替代正式审核。

## 7. 判定口径

### 7.0 编号与分级总则

- `COR` 正确性 / `COM` 完整性 / `CON` 一致性。
- **检查项共 32 项**：`COR` 10、`COM` 11、`CON` 11（v2.0 起；v1.2 及以前为 38 项，含 `EXE` 7 项）。批次边界规则 `BT-1…BT-6` 是**规则条文编号，不是检查项编号**，其问题统一落到 7.1–7.3 的某个 `COM` 项（映射见 2.3）。
- **`EXE` 组不属本分则判定范围**（总纲 2.3）：`EXE-01`~`EXE-07` 七项中，`EXE-03`（规则依赖字段在本批结构上 100% 取不到）重分类为 `COM-11`（判定所需关键字段在结构上不存在），其余 6 项不再属于预检范围。
- 每条检查项给出：判据、默认级别、责任方。
- **级别的唯一权威是 8.2 判定矩阵**：默认级别、升级条件、降级条件均以 8.2 为准；7.x 中的提示列仅作阅读参考，与 8.2 冲突时按 8.2 执行。
- 级别只有两种：阻断 / 警告。**观察项已取消**，原观察项按总纲 3.1 / 3.2 拆为 `S01` 范围外 / `S02` 规则不适配 / `S03` 移交 / `S04-S` / `S04-C`（对端未到），登记于状态表，不参与通过判定。

### 7.1 数据正确性（COR）

关注"这份数据本身是否科学、合理、符合基本逻辑"，**不判业务规则符合性**。

| 编号 | 检查项 | 判据 | 默认级别 | 升级 / 备注 | 责任方 |
| --- | --- | --- | --- | --- | --- |
| COR-01 | 起止区间倒置 | 同一行「结束」早于「开始」；计划侧与实际侧分别查。含年份穿越（如计划开始 2026-02-26、计划结束 2025-04-01） | **阻断** | — | 供应商 |
| COR-02 | 日期不可解析或写法混用 | 同一列内混用 ≥2 种写法（日期值、序列号、`2025.2.17`、`2024/1/21`、`2025年6月12日`），或填非日期文本 | 警告 | 若该列 ≥50% 不可解析 → 阻断 | 供应商 |
| COR-03 | 占位符充当真实值 | 值属于占位符集合（`/`、`N/A`、`-`、`—`、`无`、`XX`、`XXX有限公司`、`详见报告`、`合格，见报告`） | 警告 | 若占位符出现在规则判定所需字段且无替代来源 → 升级为阻断 | 供应商 |
| COR-04 | 假填充 | 单元格仅含不可见字符（全角空格、不换行空格、制表符、换行），归一化后为空 | 警告 | 落在判定所需字段且整列如此 → **升级为阻断**。实测某样本 7 列 × 52 行 = 364 格；任何按"有内容"判断的实现都会误判为已填 | 供应商 |
| COR-05 | 数值与单位不匹配或缺失 | 阈值缺单位、单位大小写或量纲不符（`Mpa`、温升写成小写 `k`、`0.8N` 漏 `m`）、数量列填成周期描述（`1件/每年一次`） | 警告 | 若该数值是规则判定阈值 → 升级为阻断（阈值不可比） | 供应商 |
| COR-06 | 取值无法唯一归一 | 同一字段的写法无法映射到数据字典规定的标准取值（结果栏 `合格`/`OK`/`PASS`/`符合` 并存，且存在 `实验合格，缺报告`、`异常` 等无法映射值） | 警告 | 若同一字段 ≥50% 无法归一 → 阻断（该列系统性不可判） | 供应商 |
| COR-07 | 序号异常 | 跳号、重复、非数字、序号与行序不一致 | 警告 | 用于发现隐藏行、误删行、行归属错乱 | 供应商 |
| COR-08 | 计数与分组不自洽 | 数量写"12件（分4组，每组3件）"但分组数×每组数≠总数；家族件的件号条数与名称条数不等 | 警告 | 件号与名称不等会导致 1:1 映射不成立 | 供应商 |
| COR-09 | 局部不可解析导致证据不完整 | 单元格文本被行高截断、内嵌图模糊或被遮挡、关键说明只存在于批注 | 警告 | 若该单元格承载规则判定所需值且无替代来源 → 阻断 | 技术支持 / 供应商 |
| COR-10 | 同一字段在一行内自相矛盾 | 同一行「试验类型」与「完成节点」时间顺序不符（如完成节点早于阶段定义）；数值与文字结论相反 | 警告 | 不判业务合理性，仅记"内部不自洽" | 供应商 |

> **口径说明**：**起止相同（同日完成）不在 COR-01 范围**。规则所有者已确认"允许相等"，同日不记任何问题（13.1-①）。实测 73 处同日起止因此转为合规，日期类缺陷只剩 9 处倒置。

判断"规则需要的数据前提是否存在、是否可定位、是否可归一"。

| 编号 | 检查项 | 判据 | 默认级别 | 升级 / 降级条件 | 责任方 |
| --- | --- | --- | --- | --- | --- |
| COM-01 | 范围声明**已作出**但与文件不符（BT-2），或已作出但缺关键要素致范围不可判（BT-1） | 见 2.3 BT-1、BT-2 | **阻断** `B02` | **完全未作声明不适用本项**：按总纲 4.2 推定部分提交记 `W01`（`B02` 定义已排除「单纯未声明」） | 提交方 |
| COM-02 | 同一文件多版本并存且无版本说明 | 见 2.3 BT-3 | **阻断** | — | 提交方 |

| COM-07 | 试验方法与判定阈值不可取得 | 缺标准号 / 版本 / 条款，或试验要求为纯描述无法形成可判定条件（**指文件里没写明**） | 警告 | 若规则要求按阈值判定 → 升级为阻断 | 供应商 |

| COM-10 | 范围外文件混入 | 该文件是 DVP&R 表单，但不在本次提交范围内（项目级应提交清单之外，或属其他 PPAP 项的文件） | `S01`（不产生级别） | **须在 `COM-09` 判定为"属本项"之后才适用**：非 DVP&R 表单归 `COM-09`，不重复记本项；范围声明已列明该文件 → 不记录 | 提交方 |
| COM-11 | 判定所需关键字段在结构上不存在（**承接原 `EXE-03`**） | 该字段在整份文件 / 该工作表的结构中**无对应列或栏**（列缺失、表头无法映射、整份不可解析）。**不含"列存在但值全空"**——后者可确定为空，按 1.2 放行给正式审核，另按 `W02` 记录 | **阻断 `B05`** | 若同源另一载体可读出该字段 → 降为 `W05` 警告并注明替代载体位置 | 供应商 |
| COM-12 | **表头字段有栏无值** | 表头信息区**已画出该字段名**（栏位存在），但与它对应的值位为空 / `/` / `-` / `待填`。**本项只判表头区，不判正文行**（正文行的空值由 CON 组判） | 警告 `W02` | **与 COM-11 的分界**：字段连栏位都没有 → `COM-11` 阻断 `B05`；栏位有、值没有 → **`COM-12` 警告 `W02`**（5.2 边界表：有列个别为空 = `W02`，整列空 = `B05`）。同一字段不因「既无值又该判」而重复计级。**本项无升级条件**（补值即可，不动结构） | 材料侧 |

> **COM-09 的判定顺序不可打乱**：先表头、再表号/标题佐证、再不可判、最后才剔除。表号为空是常见形态（页眉「表号」后无值、或整份无表号），若把「表号不在已知族」直接当成「非本项」，会把本项表单静默剔除，正式审核则拿不到这份文件——这是本类预检最危险的一种错误。
>
> **"剔除"与"阻断"的分界**：随附的资质页、装箱单等无关文件混入批次属常态，正确处理是剔除 + `S01` 状态；只有**冒充**本项表单（表号或标题指向本项、但表头不足）才阻断。
>
> **`COM-09` 与 `COM-10` 是两个不同的问题，不要混用**：`COM-09` 问"**这份文件是不是 DVP&R 表单**"（表单归属，按表头 / 表号 / 标题判）；`COM-10` 问"**这份 DVP&R 表单在不在本次提交范围内**"（范围，按范围声明与项目级清单判）。判定顺序固定为：先用 `COM-09` 剔除非本项表单，再用 `COM-10` 剔除范围外文件。一个文件若既非 DVP&R 又属范围外，只记 `COM-09`（更根本的那一层），不叠加计 `COM-10`。

## 8. 严重级别与通过规则

### 8.1 级别定义（DVP&R 语境细化）

| 级别 | 定义 | 典型形态 | 影响结论 |
| --- | --- | --- | --- |
| 阻断 | 该条成立时，正式审核至少一条规则**无法得出唯一结论**——含"取不到数"与"结论方向不唯一"两种 | 主键不唯一、表头树不可还原、范围未声明、关键字段结构缺失、起止倒置、同源不一致 | **是 → 不通过** |
| 警告 | 该条成立时判定仍可完成，但**精准度下降或存在被误判风险** | 假填充、占位符、写法混用、序号跳号、说明落在批注、非主键不一致 | **否 → 仅记录并移交** |

**五类状态、六个代码（不是级别，不参与通过判定；`S05` 定义见总纲 3.1）：**

| 状态 | 代码 | 典型形态 |
| --- | --- | --- |
| 范围外 | `S01` | **本就不属**本次范围：范围声明已明确只交一端时缺的那一端、非本项表单（剔除）、范围外文件混入。**判据与「交没交」无关** |
| **对端未到·提交方应交件** | **`S04-S`** | 属本次范围、**在可及证据集内不存在**、且提交方能自行补出：未声明范围而只到一端、声明含双端而只到一端、其他 PPAP 项未到（`CON-11`）。**配 `W01`、进整改单** |
| **对端未到·甲方受控件** | **`S04-C`** | 同上但只能向甲方索取（客户图纸、规范、客户台账）。**禁配 `W01`**、不进缺件数，进七章 7.2b |
| 规则不适配 | `S02` | 规则侧成因导致某项在本类目上无判定依据（预检不评） |
| 移交 | `S03` | PV 约束违约事实、实测值超差、合规判断、造假稽核 |

> **`S01` 与 `S04-S` 的分界只有一句：范围声明里有没有它。** 声明含双端（或未声明）而只到一端 → `S04-S`，缺的那一端本来就该你交；声明已明确只交一端 → `S01`，缺的那一端本就不在本次范围。**旧版本把后者当前者、把前者也当后者，二者一律记 `S01`，结果是「该补交的一端」不进整改单**（v2.6 修正）。

> **"数据不规范得很严重"不构成阻断。** 一条问题的级别只由"能否得出唯一结论"决定；"是否规范、是否合规、是否严重"属符合性判断，一律留给正式审核（见 1.2）。把"看起来很差"判成阻断，是本类预检最常见的越权，v1.0 的 8.1 曾留有这个口子。
>
> **警告不拦截的补偿**：警告项 100% 列入报告第五章并随报告移交正式审核；正式审核**不得因"预检已通过"而跳过警告指向的字段**（总纲 8.3）。

**归口规则（消除一题两归）：**

1. 每个检查项**只能有一个主责任方**，取 7.x 该行的责任方列；8.4 与该列不一致时以 7.x 为准并同步修正 8.4。
2. `COR-09` 是唯一在 7.x 中写有两个责任方的条目（"技术支持 / 供应商"），按**成因**二选一：文件损坏 / 不可读 → 技术支持；文件本身可读但内容被截断或遮挡 → 供应商。报告中须注明成因，**不得两处同时列**。
3. `CON-11` 只归供应商：该条判"本项与其他 PPAP 项的标识是否一致"，整改动作在供应商侧；其他项未提交时该条记 `W01` + `S04-S`（范围声明已排除该项 → `S01`），不参与判定（8.2）。
4. 责任边界的总原则：**`COM` 分两层**——"提交范围与文件组织"一类（`COM-01` / `COM-02` / `COM-03` / `COM-09` / `COM-10`）归**提交方**，"数据本身有没有"一类（`COM-04`…`COM-08`、`COM-11`）归**供应商**。同一事实不得同时落在这两类里。
5. **不设规则侧责任方**。原 8.4 表中的"规则所有者"行随 `EXE` 组退出而删除（总纲 2.3 / 10）。

**强制要求**：报告中"打回供应商整改"与"提交方补正 / 解析侧核查"必须分表列示。混列会导致范围问题被当成供应商责任，这是本类预检最常见的误用。

### 8.5 级别冲突处理

- 同一事实落入多个检查项时取最高级别，并在证据链注明"同时构成 X 类问题"，**不重复计数**。
- **禁止降级原则**（总纲 8.4）：某类问题在全批次普遍存在，**不得因其普遍性而降低级别**。报告的相应条目须注明"该问题在本批次普遍存在，属系统性缺口，非个别疏漏"。
- **禁止的调整**：阻断 → 警告（除 8.2 矩阵明列降级条件外）；因置信度低而降级（应保持级别并标注置信度）；因整改成本高而降级。
- 一个阻断项被修复后可能暴露新的警告项，属正常现象；报告只反映本次提交状态。
- 置信度为低的推断结论**不得单独构成阻断**，须降为警告并注明"需人工确认"。
- **上一条的例外**：`COM-03`（申报阶段不可确定）不属"低置信度推断"，而是"推不出可用阶段"——此时"报告区空白算缺失还是尚未到期"这个判定基准整体缺失，按 4.4 判**阻断**。两者的区别是"推断了但不确定"与"根本推不出来"；前者降级，后者阻断。

### 13.2 PV 约束的定义（口径②④⑤的落地，供规则集引用）

**业务含义**：PV（生产验证）阶段的试验须使用正式量产工装（硬模）生产的零件；用软模件、手工件、RP 件、OTS 件、平台件完成的试验不能代表量产状态，其结论不足以支撑 PPAP 批准。DV 阶段允许使用非硬模件。因此 PV 约束的实质是**试验阶段与样本状态必须匹配**。

| 要素 | 定义 |
| --- | --- |
| 约束主体 | 一个数据行（以表内数据行为单位，不因合并单元格或延续轮次行重复计数） |
| 触发条件 | 该行「试验类型」归一后属于**触发集合** |
| 断言 | 该行「状态」归一后属于**断言集合**（等价于 `硬模件`） |
| 违约 | 触发成立且断言不成立 |
| 不触发 | 试验类型属**明确不触发集合** → 该行不参与约束（**不得计为通过**） |
| 不可判 | 试验类型或状态任一为**空值 / 不可读**。此时既无法确认触发、也无法确认断言，该行不参与约束；**空值本身不记预检问题**（属正式审核，见 1.2），只有"填了但读不出"按五路表末行归口 |
| 取值越界 | 试验类型既不在触发集合、也不在明确不触发集合 → 该字段无法归一，按 `COR-06` 记**警告**；该行不进入约束 |

**触发集合（已闭合）**：`PV`（大小写不敏感）；`DV/PV` 及其分隔符变体 `DV / PV`、`DV-PV`、`DV+PV`（合写表示一轮同时覆盖两阶段，其 PV 部分仍需量产工装样本）；`型式试验`、`年度试验`（2026-10-30 确认，见 13.1 ④）。

**明确不触发集合**：`DV`；`pre-DV`（DV 之前的预研 / 预验证，不进入 PV 阶段约束）。

**断言集合（已闭合）**：`硬模件`、`硬模`、`硬模件（量产）`、`硬模件(量产)`；后三种归一为 `硬模件`（2026-10-30 确认，见 13.1 ⑤）。其余取值（`软模件`、`手工件`、`RP 件`、`OTS 件`、`平台件` 等）**一律判断言不成立**，不再判"不可判"——这是口径⑤带来的实质变化：v1.1 因同义写法未定而只能判不可判，v1.2 起归一是确定的。

**预检层与本约束的分工**：预检只回答"这一行能不能按 PV 约束检查"，不回答"这一行符不符合"。按结果分五路，各走既有出口，**不为 PV 约束新增检查项编号**：

| 判定结果 | 预检层动作 | 级别 | 归口 |
| --- | --- | --- | --- |
| 触发成立 + 断言成立 | 记录"该行满足断言" | 不产生 | — |
| 触发成立 + 断言不成立 | 登记违约**事实**（行号、试验类型原值、状态原值），移交正式审核 | **`S03` 移交** | 不设编号，写入报告状态登记表 |
| 属明确不触发集合 | 记录"该行不参与约束" | 不产生 | — |
| 取值无法归入任一集合 | 登记原值与所在单元格 | **警告** | `COR-06` |
| 字段为空 / 不可读 | 该行不参与约束。**空值本身不记预检问题**（属正式审核的不符合项，见 1.2）；只有"填了但读不出"才记问题 | 仅"读不出"时定级 | 假填充 `COR-04`、占位符 `COR-03`、截断/遮挡 `COR-09`；**仅当该列根本不存在**才记 `COM-11` |

> **为什么"违约"只记移交**：预检的结论是"输入质量是否足以支撑正式审核"，不是"业务是否合规"（1.2）。PV 行用了软模件属**符合性**问题，归正式审核的对应规则判定；预检若在此处阻断，等于用预检替代正式审核，并使同一事实在两级被重复计级。登记为 `S03` 是为了**不丢件**，不是为了让其影响通过判定（8.3）。该登记不占用检查项编号，因此不违反 8.4 的"一题一归"。

> **口径闭合后不再有"PV 约束不可判"兜底**：v1.1 中"状态取值不认识就判不可判、再转 `EXE-07`"的路径已随 13.3-B 清零而失效。若把未知取值继续判不可判，会出现"无出口"的空转；因此上表将它明确导向 `COR-06`。
