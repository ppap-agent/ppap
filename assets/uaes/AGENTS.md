# UAES 规则库版本

改动 UAES 规则、条款检查结果、规则确认问卷或 UAES 检查程序的条款正文前，先读本文件。

## 版本与修订

- **版本**（v0.0、v1.0、v2.0……）由条款集合决定：条款数量或新旧条款的对应关系变了（新增、删除、拆分、合并），就升版本号。只升第一位，第二位固定为 0。
- **修订**（m0、m1、m2……）是同一版本内的改动：条款集合不变，只改条款内容。
- 每个版本的 m0 是这个版本最初的原件；之后每一步修订都从上一修订出发。客户发来的新稿同样按这条判断：条款集合没变是新修订，变了是新版本的 m0。
- 已确认的修订冻结，不再改；只有已确认的修订能在线上跑审核。
- 一份修订里每处与上一修订不同的地方都要能追到来源：问卷答复、客户裁决，或原件里的修订与裁决说明。说不出来源的改动不进修订。
- 经他人转达、没有客户原始答复记录的口径，不当作客户已确认。
- **确认人是产品负责人**：候选是否成为下一修订、同一问题答复不一致时取哪一种，都由产品负责人决定。

## 一轮修订怎么走

1. **出问卷**：对当前修订跑条款检查，把发现的问题做成卡片；平台自己裁定或新增、客户还没确认的内容也做成卡片。用 `questionnaire.py load` 导入要作答的企业，可以导入多个企业，各企业的答复分开保存。
2. **整理候选**：根据答复写候选，线下 Markdown，放在 `assets/uaes/rulebook/<版本>/候选 m<i+1>.md`，一个版本同时只有一份。候选随答复反复修改，不跑审核。
3. **确认**：产品负责人看候选并确认。
4. **落版**：确认后生成 `rulebook/<版本>/m<i+1>/`（若答复要求增删、拆分或合并条款，则生成下一个版本的 `m0/`），写对照，删除候选文件（历史在 Git 里）。上一修订的问卷用 `questionnaire.py close` 关闭，答复保留可查。
5. **上线**：离线归档、确认条文和切换审核默认不是一件事。仅在发布验收通过并明确授权后，才整套部署到 ppap-test，在现网核对实际生效的规则、检查程序和审核结果。
6. **下一轮**：对新修订重新跑条款检查、出新问卷；上一修订的问卷不搬过去，已答清的问题不再问。问卷答复（含分歧）均已处理、条款检查也没有未决问题后，由产品负责人确认这一修订不再是「待澄清」；不能从已答数量推断。

## 候选怎么写

候选要让产品负责人不用翻别的文件就能决定，信息给全，但按决定需要的顺序排：

- 开头一段：基于哪个修订、问卷答了几张、还剩几张、有几处答复不一致；这次建议改几条。
- **要你决定的**放最前：答复不一致的卡片，并列每个人的答复（署名、时间）和建议取哪一种、为什么。
- **建议修改**：逐条写条款编号和名称、当前原文、建议改成的原文（改动处标出）、依据的卡片和答复人；改了条款集合的单独标明，确认后会升版本。
- **不改的**：已答复但不需要改条款的卡片，写一句为什么。
- **还没答的**：列出卡片，说明这一轮不处理、会在下一修订的问卷里重新出现。

## 用户看到什么

产品里遵循「不让用户思考，但不隐藏信息」：

- 规则页显示实际生效的版本和修订，用户的话写作「v1.0 修订 1」，不显示 m1 或内部编号。
- 「待澄清」的修订在规则页标出，并写明还有几个问题待确认；每条条款下直接挂它的问卷卡片，点进去就能作答。
- 和上一修订相比改了哪些条款、依据是什么，在规则页能看到，不用另找文档。
- 审核结果里，因规则更新、检查程序还没改好而没检查的条款，写明「规则已更新，暂未检查」，不显示成通过，也不显示成出错。
- 重审时有已启用的新修订或版本，默认用新的，提醒「审核规则已更新」，用户可以沿用上次的。

## 目录

- 每个已确认的修订放在 `assets/uaes/rulebook/<版本>/<修订>/`：规则库原件或修订文本、逐类抽取的 `rules/*.json`、通用判定说明。入库后不改。例外：v0.0 的 m0 是客户原稿 `assets/uaes/rules/*.docx`。
- 条款检查的审查记录与报告、问卷导入文件、检查程序使用的条款正文，都从对应修订的这些材料生成，不各自维护另一份。条款检查材料在 `clause-check-semantic-v2/`，检查程序与新条款的对齐核对在版本目录的 `检查程序对齐核对.json`。
- 每次升修订或升版本，在目标版本目录里附一份对照：每条新条款对应哪条旧条款，按判定结果是否会变分为「意思不变」「意思变了」「新增」，删除或合并的写明去向，并列出每条相关的问卷卡片。
- 版本和修订靠目录与 Git 历史识别，不另建台账或清单。

## 条款标识

- 一条条款的标识是「客户 + 版本 + 文件类型缩写:编号」，如 UAES v1.0 `CP:5`。修订号不属于标识，只说明内容是哪一版。问卷卡片、人工判定、检查程序都用这个标识，不另建映射。
- 文件类型缩写和编号照抄客户规则库原件，平台不自己重排。`rules/<缩写>.json` 里只放 `<缩写>:<编号>`，编号在一份修订内唯一。
- 同一版本的所有修订，条款编号集合完全相同；编号有增、删或改名（包括文件类型缩写改名）就是新版本。`packages/product/tests/test_rulebooks.py` 按这条检查仓库里的每份规则库。
- 跨版本不按编号相同对应：客户新版重新编号就照新版，新旧条款只按对照表对应。
- v0.0 沿用检查程序目录号（如 `U19:1`），旧语料的人工判定和回放都绑定它，不迁移；对照表里写作「v0.0 修订 1 U19:1」。
- 问卷导入文件写明它针对的修订（`rulebook_version`、`rulebook_revision`，如 `v1.0`、`0`），规则页按这两个字段把问卷挂到修订上，不从标题推断。

## 规则、检查程序与人工真值

- **版本和修订**固定审核依据。仓库归档的 m0 和离线候选都可供评审；这不代表当前审核默认，不能借展示入口让候选进入受理。
- **Checker 的 Suite Revision**固定实际绑定和代码。受理时锁定规则修订、Suite Revision、Checker 摘要、共享运行库及执行器摘要；程序修正不要求重写规则，规则改动后不能默认沿用旧程序的结论。
- **人工真值（Oracle）**绑定样本、原件证据、判定时的规则修订、条款和人工依据。规则含义未变时可以复用真值；含义变了，原件仍可复用，但要重新判定，不能改写旧真值。模型回放只用于复现调用，不是真值。
- **对齐验收**按规则修订和程序证据核对。只有新修订下验证过的绑定才标「已对齐」；错判通过或不通过都不算对齐。缺绑定记为「规则已更新，暂未检查」，不算通过，也不算执行失败。检查程序按文件类型成组，变动类型及读取其结果的关联类型一起复核。
- **旧版回归不等于新版验收。** 现有 UAES 语料明确用 v0.0 m1 的归档入口、条款、预置规则和原人工真值。归档入口仍调用当前检出的共享库；没有原运行库/执行环境的确切版本时，不宣称是原程序的逐字节复现。新版验收另外建立受当前修订约束的代表性样本和预期结果。
- **切换是单独的发布决定。** 先核实实际官方默认和适用的租户绑定、未检查项的客户表现、冲突裁决和切换影响。运行库或执行器摘要改变时，要在切换前停止旧版本受理并排空已受理任务，或保证它们仍路由到原来匹配的执行环境；不绕过摘要校验，不改写历史轮次。
