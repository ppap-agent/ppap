> 版本：v0.14
> 定位：全部 PPAP 数据标准化预检分则的公共契约。分则只写本文件族的检查项，不重复本文件内容。

## 1. 目的与定位

在正式业务规则审核之前，判断本次提交的 PPAP 文件**能否被可靠审核**。

只回答三个问题：**读得出来吗、有没有、说得一致吗**。不回答：符不符合客户要求、措施是否有效、数据是否真实。

**前提动作**：先定「这份文件属于**哪个客户的哪一类** PPAP 文件」。同一文件类型在不同客户下的必备结构与必填字段不同（如控制计划在 UAES 与蔚来分属两套结构要求），归属未定则无从选择判定基准——**归属先于一切校验**（见 4.5~4.7）。

**不做**：OCR 与解析实现、合规性判断、工程有效性审核、造假稽核、文件修复与复检、规则集本身的维护与裁定。

## 2. 范围与非目标

### 2.1 范围内

- 接收本批次 PPAP 待审文件、提交范围声明、文件清单。
- 对文件本身做数据正确性、完整性、一致性检查。
- **识别（客户 × 文件类型）并据此路由判定源**（4.5~4.9）。
- 输出结构化预检报告与两级结论。

### 2.2 非目标

- 不评判文件是否符合 IATF 16949 / AIAG PPAP / 客户特定要求。
- 不判断实测值是否超差、能力值是否达标、措施是否有效。
- 不判断数据是否造假。
- 不执行整改后复检。
- 不输出程序可直接消费的 Schema。

### 2.3 明确排除：规则侧一切问题

**预检假定规则集已在前置入口完成提交、定型、启用与口径裁定。** 以下事项一律不在预检范围内，不得作为问题登记，不得影响结论：

| 排除事项 | 说明 |
| --- | --- |
| 规则是否已录入、是否启用、是否停用 | 属规则运营 |
| 规则条数是否完整、版本是否与项目锁定一致 | 属规则运营 |
| 规则引用字段是否在数据字典中存在 | 属规则运营 |
| 已确认口径是否随规则集下发、未确认口径是否被触发 | 属规则运营 |
| 规则自身是否自相矛盾、是否存在两种执行方向 | 属规则运营 |
| 数据标准字典 / 属性层清单是否发布、取值集合是否定稿 | 属规则运营 |
| 客户专属符号表、AP 标准表等外部基准是否提供 | 属规则运营 |
| 客户审核规则的 `required_structure`（必备结构 / 必填字段摘要）是否已抽取、是否与规则正文一致 | 属规则运营 |

**由此产生的四项架构后果：**

1. **判定维度只保留三维**：正确性、完整性、一致性。原「规则可执行性」维度不属本分则判定范围。
2. **责任归属不设「规则侧」**：只保留材料侧、提交方、解析侧（见 10）。
3. **前提失效时的处理**：若规则集实际不可用，本体系**不产出任何结论**，直接返回「未执行」，由规则运营补齐后重跑；不得降级为「不通过」，也不得打回供应商。
4. **`required_structure` 的定位**：它是规则入口给定的**判定基准**，与分则判定项同为判定源（见 7.6），但预检**只消费、不评价**——其缺失、过时、与规则正文不一致均属规则运营，不构成文件缺陷，不得据此判不通过。

| 提交方 | 提交批次的组织问题（范围、版本、清单），责任在项目 / 采购 |
| 解析侧 | 文件可读性不足导致的问题，责任在解析能力提供方 |

### 3.1 状态词：五个必须区分的概念

**「不适用」一词禁用**，必须按下表拆分为五种之一。五者为**状态**，不是级别，不参与通过判定。

| 状态 | 代码 | 定义 | 是否产生级别 |
| --- | --- | --- | --- |
| 范围外 | `S01` | 该对象**本就不属**本次提交范围——本批不含该类目、该文件不属本项类目、或规则项在本范围档下不适用。判据与「交没交」无关 | 否 |
| 规则不适配 | `S02` | 规则侧成因导致该项在本类目上无判定依据（预检不评） | 否 |
| 移交 | `S03` | 该判断属正式审核（超差、合规、有效性、造假），预检只登记不判 | 否 |
| **对端未到** | **`S04`** | **该判定项须与本批另一份文件比对，而对端在「可及证据集」内不存在**（提交件与受控提供源都没有，见 3.2.1）；本侧文件已提交、结构可判，仅因无对象而比对未完成。**须按来源类别分两个子型**：`S04-S`（提交方应交件，配 `W01`）/ `S04-C`（甲方受控提供件，**不配 `W01`**），见 3.2.4 | 否 |
| **受控模板缺结构** | **`S05`** | 该判定所需的关键字段，在**客户受控模板本体**上不存在，提交方无权增列；**且该（客户 × 类型）在《PPAP-00-A》§4.4 登记了受控模板**（登记为「有」或「**有（待补登记）**」均算登记，后者标「待核」并受 §4.4.8 时限约束）。判定确实没做成，但成因在模板侧（七章 7.2c），非材料侧 | 否 |

**关键区分：**

- 「范围外」≠「文件不含该对象」。前者是该对象本就不属本次范围（**与「交没交」无关**），后者是交了但文件里没有这个字段。
- 「文件不含该对象」**是材料侧问题，按 7.2 分流表定级**：该对象不承载任何判定的关键字段 → `W01` 警告；承载某条判定的关键字段 → **`B05` 阻断**。二者都不得记 `S01` / `S02` / `S04`。
- 「规则不适配」只用于规则侧成因。不得用它兜住"文件里没有这个字段"。
- **`S04` 不用于「本文件自己的字段没有」**——那是 `B05`（结构不承载）或 `W01`（不承载关键字段的区块）。
- **`S04` 也不用于「对端在受控提供源里有、只是不在提交目录里」**——那要正常比对，不记 `S04`（3.2.1）。判 `S04` 之前必须先证明「我确实拿不到这件东西」，而不是「它不在提交件目录里」。
- **`S05` 只用于「模板本体就没有」的情形。** 该（客户 × 类型）**未登记受控模板**（即不限定表单格式，见《PPAP-00-A》§4.4）时，提交方对表结构负全责，缺栏落 `B05`，**不得记 `S05`**；模板有该栏而文件没有，同样落 `B05`（供应商删了列或改用自建表）。
- **「待补登记」不是免责出口。** 它只说明「客户有表、我没取到」，因此**责任在客户侧**、暂不改判供应商；但**结论仍标「待核」**，须在报告 10.3 逐条声明，且受 60 天补登时限约束——逾期未补自动回落为「无」，缺栏一律 `B05`。**不得用「待补登记」覆盖「模板有而文件没有」**。
- **「待核」不阻断放行，但放行不免责。** `S05` 是**状态**、不产生级别（本节表头已定），因此待核项**不改变该文件的通过结论**——该文件按其余判定项给结论，**允许进入下一阶段审核**。但必须同时满足三件事，缺一即视为「用状态码放水」：
  1. 在报告 **7.2c** 单列该行，核对状态记 `待核`、填待核截止日；
  2. 在报告 **一章结论摘要**写「**重点关注 N 项**」，N = 待核条数，并写明「**该项信息是否存在缺失尚待核实**」；
  3. 在 **10.3 待确认清单**逐条声明，并注明**下游阶段审核承接复核责任**。
  > **放行与免责是两件事。** 放行的依据是「预检只能判本批文件，客户模板不在本批」；不免责的依据是「这条判定确实没做成」——所以它必须出现在读者的视线里，而不是被「通过」两个字盖住。**补登后若模板确有该栏，改判 `B05` 并重新预检；下游若未复核即放行，责任在下游阶段，不在预检。**
- **`S05` 也不用于「规则本身与该标准体系不符」。** 若某判据要求的字段在该体系里本就不该存在（如 `R10` AP 查表在**四版**表上无 `AP` 列、`R06` 严重度取三维度最大值在四版无分值设计），那是**规则假设错**，记 `S02`。判据一句话：**该字段该不该有？** 该有而模板没画 → `S05`；本就不该有 → `S02`。
  > **典型误判（须避免）**：把「五版表头 `PC`/`O`/`DC`/`D` 四列并列、无独立分值列」当成「规则假设错 → `S02`」。**这是错的**——分值内嵌在控制措施列的**值**里（形如 `目视检查（6）`），四列并列与「值内嵌」并不互斥。**判 `S02` 前必须确认该字段在取值层面确实无处可取，不能只看表头**：表头只能回答「有哪些列」，回答不了「列里的值长什么样」。

**`S01` 与 `S04` 的分界（三者都是状态，但去向完全不同）**：

| 情形 | 归口 | 判据 | 后续动作 |
| --- | --- | --- | --- |
| 该对象**本就不属本次提交范围**（本批不含该类目；或规则项在本范围档下不适用，如 CP 的 `P-05` 在 R1 档） | `S01` | 范围可事先确定，与「交没交」无关 | **无需任何动作** |
| 该对象**属本次范围、在可及证据集内不存在、且 `src=SUB`**（提交方应交件） | `S04-S` | 范围含该对象，且提交方对该件负编制与提交责任 | **必须**：随 `W01` 移交并写明缺哪一件；补交后须重新预检 |
| 该对象**属本次范围、在可及证据集内不存在、且 `src=CUS`**（甲方受控提供件） | `S04-C` | 范围含该对象，但提交方无权编制、无权补交 | **不配 `W01`**、不进缺件数；进七章 7.2b 向甲方索取；补件后重新预检 |

**`S04` 的四条硬约束**（v0.7 由三条扩为四条）：

1. **`S04-S` 必须与 `W01` 成对出现；`S04-C` 禁止配 `W01`。** `W01` 记「缺了哪一件」（进警告清单、计入警告数、进整改建议）；`S04` 记「哪条判定因此没做成」（进第六章状态登记、**不重复计入任何计数**）。同一事实只计 `W01` 一次。成对的**前提**是「这一件本来就该提交方交」——`src=CUS` 时该前提不成立，故不成对（3.2.4）。
2. **不得把 `S04-S` 改记 `S01` 以规避整改要求。** 改记 `S01` 等于宣告「本就不该有这比对」，缺件从此不进整改单——v0.5 之前把「对端未交」写成「对象不在范围」，漏洞就在这里。
3. **不得把 `S04-C` 改记 `S04-S`，也不得改记 `S01`。** 前者把整改单派给无权补交的一方（方向错），后者让「这条没做成」从状态登记里消失（覆盖率虚高）。
4. **`S04` 不产生级别、不改变结论。** 它只说明「这条没做成」，判定仍是「无阻断即通过」（8.2）。`S04-C` 尤其如此：受控件未随批时，该判定项**既不判通过、也不判不通过**，登记为「**未审（证据未随批）**」；该文件按其余判定项给结论，但报告须列明未审条数，**不得表述为「全部审核通过」**。
   > **「未审」与「未执行」不是一回事，不得混用**（v0.8）：**「未执行」是结论级返回值**，只有 5.1 那四种成因（整批不可用、本批无文件、本类目无文件、条目既无分则也无 `required_structure`），且不进入通过率统计。**「未审」是判定项级标注**，指该条本应判、因**对端未到**（`S04-S` / `S04-C`）、**受控模板缺结构**（`S05`）或**执行方能力不足**而没判成，必须逐条计入报告「未审条数」。用「未执行」去标一条判定项，等于给它开了一个不进统计的免责出口。  
   > **`S05` 必须计入未审条数**：六章 `S05` 行本就写「该判定未完成」，若又把它排除在「未审条数」之外，同一份报告会同时出现「7 条判定未完成」与「未审 0 条」——那等于用统计口径把「没判成」抹掉，正是本条禁令要防的事。**`S05` 的「已核对 / 待核」两种形态都计入未审条数**，只是待核那部分还须另加一句「结论以客户模板补登后复核为准」。

**`B05` / `S05` / `S02` 的三分界（按「缺的成因」而非「缺的现象」）**：

同样一句「结构上没这一栏」，成因不同，归口完全不同：

| 现象 | 成因 | 归口 | 后续动作 |
| --- | --- | --- | --- |
| 无此列，**该组合有受控模板、且模板本体也没有此列** | 模板侧 | **`S05`** | 进七章 7.2c 模板结构性缺陷清单，**向甲方申请模板变更**；不打回供应商、不进缺件数 |
| 无此列，**该组合登记为「有（待补登记）」**——客户确有其表但电子模板未取到，无法核对模板里到底有没有 | 模板侧（取证侧待补） | **`S05` + 标「待核」** | 进 7.2c 并注「模板待补」；**向甲方索取模板**，补登后复核——若模板确有该列，改判 `B05`。约束见《00-A》§4.4.8 |
| 无此列，**该组合无受控模板**（不限定表单格式），或**模板有而文件没有** | 材料侧 | **`B05`** | 打回供应商补结构（7.1） |
| 该字段在**该标准体系里本就不该存在** | 规则侧 | **`S02`** | 登记规则缺口，不产生任何整改 |

> **这张表是本轮的核心。** 它把 v0.8 之前被 `B05` 一码吞掉的两种不同成因拆开：**「模板没画」不是供应商的错，「供应商删了」才是。** 与 `S04-S` / `S04-C` 的分法同构——那一轮拆的是「该谁交」，这一轮拆的是「谁定的表」。

### 3.2 本批的边界：可及证据集

`S04` 能否成立，取决于「对端到底有没有」。v0.6 及之前把「本批」等同于**提交件目录**，于是**甲方受控提供的图纸、气泡图、PGQP1 被记成提交方缺交**——动态验证实测 16 例，整改单派给了错的一方。本节把「本批」定义清楚，并把「缺了没有」与「该谁交」拆成两个独立判定。

#### 3.2.1 可及证据集（`AES`）

**可及证据集**（Available Evidence Set）= 本次预检执行时**实际可以打开并读取**的全部文件。它是「同批齐备性」的核对边界，包含两个来源：

| 记号 | 名称 | 内容 | 典型位置 |
| --- | --- | --- | --- |
| `SRC-1` | **提交件** | 提交方随本批提交的全部文件 | 提交目录 |
| `SRC-2` | **受控提供源** | 由甲方／客户受控发布、随项目提供、提交方无编制权的基准件：客户图纸、技术规范 / 材料规范 / 订货规范、客户表单模板、客户侧台账（如 PGQP1 比对副本）、客户已批准的偏差认可记录 | 比对源目录、受控资料库、项目共享区 |

**跨文件比对的对象 = `SRC-1` ∪ `SRC-2`。** 对端在这两个来源内**任一**存在，就必须正常比对，**不得记 `S04`**——无论它来自哪个源、文件名与规则里的称呼是否一致。

`SRC-1` 内部的文件互比（如 PFMEA ↔ CP ↔ PFD）同样受本定义约束：三个都在 `AES` 内，缺一个才是真缺。

#### 3.2.2 来源类别（`src`）：缺了之后归谁

对端在 `AES` 内**不存在**时，才进入来源判定。只问一件事：

> **这份件缺失时，提交方能不能自己补出来？**
> 能自行编制、或能自行向第三方取得 → `SUB`；只能向甲方索取、既无权编制也无法自行取得 → `CUS`。

用这一个问句、而不是「谁的责任」，是因为**整改单的可执行性只取决于此**：派得下去的动作才叫整改，派不下去的只能叫索取。**也不看这份文件当前放在谁的目录里**——放在提交目录里的甲方图纸仍是 `CUS`，放在比对源里的供应商报表仍是 `SUB`。

| 记号 | 名称 | 判据（能否自行补出） | 典型件 |
| --- | --- | --- | --- |
| `SUB` | **提交方应交件** | 能自行编制，或能自行委托第三方取得 | PFD、PFMEA、控制计划、特殊特性清单、MSA 报告、过程能力报告、气泡图、kappa 分析、DVR / 试验报告、实验室资质证书、PSW、交付物文件清单 |
| `CUS` | **甲方受控提供件** | 只能向甲方索取；无权编制、无权修订、无法自行取得 | 客户图纸、客户技术规范 / 材料规范 / 订货规范、客户表单模板本体（未填写）、仅由客户持有的批准 / 会签 / 台账记录 |

**`src` 不得现场推定。** 逐件登记在《PPAP-00-A》§4.3「对端来源登记表」；登记表未覆盖的对端 → 该项记 `S02` 并作为规则缺口上报，**不得猜一个写上去**。

#### 3.2.3 `S04` 的三个要件

| 序 | 要件 | 不满足时的处置 |
| --- | --- | --- |
| ① | 该判定项**确需**与本批另一份文件比对（规则原文要求跨文件比对） | 不需比对 → 该条本身不适用，按 `S01` 或 `S02` |
| ② | 该对端在**可及证据集**（3.2.1）内**不存在** | 存在 → **正常比对**，不记 `S04`（无论来自 `SRC-1` 还是 `SRC-2`） |
| ③ | 该对端的 `src` 在登记表中**可查**（3.2.2） | 查不到 → 该项 `S02` + 报规则缺口，不记 `S04` |

#### 3.2.4 两个子型与去向

| 子型 | `src` | 含义 | 配 `W01` | 进整改单 | 计入缺件数 | 报告落点 |
| --- | --- | --- | --- | --- | --- | --- |
| **`S04-S`** | `SUB` | 提交方应交件未到——本应由提交方编制并随批提交 | **必须** | 是，责任侧 = **提交方** | 是 | 六章状态登记 + 七章 7.2 提交方补正 |
| **`S04-C`** | `CUS` | 甲方受控提供件未随批——由甲方受控发布，提交方无权也无义务补交 | **禁止** | **否**，责任侧 = **甲方 / 项目流程** | **否** | 六章状态登记 + 七章 7.2b 受控件索取清单 |

**`S04-C` 为什么不塞回 `S01`，也不并进 `S04-S`**：`S01` 的语义是「本就不属本次范围」，而受控件**属本次范围**（它是判定的必要证据），只是我手上没有——这条判定确实**没做成**，记 `S01` 会从状态登记里消失、覆盖率虚高；记 `S04-S` 会把整改单派给无权补交的一方。二者都不对，所以单列。

#### 3.2.5 判定顺序（不可颠倒）

```
该判定项需跨文件比对
  └─ ① 对端在 AES 内是否存在？
       ├─ 是 → 正常比对，不记 S04
       └─ 否 → ② 查 00-A §4.3 登记表 src
                ├─ SUB → W01（缺哪一件，责任侧=提交方） + S04-S
                ├─ CUS → S04-C（不配 W01），进七章 7.2b 受控件索取清单
                └─ 查不到 → S02 + 规则缺口上报
```

**跳过第 ① 步、直接按「本次没交」记 `S04-S`，就是本轮要修的那个错误本身。**

#### 3.2.6 三个常见误判

| 误判 | 正解 |
| --- | --- |
| 文件名对不上就判缺件 | 先按 10.4 匹配键确认 `AES` 内有没有**同一对象**：图号相同但文件名带版本后缀、客户台账与提交件命名体系不同，都属同一对象 |
| 受控件未随批 → 记提交方缺件 | `S04-C`，不进缺件数，不派整改单 |
| 受控件未随批 → 该文件整体判不通过 | 不成立。`S04` 不产生级别（3.1 硬约束 4）；文件按其余判定项给结论，但报告须写明「有 N 条未审」，**不得表述为「全部审核通过」** |

### 3.3 客户受控模板：只用来定结构归属，不作比对基准

`S05` 能否成立，取决于「模板本体到底有没有那一栏」。本节把这个证据源定清楚。

**三条约束：**

1. **模板只回答一个问题**：「这个结构是不是本来就没有」。它**不是**比对基准——文件不必与模板逐栏一致（6.5「模板不作为比对基准」继续有效）。供应商在模板上加列、调整列序、改用同义命名，**都不构成问题**。
2. **模板来源唯一**：《PPAP-00-A》**§4.4 客户受控模板登记表**。该表逐条登记 41 个（客户 × 类型）组合有没有受控模板、模板文件名与表单编号。**登记表未覆盖的组合，一律视为无受控模板**，缺栏落 `B05`，不得凭印象判 `S05`。
3. **「模板本体没拿到」不等于「模板没有该栏」，但落到哪个码取决于是「客户没给」还是「我打不开」（v0.11 拆两层，消解原表述与 3.1 的冲突）**：
   - **登记为「有（待补登记）」**——客户确有其表、电子模板未提供：按 3.1 三分界第二行记 **`S05` + 标「待核」**，在报告 7.2c 列出并填截止日，受《00-A》§4.4.8 / §4.4.9 的时限与复核约束。这是「**有而未取证**」，不是「无」，也不是「我打不开」。
   - **登记为「有」**（模板在库、本应可核对）但执行时打不开 / 读不出 / 文件损坏：**不得**推定「模板大概没有」。这属于**执行侧取证失败**，按 `B05` 保守判，在报告 10.3 声明取证受限，并同时进 7.3 解析侧核查——**责任在解析侧，不在客户，也不在供应商**。
   - **`S05` 的「已核对」形态，前提始终是「我打开过模板本体、确认没有这栏」**，不是「我认为模板大概没有」。
   > **原 v0.9 表述「拿不到模板 → 一律按 `B05` 保守判」在 v1.5 三档登记后已不成立**：它把「客户没给」（登记事实）与「我打不开」（执行故障）混成一件事。前者已在 §4.4 登记为「有（待补登记）」，按 3.1 落 `S05` + 待核；后者是解析侧故障，按 `B05` + 7.3 处理。**两条路径的整改对象完全不同——一个向甲方索取模板，一个修解析通道。**

**「不限定表单格式」的口径**：某（客户 × 类型）组合在 §4.4 登记为「无」时，表示该组合下甲方**不限定表单格式**——提交方可自选或自建表。此时**结构责任完全在提交方**：缺必备字段即 `B05`，**不得记 `S05`、不得以「甲方没给模板」为由免责**。

> **一处必须记住的事实**：《00-A》§4.4 显示，理想与蔚来的多份模板**表单编号相同、页签结构相同**（PFMEA 两侧均为 `JL-APQP-3-04/V1.0`，控制计划均为单页 `控制计划`、特殊特性清单均为单页 `特殊特性清单`）。**模板族 ≠ 客户**——模板只能证明「这个结构是不是甲方认可的基准」，**不能用来反推客户**（4.5、4.6 的客户识别规则不受影响）。

## 4. 输入契约与识别路由

### 4.1 两段式运行前提

| 阶段 | 承担者 | 内容 |
| --- | --- | --- |
| 第一段 · 规则入口 | 规则运营 | 规则提交、定型、启用、口径裁定 |
| 第二段 · 预检 | 本体系 | 接收待审文件，按分则判定数据标准化状态 |

**预检不接收规则文件实体**，不评判规则本身，不做规则与字典的版本比对。

### 4.2 必选输入

| 输入 | 要求 | 缺失时处理 |
| --- | --- | --- |
| 待审文件 | 本批次提交的 PPAP 文件 | 无文件 → 结论「未执行」 |
| **客户与文件类型** | 从文件内识别，或由提交方声明 / 人工指定（4.5、4.9） | 两者均不可定 → `B03`；可经 4.9 人工指定解除 |
| 提交范围声明 | 声明本批类目范围与全量 / 部分 | 未声明 → 按部分提交推定，并记 `W01`；**不得据此判缺件阻断**，**也不得记 `B02`**（`B02` 只用于「已声明但与实到不符」或「多版本无唯一有效件」） |
| 文件清单 | 清单所列文件须可访问 | 清单有实无 → 阻断 `B02` |

### 4.3 可选输入

- 同批其他类目文件（仅用于范围登记与跨文件一致性，不用于推断应有件数）。
- 项目主数据（唯一允许跨出文件集的比对方向）。

### 4.4 证据封闭性（边界 = 可及证据集）

判定证据必须落在**可及证据集**（`AES` = `SRC-1` 提交件 ∪ `SRC-2` 受控提供源，见 3.2.1）**之内**。

> **「封闭性」的含义**：不越出可及证据集去引入项目历史、批次外记录或主观推断——**不是「只认提交件」**。客户图纸、技术规范、PGQP1 副本属 `SRC-2`，在集合之内，可作为证据。

以下属不确定信息，只能署名陈述，不能作为判定依据：

- 项目上下文、项目历史记录；
- 提交范围声明（可用于**排除**，不可用于**推定应有**）；
- 必备清单、应提交件清单。

**不得因"应该有但没交"判缺件阻断。** 缺项按两条通道分流，**均不构成「缺件阻断」**：

- **跨文件对端缺**（该审规则要求与另一份文件比对而无对象）→ 按 3.2.4 查 `src`：`SUB` 记 `W01` + `S04-S`；`CUS` 只记 `S04-C`。
- **本文件区块 / 子表缺** → 按 7.2 分流：承载关键字段 → `B05`；不承载 → `W01`。

> 「缺项一律记警告」是 v0.4 之前的旧口径，v0.5 起已由 7.2 的「是否承载关键字段」分流取代。此处与 3.1、7.2、`W01` 定义、13 节可配置项**必须同口径**（v0.8 统一）。

### 4.5 识别：五项要素与两级置信度

预检的第一个动作不是读表，而是**定归属**。归属由五项要素构成——前两项是**路由键**，后三项是**对象键**：

| # | 要素 | 取值来源 | 不可判时 | 用途 |
| --- | --- | --- | --- | --- |
| 1 | **客户** | 文件内客户标识（抬头、Logo、表单编号体系如 `F-PU-xxx` / `APQP-xxx`、顾客签署栏）、提交方声明 | 记 `—`，**不得推断** | 路由键 |
| 2 | **文件类型** | 字典内类型（4.6）+ 客户命名映射（4.7） | 记 `—` | 路由键 |
| 3 | 车型 / 项目 | 文件抬头、项目代号、图号前缀 | 记 `—` | 对象键、分组 |
| 4 | 零件号 | 表头、标题栏、编号栏内嵌号段 | 记 `—` | 对象键、跨文件关联键（10.5） |
| 5 | 零件名称 | 表头、标题栏 | 记 `—` | 键命中后的反向确认（K3，10.4） |

**置信度分两级，不得混用**（v0.6 关键修订）：

| 级 | 由哪些要素合成 | 决定什么 | 是否触发 `B03` |
| --- | --- | --- | --- |
| **路由置信度** | **客户** 与 **文件类型** 两项，取二者较低档 | 能否路由、加载哪套判定源 | **是**——仅此一项可判 `B03` |
| **对象置信度** | 车型/项目、零件号、零件名称 三项，取三者较低档 | 能否归组（10.5）、能否做键反证（K3） | **否** |

> **为什么拆两级**：路由只需「客户」与「文件类型」两项；零件名称、零件号这类**对象键**缺失只影响分组与跨文件关联，不影响路由。故拆为两级，**`B03` 只由路由置信度触发**。

**单要素档位判据（v0.6 放宽「中」档）**：

| 档 | 判据 | 处置 |
| --- | --- | --- |
| 高 | 文件内有**显式标识**（客户：Logo / 抬头 / 顾客签署栏；类型：表名 / 标题 / 字典关键列组合），且与字典或客户命名映射**唯一命中** | 直接路由 |
| **中** | 存在**可指认的主要候选**，但证据为间接的，或路由键仅一项为显式、另一项靠推断收缩 | 可路由，报告标注「建议人工确认文件类型」，**不判 `B03`** |
| 低 | **提不出任何候选**，或**候选 ≥2 且证据相互矛盾、无法择一** | 按 4.8「识别失败」记 `B03`，出路为 4.9 人工指定 |

**「中」档明确接受的四类证据**（v0.5 只写「间接证据」一句，实际执行时把下列情形全推到了「低」）：

| 证据 | 例 |
| --- | --- |
| 表单编号体系 | `F-PU-xxx`、`APQP-xxx`、客户自建编号前缀 |
| 版式签名 | 固定栏位顺序、页脚版本行格式、合并单元格形态 |
| 标题用词与必备列组合 | 标题含「初始样品检验」；表头 9 列与字典该类关键列组合匹配 |
| 同批其他文件互证 | 同组内另一份文件已明确归属同一客户，且本文件无相反证据 |

**「命中 ≥2 类型」不再一律判低**（本档最重要的放宽）：只要**能指出主要候选并写明理由**，即可判「中」并路由。择一取证参照下表：

| 证据 | 权重 |
| --- | --- |
| 显式客户标识 / 显式表名 | 3 |
| 表单编号体系命中 | 3 |
| 必备列组合匹配度 ≥70% | 2 |
| 标题 / 表名含该类关键词 | 2 |
| 版式签名 | 1 |
| 同批其他文件互证 | 1 |

- **最高分 ≥3 且与次高分差 ≥2 → 主要候选明确**，判「中」并路由；
- **最高分 <3，或最高与次高差 ≤1 → 无法择一**，判「低」记 `B03`；
- 权重表是默认操作化口径，执行方可校准，**但「主要候选必须写明依据并写入报告」不可省**——未写依据的按「低」处理。

**客户要素的取证级序：P1 用户指定 → P2 文件标识 → P3 编号体系 → P4 同批互证**

客户是**路由键**，错一位判据集整体换（同一份 PFMEA 判蔚来与判 UAES 的结论可能相反）。本节把客户的取证来源按**效力从高到低**排成四级，**逐级下探，前一级成立即采用，不得跳级、不得越级反推**：

| 级 | 来源 | 判「路由置信度」 | 使用条件 | 与上级冲突时 |
| --- | --- | --- | --- | --- |
| **P1** | **交互层用户显式指定**——产品界面上的客户选择（提交方或被审方在发起预检时主动选定），记入报告第二章「**客户来源：用户指定**」 | **高** | 无须再取证；直接路由 | 文件内出现**明确且可指认**的相反标识（另一客户 Logo / 专属表单编号）→ **不得静默改判为 P1**，须记「**客户冲突**」并在 10.3 与重点关注区列明，交人工确认后重跑 |
| **P2** | 文件内**显式客户标识**——Logo、抬头、顾客签署栏 | **高** | 与《00-A》§4.1 客户清单**唯一命中** | — |
| **P3** | **表单编号体系**命中《00-A》§4.4 登记表（如 `F-PU-xxx`、`JL-APQP-x`） | **中**（须写明编号与登记条目） | 该编号在登记表中**只对应一个客户** | 编号体系跨客户共用时**不得单独定客户**（3.3「模板族 ≠ 客户」）→ 降 P4 |
| **P4** | **同批其他文件互证**——同组内另一份文件已按 P1~P3 定客户，且本文件无相反证据 | **中** | 同批内**只出现一个**候选客户 | 同批出现 ≥2 个候选且本文件无法择一 → 判「低」记 `B03`（出路 4.9） |
| — | 四级均不成立 | **低** | — | `B03`，出路 4.9 人工指定 |

**三条必须记住的边界**：

1. **P1 是「业务事实声明」，不是「从文件推断」**——本节四条识别纪律（不得按后缀推类型、不得按模板签名反推、不得因同批他件推类型、依据须写入报告）**约束的是从文件取证**，不约束用户声明。用户选定的客户**无须从文件里再找一遍证据**。
2. **但 P1 不免除冲突报出义务**：用户选 UAES、文件抬头上印着理想 Logo，这不是「按用户说的算」，而是**一个必须报出来的矛盾**。理由：客户错一位 → 判据集整体换 → 结论可能整体反转，**静默采用上级等于把矛盾藏进结论里**。
3. **P1 不改变判定强度**：`S05` 是否成立仍须查《00-A》§4.4 该（客户 × 类型）的模板登记值，**不得因「客户是用户选的」就推定模板有无**。识别来源只决定「路由到哪」，不决定「判得多严」（8.4）。

> **为什么不做「图号 / 零件号前缀 → 客户」映射表**（v0.12 记录）：该映射在生产现场确实存在，但**不是稳定事实**——同一前缀在不同项目、不同年份会跨客户复用，且新项目上线即失效。**一张会过期的映射表比没有映射表更危险**：它会以「高置信度」的外观给出错误客户。故本轮取 P1 交互层指定作为最高效力源，**把「谁是客户」交回业务方声明，而不是让规则去猜**。

**放宽的是识别门槛，不是判定强度**：路由到主要候选后，判定项与级别**一律不得下调**（8.4）。识别依据不足只影响「路由可不可信」，不影响「判得多严」；报告中须标「识别依据：间接（中）」。

**识别纪律（四条禁止）**：

1. **不得按文件名后缀推类型**（`.xls` 不等于检验报告）。
2. **不得按模板签名反推类型**——模板有无是**客户级属性**（UAES 对 12 类无模板、理想/蔚来对其中 6 类有模板），据此反推会把「无模板」误判为「不是该类」。
3. **不得因同批其他文件的类型推定本文件类型**。
4. **识别依据必须写入报告**（第二章逐文件列「识别依据」），不得只写结论。

### 4.7 分则路由：三级判定源

路由 = 由（客户 × 文件类型）唯一确定**用哪一套判定源**。若按文件类型通用生效、与是否选客户解耦，在场景 A（审核供应商提交件）下会**用错结构去校验别人的文件**。

| 级 | 判定源 | 触发条件 | 校验深度 | 报告标注 |
| --- | --- | --- | --- | --- |
| **L1 分则直判** | 本体系对应分则的**公共判定项 + 该客户差异层** | 该（客户 × 类型）条目有**具备完整判定深度**的分则（结构 + 字段 + 正确性 / 完整性 / 一致性） | 完整：结构 + 字段 + 正确性 / 完整性 / 一致性 | 分则号 + 差异层代号 |
| **L2 规则驱动** | 该客户审核规则的 `required_structure`（必备结构 / 必填字段摘要） | 无完整深度分则（含**仅有结构判定分则**的情形），但规则集已有该条目且 `required_structure` 已抽取 | 限于**结构存在性与必填性**；不做数值复算、不做跨文件一致性 | `L2`，并列出所依据的 `required_structure` 条目 |
| **L3 无规则覆盖** | 无 | 规则集无该条目，或条目标记「规则待补充」 | 仅格式级门禁 + 识别；**内容级不判** | `L3`，记 `S02`（4.8） |

**加载纪律（六条硬约束）**：

1. **先定归属，再加载判定源。不得先加载再套。** 顺序反了就是「拿一套通用结构去量所有客户的文件」。
2. **客户差异层只写差异。** 公共判定项一律取自总纲与分则公共部分，差异层不得复制公共项，也不得改写公共项的级别与原因码。
3. **模板不是判定源。** 模板（Reference Style）只用于识别辅助与整改建议中的示例，**不得作为「结构是否合格」的判据**。报告中禁止出现「与模板不一致」作为不通过理由。
4. **客户差异层缺失时的兜底**：按该分则的「通用默认层」判，并在第十章标注「未加载到客户专属层，判定可能偏严」，置信度下调为「中」；**不额外记警告、不改变级别**。
5. **路由结果必须逐文件写入报告第二章**：客户 / 类型（`T`/`E` 号）/ 判定源（L1/L2/L3）/ 命中的差异层。缺这一列的报告为不合格报告。
6. **判定源由判定深度决定，不由「有没有分则文件」决定。** 为 L2 条目编写的**结构判定分则**（只判结构存在性与必填性）**不构成 L1**，判定源仍为 L2，报告标注仍为 `L2`；分则只提供判定方式、级别分流与边界，**判据本体以 `required_structure` 为准**。此条防止一种退化：每写一份分则就把条目升一级，最后 41 条全变 L1，三级判定源名存实亡。
   > **冲突时谁为准，按判定源分层，不按「分则 / `required_structure`」分**（见 7.6 规则 3）：
   > - **L1 条目**：判定本体就是分则判定项，`required_structure` 只是补充来源 → **以分则为准**；
   > - **L2 条目**：判定本体是 `required_structure`，分则只是文档形态 → **以 `required_structure` 为准**。
   > 旧文两处各说各话（4.7 说以 `required_structure` 为准、7.6 说以分则为准），照字面执行会得到相反结论；按条目层级切开后二者不再冲突，且各自保住了原本要防的那件事——4.7 防「写份分则就升级」，7.6 防「用粗结构清单推翻细判定项」。

### 4.8 未匹配两态：无规则覆盖 与 识别失败

「未匹配」不是一种状态，是两种，**必须分开**——混写会把「我们没这规则」误报成「你这份文件看不出是什么」。

| 态 | 判据 | 报告表述 | 状态 / 级别 | 出路 |
| --- | --- | --- | --- | --- |
| **无规则覆盖** | 识别**成功**（客户与类型均可定），但路由表无该条目或标「规则待补充」 | 「该客户 × 类型暂无审核规则，可能因规则覆盖有限」 | `S02`（规则不适配，不评） | 用标准模板 / 反馈补充模板 / 移除；用户仍可勾选，确认时按 `remove_reason = 未匹配到规则` 自动移除，不计费 |
| **识别失败** | **路由置信度为「低」**（4.5）——提不出任何可指认的主要候选，或候选 ≥2 且证据相互矛盾、无法择一 | 「未能确定该文件的客户或类型」 | `B03`（阻断） | 人工指定（4.9）后重新路由 |

> **「识别失败」的入口已收窄（v0.6）**：只有**路由置信度**（客户 + 文件类型）为「低」时才落 `B03`。对象键（车型 / 零件号 / 零件名称）缺失或低置信**不构成识别失败**——它只影响同批归组（10.5）与键反证（K3），不影响路由。反过来，路由置信度为「中」时**不得**记 `B03`，按正常路由判定，仅标「建议人工确认文件类型」（4.5）。

**三条禁令**：

1. **禁止**把两态合并写作「未匹配」。
2. **禁止**把识别失败记成 `S01`（范围外）——文件明明交了，不是范围外。
3. **禁止**把无规则覆盖记成「未执行」——「未执行」表示没得查（5.1），而这里查了、确认是没规则。

**补充机制**：规则文档到位后，只需在 00-A §1 对应客户表登记该（客户 × 类型）并标生效，该条目即从 L3 升为 L2/L1，**无需改本文件**。

### 4.9 人工指定（客户, 文件类型）

识别不总是自动可解。供应商文件的抬头可能被裁掉、表单编号可能自造，此时**卡死等于拒绝服务**，故开人工入口。

| 项 | 规定 |
| --- | --- |
| 触发 | **路由置信度为「低」**（即 4.8「识别失败」，记 `B03`）、用户主动改判 |
| 可改字段 | **客户、文件类型均可改**。旧版「文件类型不可改」的限制**废止** |
| 指定后动作 | 必须**重新路由并重跑内容级校验**；旧结论作废 |
| 报告留痕 | 记录「判定基准变更：`旧类型 → 新类型`，指定来源：人工」，写入第二章与第十章 |
| 不构成放宽 | **不得因人工指定而放宽任何判定**；指定只改「用哪套尺子」，不改「尺子的刻度」 |
| 落到 L3 时 | 按 4.8「无规则覆盖」处理（`S02`），不因「人工指定过了」就强行判 |
| 责任侧 | 指定动作本身属**提交方**（不计材料侧缺陷）；但指定后内容级校验发现的缺陷仍归**材料侧** |

## 5. 输出契约

### 5.1 总体结论（仅两级）

| 结论 | 判定条件 | 后续处理 |
| --- | --- | --- |
| 通过 | 无阻断项 | 可进入正式审核；警告项全部随报告移交 |
| 不通过 | 存在任一阻断项 | 按责任分派：材料侧打回整改、提交方补正、解析侧转技术支持 |

**另有唯一非结论返回值**：以下情形返回「未执行」，须说明原因，**不产出通过 / 不通过**。

| 情形 | 影响范围 | 说明 |
| --- | --- | --- |
| 规则集不可用 | 整批 | 规则入口侧未就绪，预检无法启动 |
| 本批无任何待审文件 | 整批 | 提交目录为空，或全部文件不可访问 |
| **本批有文件、但无本类目文件** | **单类目** | 如本批只交了检验报告与控制计划，则 PFMEA 分则对本批返回「未执行」，其他类目照常判定 |
| **该（客户 × 类型）条目既无分则也无 `required_structure`** | **单条目** | 本期范围内真缺口。**范围外类型不适用本行**——范围外走 4.8「无规则覆盖」记 `S02`，不返回「未执行」 |

**「未执行」的收窄口径（v0.5 强制）**：内容级「未执行」**只剩上表第四行这一种成因**。凡该条目已有分则（L1）或已抽取 `required_structure`（L2），**都必须执行内容级校验**，不得再以「预检未覆盖该类」为由返回未执行。旧口径「预检只覆盖 10 类、其余仅格式级门禁」已废止。

**「未执行」与 `S01` / `S02` / `S04` 的分界（必须分清，混用会导致覆盖率虚高）**：

| 情形 | 归口 | 理由 |
| --- | --- | --- |
| 本类目**一份文件都没有** | 该分则「未执行」 | 没得查 |
| 本类目有文件，但**某个判定项的对象本就不在范围**（如 CP 的 `P-05` 在 R1 档下不适用） | 该项 `S01` | 查了，确认不需要查 |
| 本类目有文件，但**该判定项要比对的对端在可及证据集内不存在** | `src=SUB` → 该项 `S04-S`，同源事实另记 `W01`（**只计一次**）；`src=CUS` → 该项 `S04-C`，**不配 `W01`** | 查了，想比但无对象——不是「不需要查」（3.1、3.2） |
| 该（客户 × 类型）**无规则覆盖**（L3，4.8） | 该项 `S02`，**不返回「未执行」** | 查了，确认是没规则，不是没得查 |
| **禁止**用「未执行」掩盖应当判定的项目 | — | 「未执行」不进入通过率统计，容易被当成免责出口 |
| **禁止**把「本类目无文件」记成 `S01` 计入状态统计 | — | 二者含义不同，见上两行 |
| **禁止**把「对端未提交」记成 `S01` | — | 那等于宣告「本不该有这比对」，缺件从此不进整改单（3.1） |
| **禁止**把「无规则覆盖」记成「未执行」 | — | 前者是规则侧缺口且已归口 `S02`，后者是本次没查 |
| **禁止**把「受控件未随批」（`S04-C`）混同「提交方缺件」（`S04-S`） | — | 前者提交方无责，派整改单会指向错的一方（3.2.4） |

### 5.2 原因码

结论为「不通过」时必须给出原因码。**一个阻断项一个码**，不得合并。

**阻断原因码（B 系列）**

| 码 | 含义 |
| --- | --- |
| `B01` | 文件无法解析，且范围内无同源替代 |
| `B02` | 提交范围不可判——**已作出范围声明但与实到不符**，或**多版本并存且无唯一有效件**。**单纯「未声明」不属本码**（按 4.2 推定部分提交并记 `W01`） |
| `B03` | 对象身份不可归属（无法断定属本项，或主键不可取唯一值） |
| `B04` | 结构不可判（表头树 / 行归属 / 有效行集合无法确定） |
| `B05` | **本文件**判定所需关键字段在文件结构上不存在，或整列取值全部不可判定（见下方边界表）。**仅指本文件自身结构**——跨文件对端未提交不是本码，记 `W01`（7.2）。**且仅当「该结构本应存在」**：该（客户 × 类型）有受控模板而**模板本体也没有该列**时，记 `S05` 而非 `B05`（3.1 三分界、《00-A》§4.4） |
| `B06` | 两类：① **同一事实在不同位置取值冲突**且无法确定以何为准（封面 ↔ 明细、表头 ↔ 履历、跨页同名栏）；② **同一文件内派生值 / 复算值与其来源不自洽**（代数关系不成立、计算链断裂），如公差带 ≠ 上公差 − 下公差、Centering / Range 复算不符、产能算式不成立 |

**警告原因码（W 系列）**

| 码 | 含义 |
| --- | --- |
| `W01` | 缺项，三种形态：① 缺跨文件对照件（`src=SUB` 时与 `S04-S` 成对）；② 缺**不承载关键字段的**子表 / 必备区块；③ 文件不含该对象。**承载关键字段的子表 / 区块缺失记 `B05`**——按 7.2 分流表判定，不得一律记 `W01`。另承接一处非「缺文件」用法：**提交范围声明未提供**（4.2 按部分提交推定并记 `W01`，`B02` 只管「已声明但与实到不符」） |
| `W02` | 字段存在但为空 / 占位符 / 假填充 |
| `W03` | 写法不规范（多写法并存、单位混用、符号未定义、取值不可归一） |
| `W04` | 非主键不一致 |
| `W05` | 局部不可解析（有替代来源或可另行确认） |
| `W06` | 文件内部不自洽，但不影响结论方向 |

**`B05` 的边界（统一口径，各分则不再各自表述）：**

| 情形 | 定级 | 理由 |
| --- | --- | --- |
| 结构上**无此列 / 无此栏**，且**该组合无受控模板**（不限定表单格式） | `B05` | 提交方自选 / 自建表，结构责任在其自身 |
| 结构上**无此列 / 无此栏**，但**受控模板本体也没有该列** | **`S05`** | 模板侧缺位，提交方无权增列；整改方向是甲方改模板（7.2c） |
| 结构上**无此列 / 无此栏**，但**受控模板本体有该列** | `B05` | 供应商删列或改用自建表，材料侧问题 |
| 有列，但**整列无一个可判定值**（值读不成数、全部为自由文字、整列空） | `B05` | **整列空 = 结构不可用**，不按空值处理 |
| 有列，**个别单元格为空** | `W02` | 这是缺值，不是缺结构 |
| 有列有值，但**值需语义判断才能用** | `S03` | 判定依据存在，只是要人来裁定，不是 `B05` |

**证据形态与文件形态不匹配时**（同一事实以图片 / 扫描件 / 嵌入对象形式存在）：

| 情形 | 处置 |
| --- | --- |
| 执行方**无**相应读取能力（无视觉通道等） | 标「未执行」，**不记级别、不判供应商责任**（4.3 能力前提） |
| 执行方**有**能力，但该形态不可靠（截断、压缩失真、局部遮挡） | `W05` 局部不可解析 |
| **不得**因「我读不出来」判 `B05` | `B05` 的前提是**结构上不存在**，不是解析能力不足 |

> 判 `B05` 前必须依次回答两句（v0.9 由一句扩为两句，第二句不可跳过）：
>
> **①「这个字段在文件的列结构里到底有没有？」** 答「有，只是我没读到」→ 走上表的「未执行」或 `W05`，**不判 `B05`**；答「有，但整列都不可用」→ 直接 `B05`，不必问第二句。
> **②（答「没有」时必答）「客户受控模板本体里有没有？」** 查《00-A》§4.4，登记值有四种去向：
>
> | §4.4 登记值 | 落码 |
> | --- | --- |
> | **无**（不限定表单格式） | **`B05`** — 表结构责任在提交方 |
> | **有**，且模板本体也没有该栏 | **`S05`** |
> | **有**，且模板本体有该栏 | **`B05`** — 供应商删列 / 改用自制表 |
> | **有（待补登记）**，模板未取到、无法核对 | **`S05` + 标「待核」** — 责任在客户侧，结论待模板补登后复核（《00-A》§4.4.8） |
>
> 前三种是**已定论**的落码；第四种是**暂定值**，不是定论——报告须单列声明，不得与已取证的 `S05` 混计。
>
> **跳过第二问直接判 `B05`，就是把「模板没画」记成「供应商缺」——这正是 v0.9 要修的那处错派。**

### 5.3 结论颗粒度

| 颗粒度 | 输出要求 |
| --- | --- |
| 文件级 | 每个文件是否有阻断、警告数与最高级别 |
| 检查项级 | 每条检查项 满足 / 不满足 / 状态（`S01` / `S02` / `S03` / `S04-S` / `S04-C` / `S05`） |
| 批次级 | 总体结论、原因码、阻断清单、警告清单、状态清单、移交清单 |

**判定对象的粒度**：上表的「文件级」「检查项级」回答的是**输出颗粒度**，本节回答**判定挂在哪一级**——两者不是一回事。

| 层级 | 定义 | 适用条件 |
| --- | --- | --- |
| **文件级**（默认） | 一个提交件 = 一个判定对象 | 载体为单表 / 单页签，或虽多页签但同属一个类目 |
| **页签级**（例外） | 判定对象下移到页签，报告须书作 `<文件名> › <页签名>` | **三条件同时成立**：① 该页签有独立表头与独立数据区；② 该页签能独立归属某一类目（4.5 / 4.6）；③ 页签之间无数据依赖（不存在跨页取数参与同一条判定） |

**状态码的挂载层级**：

| 码 | 挂在哪级 | 写法要求 |
| --- | --- | --- |
| `B` / `W` 系列 | 文件级 **或** 页签级（按上述例外下移） | 必须写到 `文件 › 页签 › 单元格/列`，不得只写文件名 |
| `S01` / `S02` / `S05` | **对象级**（文件或页签） | 须写明是哪一级；页签级须写页签名 |
| `S03` / `S04` | **判定项级**（挂在具体判定项上，不下放到页签） | 记「第 X 条判定未做成」，不写「某页签状态为 `S04`」 |

**两条禁止**：

1. **不得把文件级结论下放到页签**——`B02`（多版本并存）、`B01`（无法解析）描述的是整份提交件的状态，不能写「第 3 页签 `B02`」。
2. **不得把页签级缺陷上提为「整份文件不通过」而不注明页签**——那会让整改方向不可定位。写法：结论仍可为不通过，但每条须落在具体页签。

> **为什么单独写这一条（C10）**：`S01`~`S04` 的定义全部是**文件级**概念（「该对象本就不属本次提交范围」「对端未到」），但真实载体里确有「一文件多页签、页签含异类目」的情形（如某检验报告 8 个页签里有 2 个属其它类目）。规则若不说清判定挂在哪一级，执行方只能外推——**外推的结果是同一份文件在不同执行者手里得出不同结论**，而这正是本轮要消掉的那类分歧。

## 6. 执行流程

1. **接收与清单核对**：确认文件可访问；清单有实无 → `B02`。
2. **识别与路由**：按 4.5 定五项要素 → 按 4.6 落字典类型 → 按 4.7 定判定源（L1 / L2 / L3）。不能归属 → `B03`（可经 4.9 人工指定解除）；落 L3 → 记 `S02`，**不做内容级校验**（4.8）。不属于本批次任何类目的文件 → `S01` 剔除，不计数。
3. **可读性核验**：无法解析且无同源替代 → `B01`。
4. **结构核验**：表头树、行归属、有效行集合无法确定 → `B04`。
5. **三维度检查**：按 L1 分则判定项（公共项 + 客户差异层）与 L2 `required_structure` 逐项执行正确性 / 完整性 / 一致性检查（7.6）。**模板不作为比对基准。**
6. **汇总定级**：每项按 8.1 定级；同一事实落入多项取最高级别并注明，不重复计数。
7. **出结论**：无阻断 → 通过；有阻断 → 不通过 + 原因码。
8. **输出报告**：按第 11 节模板。

**终止条件**：第 2 步落 `B03` / `S02` / `S01`，或第 3、4 步任一失败，该文件后续检查不再执行，直接定级并出结论；不得在结构不可判的情况下继续做内容比对。

## 7. 三维度判定口径

### 7.1 数据正确性

判断单份文件内的信息是否科学、合理、符合基本逻辑。判定依据优先级：

1. 字段类型、格式、值域；
2. 属性内部代数自洽（公差下限 ≤ 名义值 ≤ 上限、处数 ≥ 1、重量为正）；
3. 基本常识与科学逻辑；
4. 业务常识与领域方法常识；
5. 数据标准字典。

**不判**：实测值与公差的比较结论、业务合理性、工程有效性——一律 `S03` 移交。

### 7.2 数据完整性

判断判定所需的数据是否存在、是否可定位、是否可归一。

**缺项统一规则：**

> 缺项是否阻断，取决于**该缺项是否由审核规则本身要求做跨文件比对**。

| 情形 | 处置 |
| --- | --- |
| 审核规则要求跨文件比对（如 PFMEA ↔ CP ↔ PFD、证书 ↔ 试验报告），而对端在**可及证据集**（3.2.1）内不存在 | 按 3.2.2 查 `src`，**写明具体缺哪一件**：`src=SUB` → 记 `W01` 警告 + 受阻判定项 `S04-S`；`src=CUS` → 只记 `S04-C`、**不配 `W01`**；**均不阻断**（3.2.4），不阻碍进入下一步审核 |
| 文件内含的必备区块 / 子表缺失，且**该区块承载某条判定的关键字段** | 阻断 `B05`——该判定在该文件上无承载位置 |
| 文件内含的必备区块 / 子表缺失，且**该区块不承载任何判定的关键字段**（仅少一路交叉校验来源） | 记 `W01` 警告 |
| 判定所需关键字段在**结构上不存在**（无此列 / 无此栏），且该组合**无受控模板**或**模板有而文件没有** | 阻断 `B05`——这已不是缺值，而是该文件不承载该判定 |
| 该关键字段在**客户受控模板本体**上也不存在（《00-A》§4.4 已登记该组合有模板） | 记 **`S05`** 状态（**不阻断**、不配 B/W 码、不进缺件数）——判定确实没做成，但提交方无权增列；整改方向是甲方改模板（7.2c），**不得写入 7.1 材料侧** |
分则中凡出现「必备区块缺失一律记警告」的表述，均按上表按**是否承载关键字段**分流修正。

其他完整性要求：

- 核对范围是**可及证据集**（`SRC-1` ∪ `SRC-2`，3.2.1），**不是「提交件目录」**；受控提供源内的图纸、规范、客户台账同样纳入比对。未提交的**不得记 `S01`**：`src=SUB` 记 `W01` + `S04-S`，`src=CUS` 记 `S04-C`。
- 按对象分组核对（零件号 + 零件名称）；分组失败记 `W01` 并按文件独立核对。
- 空值、占位符、假填充必须区分：空 ≠ `/` ≠ `N/A`，分别记录。
- 「部分文件有、部分文件无」按文件列明，不得概括为「普遍存在」。

### 7.3 数据一致性

判断不同数据之间的关联关系是否自洽。

- 不要求预先指定关联键，基于本批整体内容自主推断，推断依据写入证据链。
- 无依据不得判不一致。
- 跨文件比对的对象是**可及证据集**（`SRC-1` ∪ `SRC-2`，3.2.1）内的全部文件。**对外只有两条方向**：① `SRC-2` 受控提供源（客户图纸、技术规范 / 材料规范 / 订货规范、客户表单模板、客户侧台账、客户已批准偏差记录）；② 项目主数据。`SRC-2` 内的件**必须纳入比对**，不得因其不在提交件目录而视为「没有」。
  > **v0.8 修正**：本行原写「仅限本批已提交文件之间，以及『文件 vs 项目主数据』这一唯一对外方向」，与 3.2.1 正面冲突——v0.7 把 `SRC-2` 加入证据集后，对外方向就不再是「唯一」一条。
- 不得假定跨文件应当一致的零件号。

### 7.4 规则可执行性：本分则不设

「规则可执行性」不属本分则判定范围（见 2.3），分则中 `EXE` / `PF-G` / `PC-F` 类检查项及其「不可判定项清单」「预检不可用」机制一并废止。两类原属规则侧、现象落在文件上的问题重分类保留：

| 原问题 | 新归口 |
| --- | --- |
| 规则所需字段在本批结构上 100% 取不到 | `B05` 关键字段结构上不存在（材料侧阻断） |
| AP 标准表等随文件提交的基准表被改动 | 正确性阻断（材料侧） |

### 7.5 严格标准及其边界

- 宁可严格误判，也不放过潜在不规范；推断性判断必须标注依据与置信度。
- 未识别符号、未在白名单内的取值、未在别名表内的字段名，**不得自行归一化后放行**：写法明显不规范 → `W03`；确实定不了 → `S02`。
- **严格标准只影响"是否记警告"，不影响"是否判阻断"。** 严禁把"看起来很差"判成阻断（见 8.2）。

### 7.6 内容级校验源：分则判定项 + `required_structure`

内容级校验**不再以模板为基准**。校验源有两级，按 4.7 的路由结果取用：

| 优先级 | 校验源 | 判什么 | 不判什么 |
| --- | --- | --- | --- |
| 1 | 分则判定项（公共项 + 客户差异层） | 该分则规定的全部正确性 / 完整性 / 一致性项 | 分则未列的项 |
| 2 | 该客户审核规则的 `required_structure` | **必备结构是否存在、必填字段是否有值** | 字段值是否合理、是否合规、跨文件是否一致 |

**冲突与叠加规则**：

1. **两者并存时取并集执行**，不是二选一。分则项覆盖更细的判断，`required_structure` 补分则未展开的结构性要求。
2. **同一事实两边都命中时只计一次**，取最高级别，证据链注明两处来源（8.6）。
3. **两边口径不一致时，按该条目的判定源层级裁决**（与 4.7 纪律 6 同口径）：
   | 该条目判定源 | 以谁为准 | 理由 |
   | --- | --- | --- |
   | **L1**（有完整深度分则） | **以分则判定项为准** | 分则才是该条目的判定本体，更具体且经实测校准；`required_structure` 在此仅为补充 |
   | **L2**（仅结构判定分则或仅有 `required_structure`） | **以 `required_structure` 为准** | 分则只提供判定方式与边界，不构成本体（4.7 纪律 6） |
   
   无论哪一种，均须在报告注明「该处 `required_structure` 与分则口径不一致，已按 L? 层级裁决，并在第六章登记 `S02`」。**不得**因为两者不一致就判文件不通过——口径冲突属规则侧（2.3）。

4. **客户差异层是覆盖层，不是补充说明**（全库统一通则）：
   | 差异层写法 | 对通用判定项的效力 | 落码 |
   | --- | --- | --- |
   | 「**必备**」/ 给出具体门槛 | 该项在**该客户上生效**，按差异层口径执行 | 按原项级别 |
   | 「**无此要求**」/ 「不要求」 | 该项在**该客户上关闭** | `S02`（规则不适配），**不得判 `B05`／`W01`** |
   | 未提及 | 沿用通用项 | 按原项级别 |

   **冲突时一律以差异层为准。** 理由是**结构能力**：受控模板本体决定文件里能不能有那一栏——通用项若强于差异层，等于要求供应商往甲方模板里加列，那是把模板侧缺陷记成材料侧缺陷（3.1 三分界在状态层的同一处理）。每次关闭 / 生效须在报告 10.6 逐条列明项号，**不得只在执行时默默按差异层处理**。
   > **典型**：10 分则 `M-01` 要求 18 项表头，而 UAES × `T11` 受控模板只有 7 项表头（00-A §4.4 登记为「有」、模板已核对）。按本通则，`M-01` 对 UAES **关闭 11 项**、按 7 项执行；**不得按 18 项判 `B05`**——供应商无权给甲方模板加列。

**`required_structure` 的四条使用边界**：

| 情形 | 处置 |
| --- | --- |
| 声明必备、文件**结构上无此列/无此栏** | 承载关键字段 → `B05`；仅少一路交叉来源 → `W01`（按 7.2 分流） |
| 声明必填、**个别单元格为空** | `W02` |
| 声明必填、**整列全空或无一个可判定值** | `B05`（5.2 边界表：整列空 = 结构不可用） |
| 有值，但**是否满足规则意图需人判断** | `S03` 移交，**预检不判** |

**硬约束**：

- **不得**用模板比对替代 `required_structure`。项目有模板 ≠ 文件必须与模板一致；供应商文件（场景 A）基本不会与模板完全一致，按模板比对会制造大量误判阻断。
- **不得**因 `required_structure` 未抽取、过时、或与规则正文不符而判文件不通过——这属规则侧（2.3），该类目/条目返回「未执行」（5.1）。
- **不得**只在报告里写「结构不完整」，必须指明是 `required_structure` 的哪一条、缺哪一列/哪一字段。

### 7.7 深度模式（可选运行档）

| 档 | 触发 | 范围 | 增量 |
| --- | --- | --- | --- |
| **标准档**（默认） | 默认开启 | 只对 L1 / L2 条目执行完整校验 | — |
| **深度档**（可选） | **仅当用户显式开启时生效**（默认关闭）。**识别置信度为「中」不自动触发**——4.5 放宽后「中」将明显增多，若让它自动触发，可选档就变成默认档了 | L1 / L2 同标准档；**另对 L3 条目**尝试按「通用结构 + 通用必填字段」做试探性判定 | 给出「疑似缺结构 / 疑似缺字段」清单，统一标注「建议人工复核」 |

> **深度档不因置信度自动开启**（v0.6）：档位是**运行成本选项**，由用户决定；置信度是**识别可靠性**，只影响路由与标注。二者不能互相驱动。

**深度档的三条硬约束**：

1. **不改变规则范围，不改变点数，不改变级别判据。** 深度档只是「多看一层」，不是「判得更重」。
2. **试探结论置信度上限为「中」**，且只能落 `W01` / `W02` / `W03`，**不得据此判阻断**——L3 条目本无该客户的判定基准，试探出的差异不能算供应商的错。
3. **深度档结论必须与标准档结论可分离**：报告中单列「深度档试探项」小节（第十章 10.4），不得混入第四、五章的正式问题清单。

**为什么需要深度档**：场景 A 下供应商文件常「弱匹配」——版式不像任何一个标准形态。标准档此时只能落 `S02` 放行，深度档至少能给出「你这份文件可能缺了受控日期栏」这类可行动的提示，与客户规则中「无法辨识则不通过、须提醒人工复核」的既有落点一致。

## 8. 严重级别与通过规则

### 8.1 级别定义（仅两级）

| 级别 | 定义 | 影响结论 |
| --- | --- | --- |
| 阻断 | 该问题导致至少一条审核规则**无法得出唯一结论**——含"取不到数"与"结论方向不唯一"两种 | 是 → 不通过 |
| 警告 | 判定仍可完成，但结果不完整或存在被误判风险 | 否 → 仅记录并移交 |

**定级判据只有一句：这个问题是否让某条规则无法得出唯一结论。** 与"是否严重""是否合规""整改成本多高"无关。

### 8.2 通过规则

- **无阻断项 → 通过。**
- **存在任一阻断项 → 不通过。**
- **警告项不影响结论**，但必须 100% 列入报告警告清单，逐条列明，不得合并、不得概括为「其余若干」。
- **状态项（`S01`~`S05`）与「未执行」不参与通过判定**（3.1 已定：状态不是级别）。其中 **`S05` 待核项不阻断放行**——文件按其余判定项给结论、可进入下一阶段审核；但通过结论**必须连载「含待核 N 项」**，且 N>0 时报告须有 7.2c 的待核行与一章的「重点关注」行。**只写「通过」而不写「含待核 N 项」，视为报告不合格。**
- 「通过」不构成"数据无问题"的结论。报告中禁止出现「数据无问题」「数值全部合格」「无造假风险」。

### 8.3 警告的补偿条款（强制）

警告不拦截后，其约束力全部来自下游，因此必须锁死三条：

1. **全量列报**：警告项 100% 进入报告，逐条含位置、证据、影响、整改方向。
2. **移交留痕**：警告清单作为附件随报告移交正式审核，不得删减。
3. **不得免检**：正式审核**不得因「预检已通过」而跳过警告指向的字段**。警告是移交清单，不是免检证明。

报告模板中此三条须以固定话术出现（见 11.8）。

### 8.4 禁止降级原则

- **某类问题在全批次普遍存在，不得因其普遍性而降低级别。** 行业性缺口恰恰是预检最应拦住的问题。
- 报告的相应条目须注明「该问题在本批次普遍存在，属系统性缺口，非个别疏漏」。
- **禁止的调整**：阻断 → 警告（除 8.5 允许外）；因**识别 / 路由置信度**低而降级（**已确证的事实**应保持级别并标注置信度）；因整改成本高而降级。
  > **与 8.6 的分工（v0.8 明确）**：本条规定的是「**已经确证的事实**不因识别得不准而降级」，防的是拿「我可能认错了客户」当减责理由；8.6 规定的是「**推断本身**置信度低时不得单独构成阻断」，防的是拿「我猜的」当证据判不合格。二者管的是两件事，不是矛盾。判别的问法只有一句：**这是已读到的原文，还是我推出来的意思？**

### 8.5 允许的级别调整

| 方向 | 触发条件 | 要求 |
| --- | --- | --- |
| 警告 → 阻断 | 该警告直接导致下游规则完全无法计算或无法比对。**但不含「缺对照件」**——7.2 已定级为 `W01` 且明令不阻断；该项因缺对端而无对象时按 3.1 / 3.2 记 `S04-S` 或 `S04-C`，**不得改判阻断** | 报告中说明调整理由 |
| 阻断 → 警告 | 存在**同源替代载体**（另一格式 / 另一份同源文件可读出同一事实） | 须注明替代载体位置 |
| 任何级别 → `S01`/`S02`/`S03` | 经确认属范围外、规则不适配或应移交正式审核 | 须记录确认来源，不得自行推定。**本行不含 `S04` 系与 `S05`**（见下方注） |

> **`S04`（含 `S04-S` / `S04-C`）与 `S05` 都不在本表任何一行之内。** 二者均由**客观事实**决定——`S04` 由「对端确实未提交」决定，`S05` 由「客户受控模板本体确实没有该栏」决定——不是级别调整的结果：既不能通过调整「获得」它们来消解一条阻断，也不能通过调整把它们变成级别。凡出现「先判阻断、再调成 `S04` / `S05`」的，属违反 8.4。  
  > **`S05` 为什么必须写进这条禁令**：`S05` 是「不阻断」，而 `B05` 是「阻断」，两者只差一个字母、现象都是「结构上没有这一栏」——这正是最容易被当成「降级开关」的一对。**唯一合法的分流路径是 5.2 两问**（先问文件列结构、再问模板本体），不是「觉得应该宽一点就记 `S05`」。

### 8.6 去重与冲突

- 同一事实落入多个检查项，取最高级别，证据链注明「同时构成 X 类问题」，**只计一次**。
- 同一根因导致多条规则失败，合并为一条问题、并列关联规则，级别不变。
- **推断**的置信度为低时，该推断**不得单独构成阻断**（须另有已确证证据支撑，或改记 `S02` / `S03`）；判不了就记 `S02`，不得硬判。已确证事实的级别不因识别置信度下调（8.4）。
- **跨文件比对项的去重另见 10.3**：同一处跨文件冲突只在一个分则计阻断，另一侧记 `S03` 移交。本节的去重适用于同一文件内部。

### 8.7 共用母版与共用附件的去重

同一批次内，多份文件常共用同一份母版、同一张计划表或同一段附件（典型：多台量具的 MSA 报告共用一张「目录」计划表；同系列特性共用同一张 CPK 页眉）。

**处理规则：**

| 情形 | 列报要求 | 计数 |
| --- | --- | --- |
| 缺陷位于共用母版本身 | **每一份引用它的文件均须列报**该缺陷，不得因「反正在别的文件里已写过」而隐藏 | **只计一次阻断**，计入首个出现的文件 |
| 其余引用件 | 文件级结论栏标注「继承自共用件 `<文件名 › 工作表>`」 | 不重复计 |

**两条硬约束：**

1. **不得静默去重。** 只在一份文件列报、其余文件只字不提，会让审阅者误以为其余文件没问题——必须逐件标注继承关系。
2. **文件级阻断数之和 ≥ 分则级阻断项数。** 若两者相等，说明本批次无共用件缺陷；若前者大于后者，差值即继承计数，报告中须写明「其中 N 项为共用件继承，不重复计入」。

## 9. 报告话术纪律

- 缺项写「本批次未识别到」，**不得**写「缺失」「未提交」。
- **「范围外」只给 `S01`**（该对象本就不属本次范围）。属本次范围而应收未到的，按来源写：`src=SUB` → 「本批次未识别到」（配 `S04-S`）；`src=CUS` → 「受控件未随批，需向甲方索取」（配 `S04-C`）。三者**都不得**写「缺失」「不一致」，**也不得**把后两种写成「范围外」——那会让缺件从整改单与索取清单里消失（3.1 硬约束 2、3）。
- 移交写「移交正式审核」，**不得**写「不合规」或「不合格」。
- 通过写「通过预检」，**不得**写「合格」「无问题」。
- 推断结论必须标注置信度（高 / 中 / 低）与依据。

## 10. 责任归属

**只有三侧，无规则侧。**

### 10.1 三侧定义

| 责任侧 | 涵盖问题 | 处理去向 | 是否打回供应商 |
| --- | --- | --- | --- |
| 材料侧 | 文件内容本身的正确性、完整性、一致性问题 | 打回整改 | 是 |
| 提交方 | 范围声明、版本唯一性、文件组织、清单一致性 | 补充声明 / 指定唯一版本 | 否 |
| 解析侧 | 文件可读性不足（损坏、加密、纯图像无文本层） | 转技术支持核查 | 否 |

**归口规则：**

1. 每个检查项**只能有一个主责任方**，以分则该行的责任方列为准。
2. 报告中「打回供应商整改」与「提交方补正 / 解析侧核查」**必须分表列示**，混列会导致范围问题被当成供应商责任。
3. **甲方侧去向不进 10.1 三侧统计**：七章 7.2b 受控件索取清单（`S04-C`）与 7.2c 模板结构性缺陷清单（`S05`）的责任侧记「甲方 / 模板提供方」，**它们不是第四种责任侧**，而是「三侧之外、不进分布」的一类。三.1「级别 × 责任侧」二维计数、11.10 的「责任侧分布」行，**都只统计材料侧 / 提交方 / 解析侧**；甲方侧条目只在 7.2b / 7.2c 分表列示并计入「未审条数」。**不得把它们塞进「材料侧」凑数**——那会让「打回供应商」的条数虚高，与 3.1 / 3.2 的整体方向相反。

### 10.2 责任侧的判别标准

**判据是「修复动作是什么」，不是「问题看起来像什么」。**

| 修复动作 | 责任侧 |
| --- | --- |
| 改文件内容：改字段值、补列、补行、改写法、修正运算关系 | **材料侧** |
| 改提交动作：补范围声明、指定唯一版本、重命名、重新组织文件 | **提交方** |
| 换工具 / 换通道才能把内容读出来 | **解析侧** |

**两条最常见的误挂：**

1. **「跨文件问题」不是责任侧。** 跨文件比对项的责任侧按**缺陷实际落在哪一份文件的哪个字段**来定，不按「这是跨文件问题」定。落在字段取值 → 材料侧；只表现为两份文件对不上、无法定位谁错 → 提交方（配对与归并责任）。判定方法见 10.3。
2. **「普遍存在」不是责任侧，也不是级别。** 见 8.4，普遍性不改变级别。

### 10.3 跨文件比对项的缺陷归属

跨文件比对项（PFMEA ↔ CP ↔ PFD 的零件号与工序号对齐、证书 ↔ 试验报告的时间窗等）的判据只回答「**是否一致**」，不回答「**谁的错**」。若两份文件的报告都就同一处冲突各开一张整改单，会向供应商下达方向相反的两种要求——改哪一份？因此比对失败后**必须先做归属定位，再定级别**。

| 情形 | 识别依据 | 本文件该判定项 | 缺陷计入 |
| --- | --- | --- | --- |
| **A 单向定位到本文件错** | 配对件有内部他证（编号栏内嵌号段、图纸号、其他引用位）指向与本文件不同的值，且本文件无相反他证 | 记**阻断** | 本分则 |
| **B 单向定位到配对件错** | 配对件内部自相矛盾，且矛盾的一侧与本文件取值一致——即配对件的自身他证**支持**本文件的取值 | 记 `S03` 移交 | 配对件所属分则 |
| **C 缺陷确定在配对件、本文件是否有错不可判** | 配对件内部自相矛盾（缺陷确定存在），本文件该字段为单点取值、内部无矛盾可对照 | 记 `S03` 移交 | 配对件所属分则 |
| **D 无法定位** | 两方均无他证；或两方各自内部均有矛盾且方向相反 | 记**阻断** | 本分则（配对件分则同判，但**整改单合并为一张**） |

**四条硬约束：**

1. **同一缺陷只在一个分则计阻断。** B、C 情形下本报告该判定项记 `S03`，但冲突事实、位置、原文取值、影响、证据链**仍须完整列报**，并在责任侧栏写明「缺陷归属：见 <配对件分则> 报告对应条目」。
2. **`S03` 不得用作免责出口。** 只有配对件缺陷**已被证实**（内部自相矛盾，或存在反向他证）才能用 B、C。本文件自身有疑点但未证实、或双方各自均有矛盾且方向相反，属 A、D，仍记阻断。
3. **结论可逆性必须声明。** B、C 情形下本文件结论按 8.2 计算，但报告总体结论须写明：「本结论受 N 项移交事项制约；若正式审核确认缺陷实际在本文件，则本文件结论应改判不通过。」
4. **归属不等于责任侧。** B、C 情形下本文件责任的判定被挂起，判定项级责任侧写「**待定（移交）**」，**不得写成「材料侧」**——那会把整改指向本文件。

**C 情形与 A 情形的分界**：本文件该字段「内部无矛盾可对照」是 C 成立的前提。若本文件也存在同一字段的其他引用位、且该引用位与本文件取值冲突，则本文件自身已不自洽，属 A（或 D），不得记 `S03`。

**与分则的关系**：分则可就本侧文件的常见情形补充落地细则（例：控制计划的编号规则内嵌零件号，构成天然的内部他证，故其跨文件项在配对件缺席时仍可独立判定），但**不得改变 A/B/C/D 的分流逻辑或上述四条硬约束**。

### 10.4 跨文件匹配键的前置校验

跨文件比对（CPK ↔ 控制计划、PFMEA ↔ 控制计划 ↔ PFD、证书 ↔ 试验报告）**必须先证明匹配键可用，再做比对**。

**三条前置校验，任一不通过即停止比对：**

| # | 校验 | 不通过判定 |
| --- | --- | --- |
| K1 | **键在单侧唯一**：同一匹配键在任一文件中只对应一个对象 | 键重复 → 不得判冲突，记 `B03`（身份不可归属） |
| K2 | **键的构造口径已在两侧对齐**：键由哪些字段拼成，两侧必须同构 | 口径不一致（如一侧「序号」是工序内序号、另一侧是图纸气泡号）→ 记 `S02`，并在报告写明两种口径，**不得**按数值前缀强行匹配 |
| K3 | **键可通过名称或规格反证**：键命中后须用名称/规格做一次反向确认 | 名称或规格明显不同（属不同对象）→ 判为「键碰撞」，不得计为冲突 |

**硬约束：**

1. **不得以「编号相同」直接推定「对象相同」。** 编号体系在 PPAP 文件间普遍不统一（工序号、气泡号、件号、特性号混用），单凭编号相等即判冲突，是跨文件比对最高频的误判来源。
2. **名称写法差异不构成冲突。** 「电机舱直径 / 电机舱尺寸」「喉口 / 候口」这类同义写法，只能记 `W04`（非主键不一致），**不得**记 `B06`（两处取值冲突）。
3. **无法构造唯一键时，该比对项记 `S02`，不记阻断。** 预算不出「谁对谁错」的比对，交给正式审核，预检不得硬判。

#### 10.4.1 「唯一标识」与「页序映射」的合法形态

`B03` 的整改方向写着「提供唯一标识或明确页序映射」，但**这两者此前在全库没有格式定义**——供应商照这句话改，改成什么样算合格，无从判断。本节定四档，**按承载物分，不按强弱分**；强弱只体现在它**能支撑到哪一步比对**。

| 档 | 承载物 | 成立条件 | 能支撑到 |
| --- | --- | --- | --- |
| `R-0` | 无 | 页签靠 Excel 自动去重后缀（`(2)` / `（3）` / `-2`）区分，且簿内**无任何**页序登记 | 无 → 记 `B03` |
| `R-1` 定位级 | **簿内页序登记表**（目录页 / 索引页） | 含序号列，取值为 **1..N 连续整数、无缺号无重号**；**行序与工作表顺序逐行对应**；N = 该簿待判页数 | 簿内逐页定位、不重计 |
| `R-2` 语义级 | **页签名**或专用列 | 除公共名称外的差异部分能指认**具体测点 / 腔 / 位置**（`测点1`、`Cav3`、`MP2`），且簿内唯一 | 跨文件逐页比对 |
| `R-3` 字段级 | **数据区列** | 数据区（非表头）存在可唯一区分列（测点号 / 腔号 / 模腔号 / 位置号），逐页填写且簿内取值唯一 | 同 `R-2` |

**按 `R-0` → `R-1` → `R-2` → `R-3` 的顺序取第一个成立档；仅 `R-0` 记 `B03`。**

> **四档只回答「`B03` 是否成立」，不构成对提交方的达标要求。** `R-1` 即合格终点——达到 `R-1` 之后**不要求、也不再核查**是否升级到 `R-2` / `R-3`（见边界 5）。`R-2` / `R-3` 的唯一用途是：**当供应商主动提供了语义标识时，怎么认它**。

**五条边界：**

1. **`R-1` 的「行序 = 页序」必须逐行核，不得只核「行数 = 页数」。** 行数相等而中间错位的（目录跳页、插页、隐藏页）一律视为 `R-0`。核法：第 i 行的名称与该序位工作表名，**按 10.4.2 归一化后**须一致。
2. **`R-1` 不因「目录里名称重复」而失效。** 目录里连续三行都写 `14#位置度` 是**正常**的——序号列已把它们区分开。**重复的是名称，不是键。**
3. **`R-1` 不等于已解决跨文件归属。** 它只保证「簿内每一页可被唯一指认」，不保证「这一页对应控制计划 / PFMEA 的哪一个测点」。故 `R-1` 成立而 `R-2` / `R-3` 不成立时，跨文件比对项按本节硬约束 3 记 `S02`（无法构造唯一键，不硬判），**不得**因「N 页对 1 行」而记 `B06`。**也不得因记了 `S02` 就要求提交方补建页↔测点映射**——`S02` 是「交给正式审核」，不是「打回整改」。
4. **纯数字后缀不算 `R-2`。** `(2)` `-2` `_2` 这类与 Excel 自动去重后缀**同形**的写法，无法与「复制工作表」区分，不承载语义，只按 `R-1` 认；若同时无页序登记表，则为 `R-0`。
5. **不要求、不核查「页 ↔ 测点 / 腔」的对应关系（v0.14 定）。** `R-2` / `R-3` **不作为必达项**，具体三条：
   - **不设「语义标识缺失」判定项**，不产生任何码——既不记 `B03`，也不记 `W`。
   - **工具信息栏（`# Cavities` / `Tool number` 等）只核「是否填写」**（07 `PRE-06 g)` → `W02`）。**填写后不核其与页的映射**，也**不核「腔数是否等于同名页数」**。
   - 理由：腔号 / 测点号与页的绑定属**工艺台账**范畴，不是 PPAP 文件的自证内容——模板无强制承载位，页内数据也反推不出。强行核查只会产出**无法整改**的问题项。

#### 10.4.2 「同一对象」的归一化口径

`K1` 与 `R-1` 都要判「是否同名」，而此前「同名」二字在本框架内**没有定义**。**按以下五步归一后再比，五步全部相同才视为同一名称：**

| 步 | 处理 | 例 |
| --- | --- | --- |
| 1 | 全角转半角（`NFKC`） | `（3）` → `(3)` |
| 2 | 去首尾与内部空白（含全角空格） | `19#粗糙度 ` → `19#粗糙度` |
| 3 | 剥 Excel 自动去重后缀 | `14#位置度 (2)` → `14#位置度` |
| 4 | 同义字 / 同义写法归并（**须有清单**） | `候口` → `喉口`；`孔径` → `孔直径` |
| 5 | 大小写与中英混写归一 | `CPK` = `Cpk` |

**两条硬约束：**

1. **第 4 步的同义清单是受控的，不得即席扩写。** 截至 v0.13 已确认并入清单的只有两组：`候口 / 喉口`、`孔径 / 孔直径`（均在 `776` 实测中确认指向同一物理特征）。新增同义组须同时满足①两侧指向同一物理特征、②不影响任何判定的归属，并在分则的同义字段表中登记。
2. **不得用第 4 步把「不同测点」归并成「同一对象」。** 归一化是为了**识别重复**，不是为了**消除重复**——`14#位置度` 与 `88#轮廓度` 归一后仍是两个对象，`Cav1` 与 `Cav2` 亦然。

**归一化之后必须回原文复述。** 报告写「`14#位置度`（含 `(2)` / `(3)` 两页，共 3 页）」，**不得只写归一化后的名字**，否则读报告的人找不到那三页。

### 10.5 同批文件关联：按（客户 × 零件号）前置

跨文件比对的前提是**先找到对端**。场景 A 的供应商文件不以模板组织、也不按 PPAP 编号命名，只能靠（客户 × 零件号）把它们串起来。这一步必须在内容级校验**之前**完成，否则「缺对照件」会被误判成「文件本身有问题」。

| 步 | 动作 | 失败处置 |
| --- | --- | --- |
| 1 | 按（客户 × 零件号）分组：同组内文件视为同一零件的同批提交件 | 零件号缺失或不可归一 → **提示提交方补选，不判阻断**；该文件按单文件独立判定，报告注明「未参与同批关联」 |
| 2 | 在组内列出本批**已建立的**跨文件依赖（`T11` CP ↔ `T10` PFMEA ↔ `T09` PFD；`T07`↔`T08`；`T11` ↔ `E12` PGQP1；`E04` 证书 ↔ 试验报告），并**把 `SRC-2` 受控提供源一并纳入核对范围**（3.2.1） | 对端在**可及证据集内不存在**时：`src=SUB` → `W01` + 受阻判定项 `S04-S`；`src=CUS` → `S04-C`（**不配 `W01`**）；正文写明「**缺比对文件《…》**」；**均不阻断**（3.2、7.2） |
| 3 | 键唯一性（K1）与构造口径（K2）、名称反证（K3）校验 | 按 10.4 处置：键重复 → `B03`；口径不一致 → `S02`；键碰撞 → 不计冲突 |

**四条硬约束**：

1. **同批关联只用于「找对端」与「提示缺件」，不得用于推定应有件数。** 「这个零件应该还有一份 PFMEA」不是证据（4.4 证据封闭性）。
2. **不得跨零件号强行配对。** 关联键缺失或归一时，宁可该项记 `S02`，也不得把 A 零件的 CP 与 B 零件的 PFMEA 拉来比对——那会产出方向完全错误的整改单。
3. **客户不同不配对。** 同一零件号交给两个客户时是两套结构要求，跨客户比对无意义。
4. **关联结果写入报告**：第二章逐文件写「同批组号」，第十章 10.5 写「组内已提交件 / 缺对端件 / 未参与关联件」。

## 11. 报告模板（统一报告模板 v1.0）

### 11.1 单一模板与强制力

全部规则（1 份总纲 + **27 份分则** = 10 份 L1 完整深度分则 + 17 份 L2 结构判定分则，另 1 份配套路由表 `PPAP-00-A`）输出**同一套报告结构**。

| 事项 | 规定 |
| --- | --- |
| 章序 | 十章固定，顺序不可调整 |
| 章名 | 固定，不得改写（如「阻断项明细」不得写成「拦截项汇总」「问题清单」） |
| 字段 | 第四章十条字段固定，只可增不可减（见 11.4） |
| 话术 | 第八章逐字保留（见 11.8） |
| 分则差异 | 一律下沉至第十章「附录·分则附加节」，**不得插入一至九章之间**（见 11.9） |

**分则不得自行定义报告结构。** 分则原「报告模板」章节一律改为对本节的引用 + 附加节挂载清单。

### 11.2 十章结构

| 章 | 名称 | 必备 | 主要内容 | 建议篇幅 |
| --- | --- | --- | --- | --- |
| 一 | 结论摘要 | 是 | 结论、原因码分布、三档计数、可否进入正式审核、一句话判断 | ≤ 10 行 |
| 二 | 提交范围与文件集 | 是 | 文件清单、载体族/模板代际、可解析性、范围判定 | ≤ 15 行 |
| 三 | 问题总览 | 是 | 级别 × 责任侧二维计数、原因码分布、首查清单 | ≤ 20 行 |
| **四** | **阻断项明细** | 是 | **逐条卡片，十条必填字段，含单元格级整改建议** | **全文 25%~40%** |
| **五** | **警告项明细** | 是 | **逐条卡片，100% 列报，不得合并概括** | **全文 25%~40%** |
| 六 | 状态登记 | 是 | `S01` / `S02` / `S03` / `S04-S` / `S04-C` / **`S05`（注明「已核对」/「待核」）** / 未执行，逐条列报 | ≤ 15 行 |
| **七** | **整改建议汇总** | 是 | **按文件分组、含 7.4 跨文件合并整改、7.5 复检要点** | **全文 15%~25%** |
| 八 | 结论作用域与局限性声明 | 是 | 固定话术，逐字保留 | 固定 |
| 九 | 附录·检查项全量结果 | 是 | 全部规则项 × 结果 × 原因码 × 问题号 | 视规则条数 |
| 十 | 附录·分则附加节 | 选 | **客户差异层、路由结果**、载体族判定、模板代际、要素矩阵、版本路由等 | 视分则 |

**篇幅纪律**：一、二、三章合计不超过全文 20%；四、五、七三章合计不少于 70%。**若报告读起来「结论很长、问题很短」，即为不合格报告。**

### 11.3 设计取向：问题项与整改建议是报告主体

报告的价值不在「通过 / 不通过」这四个字，而在**让供应商看完就能改**。故三条硬性要求：

1. **四、五章是主体**。每条问题独立成块，不得压缩成表格里的一行摘要——表格一挤，位置和证据必然被省略。
2. **每条问题必须「三固定」**：

   | 固定项 | 要求 | 不合格写法 |
   | --- | --- | --- |
   | 固定位置 | 到单元格：`文件 › 工作表 › 单元格`；多单元格给区间 | 「材料清单表格中」「计划表里」 |
   | 固定证据 | 照录单元格原文；公式给公式串；空值写 `(空)` | 「内容不对」「明显有误」 |
   | 固定整改动作 | 写清「改成什么值」，可被直接执行 | 「请核实」「建议完善」 |

3. **七章不是四、五章的复述**。四、五按「问题」组织，七按「**改哪份文件、一次改完**」重新组织。两者视角不同，不允许复制粘贴。

### 11.4 一条问题的十项必填字段

| # | 字段 | 要求 | 反例 |
| --- | --- | --- | --- |
| 1 | 位置 | 文件 › 工作表 › 单元格（或行列区间） | 「目录页」 |
| 2 | 证据 | 单元格原文照录，不得改写、概括、翻译 | 「表头缺列」 |
| 3 | 判定依据 | 分则规则号 + 总纲条款号 | 「不符合要求」 |
| 4 | 原因码 | `B01`~`B06` / `W01`~`W06`，一条一个 | 「有问题」 |
| 5 | 影响 | 阻断：使哪条规则无法得出唯一结论；警告：存在何种被误判风险 | 「影响审核」 |
| 6 | **整改建议** | 按 11.5 写，或指向第七章对应条目号 | 「请核实」 |
| 7 | 责任侧 | 材料侧 / 提交方 / 解析侧（按 10.2 判据） | 「规则侧」 |
| 8 | 置信度 | 高 / 中 / 低 | — |
| 9 | 关联 | 同源问题号（`B-03`、`W-07`），无则 `—` | 留空 |
| 10 | 出处 | 跨文件问题时标首次出现位置 | 留空 |

**任一项留空或填写反例内容，该条视为未完成，不得计入阻断/警告计数。**

### 11.5 整改建议的写法（硬约束）

**一条合格的整改建议 = 目标文件 + 目标位置 + 现状值 + 目标值 + 验证方式。**

| 合格 | 不合格 |
| --- | --- |
| `材料清单 › C9：现为「宁波法莱欣」，应改为该零件的供应商零件号（与图纸/PSW 一致）；改后须与 B9 的零件号一一对应` | 请核实供应商零件号 |
| `毛坯CPK › 95#螺钉孔直径 (2) › E7：现为 «F01R10Y704»，应改为 «F01RD0Y776»（与同文件其余 48 张表一致）` | 零件号不一致，请确认 |
| `5 份 MSA 共用的「目录」表头：增补「精度/分辨率」「分析项目」两列，逐行填写；若模板不支持增列，改由提交方出具列映射说明` | 建议完善计划表 |

**禁用整改话术**（出现即视为该条未完成）：
「请核实」「请确认」「请注意」「建议完善」「予以规范」「加强管理」「举一反三」「下不为例」「按标准执行」「确保一致性」「如有问题请反馈」

**允许的整改动作只有四类**：**改值 / 增补 / 删除 / 重做映射**。

若一个问题无法用这四类动作描述，说明它**尚未定位到具体字段**——此时应退回补充证据，**不得**先写一条模糊建议凑数。确实无法定位到字段的，记 `S03` 移交，并在六章登记。

### 11.6 第四、五章正文格式（卡片式）

每条独立成块，标题为「编号 ｜ 一句话问题」：

```markdown
#### B-01 ｜ 5 份 MSA 共用计划表结构缺 2 个必填列

| 字段 | 内容 |
| --- | --- |
| 位置 | `MSA-1~5 › 目录 › 第 4 行表头`（5 份文件同一母版） |
| 证据 | 表头实为 9 列：序号 / 测量工具名称 / 工具编号 / 产品名称 / 测量参数·公差范围 / 计划开始日期 / 计划完成日期 / 结果 / 备注；无「精度/分辨率」、无「分析项目」 |
| 判定依据 | 06 分则 `MSA-PRE-18`；总纲 5.2 边界表（整列不存在 → `B05`） |
| 原因码 | `B05` |
| 影响 | `P-10` 分辨率十分之一法则无法执行；`P-06` 计量型/计数型一致性无从比对 |
| **整改建议** | 见 **7.1-①**（同一动作，5 份文件只需改一处母版） |
| 责任侧 | 材料侧 |
| 置信度 | 高 |
| 关联 | 与 `W-03` 同源（共用母版） |
| 出处 | `MSA-1-卡尺.xls › 目录`（其余 4 份为同源副本） |
```

**编号规则**：阻断用 `B-01`、`B-02`……；警告用 `W-01`、`W-02`……（**不得**与阻断原因码 `B01`~`B06` 混写成同一形式，故加连字符）。三章「问题总览」与七章整改汇总**必须使用同一套编号**，实现双向可查。

### 11.7 第七章的分组规则（防「分头改、改出新问题」）

七章按**文件**分组，不按问题分组——同一文件的问题集中一处，让供应商一次改完。

| 小节 | 分组依据 | 必含列 |
| --- | --- | --- |
| 7.1 材料侧（打回供应商整改） | 按**文件**分组，组内按位置从上到下排序（模拟逐个单元格改） | 位置 / 现状值 / 应改为 / 关联问题号 / 优先级 |
| 7.2 提交方补正 | 按**动作**分组：补范围声明 / 指定唯一版本 / 重命名 / 重组文件 | 动作 / 对象 / 要求 / 关联问题号 |
| 7.3 解析侧核查 | 按**工具**分组 | 文件 / 现象 / 需何种工具 / 关联问题号 |
| **7.4 合并整改项（强制）** | **跨文件同根因的问题合并为一条** | 根因 / 涉及全部位置与取值 / 统一应改为 / 关联问题号 |
| 7.5 复检要点 | 按问题号 | 复检范围 / 合格判据（**只列，不执行复检**） |

**7.4 为强制项，不得省略。** 判据：同一事实在 ≥2 份文件中以不同形态出现（如同一零件号在不同文件写成 5 个变体、同一母版缺陷在 N 份文件重复），即须合并为一条「合并整改」，并在正文列出**全部**受影响文件的取值。

> **7.4 防的是**：同一事实按分则分头下发整改时，供应商各改各的、改出新变体。

### 11.8 固定话术（逐字保留，不得删改）

**第一章末尾**：

> 本预检只判定「本批能否被可靠审核」，不判定「文件是否合规」，不执行修复与复检。**「通过」只表示「能审」，不表示「审过了没问题」。**

**第五章章首**：

> 下列警告不拦截放行，但 100% 随本报告移交正式审核。**正式审核不得因「预检已通过」而跳过下列任何一条指向的字段。** 警告是移交清单，不是免检证明。

**第八章（固定六条 + 分则一条）**：

- 本预检不判定文件是否符合客户要求、IATF 16949 或 AIAG PPAP 标准。
- 本预检无法区分「真缺项」与「本批次未提交」，缺项类结论只能表述为「本批次未识别到」。
- 未声明提交范围时按部分提交推定，相关缺失类判定不构成缺件阻断。
- 警告项不拦截放行，但已全部列入第五章并随本报告移交正式审核。
- **正式审核不得因「预检已通过」而跳过警告项指向的字段。** 警告是移交清单，不是免检证明。
- 本预检不执行修复、补全、格式转换与整改后复检。
- 〔分则补充一条：本预检**不判定**该类目的业务结论是否合格，具体范围见第 10 章 10.1〕

**第九章末**：结论为不通过时，材料侧问题须完成线下整改后重新提交，重新以无状态方式执行；本预检不包含整改后复检流程。

> - **`已核对`** — 打开过客户受控模板本体，确认模板里确实没有该栏。**结论为定论。**

>
> **「建议方案（含放行口径）」列的固定写法**：本列不只写「向甲方申请模板变更」，还须写清**放行处置**与**下游动作**，三段缺一不可：

> | 段 | 内容 | 示例 |
> | --- | --- | --- |
> | ① 建议方案 | 向谁、要什么 | 「向 UAES 索取该类型受控模板电子件，补登 00-A §4.4.9 台账」 |
> | ② 放行口径 | `已核对` → 「本项为定论，不阻断」；`待核` → 「**本项不阻断，已放行**，允许该文件进入下一阶段审核」 | 「本项不阻断，已放行」 |

## 12. 执行要求与约束

1. 严格按 2.3 排除规则侧问题，**不得输出任何关于规则集、字典、口径的问题**。
2. 只判本批文件内可自证的事实，不得引入外部历史库或跨批次证据。
3. 不得因"应该有但没交"判缺件阻断；缺项按 3.2.4 分流——`src=SUB` 记 `W01` 警告，`src=CUS` 记 `S04-C`（**不配 `W01`**、不进缺件数）。
4. 不得把"看起来很差"判成阻断；阻断的唯一判据是 8.1。
5. 「不适用」一词禁用，必须按 3.1 拆为 `S01` / `S02` / `S03` / `S04-S` / `S04-C` / `S05`。**对端未提交不得记 `S01`；判 `S04` 前必须先核「可及证据集」（3.2.1），不得以「不在提交件目录」代替「取不到」；判 `S05` 前必须先查《00-A》§4.4 登记值并按 5.2 两问走完，不得以「客户大概没这栏」代替「打开过模板本体」。**
6. 警告项必须 100% 列报，不得省略、合并、概括。
7. 同一事实只计一次，取最高级别并注明。
8. 报告必须包含第八节局限性声明，逐字保留。
9. 不修复、不补全、不转换、不复检。
10. 每次调用无状态，不继承历史整改记录。
11. **报告结构一律按第 11 节统一模板输出**，章序、章名、十条字段、固定话术不得改动；分则差异只允许下沉至第十章附录。
12. **每条问题必须给出单元格级位置与可执行整改动作**；整改建议中出现 11.5 禁用话术的，该条视为未完成，须补证据后重写，不得计入手工统计。
13. **第七章 7.4「合并整改项」为强制项**：同一事实跨 ≥2 份文件以不同形态出现时，必须合并为一条并列出全部位置与取值。
14. **共用母版缺陷按 8.7 列报**：每份引用件均须标注继承关系，只计一次阻断，且须写明继承计数。
15. **必须先完成（客户 × 文件类型）识别与路由，再做内容级校验**（4.5~4.7）。报告第二章缺「客户 / 类型 / 判定源」三列的，视为不合格报告。
16. **不得以模板作为结构合格判据**（7.6）。不通过理由中出现「与模板不一致」的，该条无效，须改按分则判定项或 `required_structure` 重新取证。
17. **识别失败与无规则覆盖必须分开归口**（`B03` / `S02`），不得合并写作「未匹配」，不得互换（4.8）。
18. **人工指定后必须重新路由并重跑校验**（4.9），不得沿用指定前的结论；指定动作须在报告中留痕。

### 附录 B · 命名与版本规范

**文件名格式**：`PPAP-<类别号>_<对象名称>_预检规则_v<主版本>.<次版本>.md`

| 规则 | 要求 |
| --- | --- |
| 类别号 | 与 `PPAP文件集/文件/` 目录前缀严格一致；子类用 `-1` `-2` `-3` 后缀 |
| 对象名称 | 与 PPAP 类目正式名称一致，不加"数据标准化"等冗余前缀 |
| 版本号 | **以文内元信息表为准**，文件名必须与之相同 |
| 后缀 | 统一为「预检规则」，不再使用「Skill 描述」 |
| 配套矩阵文件 | `PPAP-00-A` 为配套文件而**非分则**，命名沿用同一规范，类别号记 `00-A`；其版本独立迭代，不受分则版本约束 |

### 附录 D · 类目覆盖三级口径

本期 41 个（客户 × 类型）条目的判定源分布：

| 判定源 | 条目数 | 含义 | 内容级校验深度 |
| --- | --- | --- | --- |
| **L1 分则直判** | 19 | 有分则，按分则判定项（公共 + 客户差异层）执行 | 完整 |
| **L2 规则驱动** | 22 | 无完整深度分则（含**已配结构判定分则**的条目，如 `E03`），按该客户规则的 `required_structure` 执行 | 结构存在性 + 必填性 |
| **L3 无规则覆盖** | 0（本期范围内） | — | 不做内容级校验 |

**判定源不随分则数量变动**：为 L2 条目编写结构判定分则（如 `PPAP-E03` 包装方案）**不改变其 L2 归属**——分则只提供判定方式与边界，判据本体仍为 `required_structure`（4.7 纪律第 6 条）。

**核心 17 类中本期无 L1 分则的类型**：`T05` 检具验收、`T06` 模具验收、`T09` PFD、`T12` 特殊特性、`T13` 设备清单、`T14` 产能评估、`T15` 项目问题、`T16` 年度试验、`T17` PSW。它们在对应客户下走 **L2**，做必备结构与必填字段校验。**「有规则、无分则」不得表述为「不支持」**——这是拆分模板覆盖与规则覆盖两个指标的原因（PRD 模板库卡片须分列 `N1/总类` 与 `N2/总类`）。

**本期范围外**的（客户 × 类型）（如向蔚来提交检具验收报告、向 UAES 提交其未提供规则的类型）一律落 **L3**：仅格式级门禁 + 识别，记 `S02`，提示「该客户 × 类型暂无审核规则」，**不返回「未执行」、不做内容级校验、不计入通过率**。规则文档到位并登记生效后，自动升为 L2 / L1，**无需改本文件**。

其中 `T09` PFD、`T12` 特殊特性在两个 L1 分则中作为跨文件比对对象被引用（09 PFMEA、10 控制计划）；对照件缺失时按 7.2 记 `W01` 警告，不阻断。

**逐条落位（41 条目 × 判定源 × 差异层）见《PPAP-00-A 客户与文件类型覆盖矩阵 · 路由表》。**
