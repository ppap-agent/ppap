## 0. 用法与三条纪律

| 谁用 | 怎么用 |
| --- | --- |
| 预检执行者 | 先按总纲 4.5 定（客户 × 类型）→ 查 §1 路由总表得判定源 → L1 转对应分则，L2 取 §2 的 `required_structure` |
| 分则编制者 | §3 的「结构基线」是该客户下必备的表头与列清单，写客户差异层时以其为下限，不得低于 |
| **产品交互层（发起预检的一方）** | **发起时直接选定客户**（总纲 4.5 **P1 用户指定**）——这是客户要素的最高效力来源，选定即路由，无须再从文件里找 Logo。**但文件内若出现明确可指认的相反标识，必须报「客户冲突」交人工确认，不得静默按用户选择改判**（总纲 4.5 边界 2）。用户未选时按 **`P2` 文件显式标识 → `P3` 表单编号体系 → `P4` 同批互证** 依次取证，四级均不成立判**低置信度**并记 `B03`（完整级序与边界见总纲 4.5）。 |

**三条纪律**：

1. **`required_structure` 只判「结构是否存在、必填是否有值」**，不判字段值的业务正确性（那是 `S03` 移交）。总纲 7.6 已锁死此边界。
2. **本文件不新增级别**。每条 `required_structure` 缺失时落 `B05` 还是 `W01`，一律按总纲 7.2「是否承载关键字段」分流。
3. **本文件与分则冲突时，先看该条目的判定源层级，再看谁为准**（与总纲 4.7 纪律 6、7.6 规则 3 同口径）：
   | 条目判定源 | 冲突时以谁为准 | 本文件的角色 |
   | --- | --- | --- |
   | **L1**（19 条，有完整深度分则） | **以分则判定项为准** | §2 的 `required_structure` 退为**补充来源**；其漏列的必备表头由 §3 结构基线补齐 |
   | **L2**（22 条，仅有结构判定分则或仅有本文件） | **以本文件 §2 为准** | 分则只提供判定方式、级别分流与边界，**不构成本体** |
   
   **无论哪一层，结构清单均以本文件为下限**——分则不得低于 §2 / §3 已列的必备表头；缺的必须补，不能反过来把下限拉低。
   > **但客户差异层可以关掉一条（总纲 7.6 规则 4）**：「以本文件为下限」说的是**分则不得漏列**，不是**每个客户都必须按全部条目判**。分则客户差异层写「无此要求」的项，在**该客户上**关闭并记 `S02`；本文件 §2 / §3 的对应条目对该客户同样不生效。典型：`M-01` 18 项表头 vs UAES 受控模板 7 项——UAES 按 7 项判，`M-01` 其余 11 项对 UAES 关闭。**理由是结构能力：供应商无权给甲方模板加列。**
4. **`S05`（受控模板缺结构）只认 §4.4 的登记。** 该表逐条登记 41 个（客户 × 类型）组合有没有受控模板。**登记为「无」的组合，缺栏一律落 `B05`，不得记 `S05`**——不受限表单格式时，表结构责任在提交方（总纲 3.3）。**登记为「有（待补登记）」的组合缺栏记 `S05` 并标「待核」**；该值**只能由规则运营登记**，不得由提交方发起。
   
   > 本条 v1.2 原写「判定口径以分则为准」，与同文件 §2 开头「判据本体仍以 `required_structure` 为准」**直接冲突**，且与总纲 4.7 纪律 6 冲突。二者其实各防一件事：前者防「用粗结构清单推翻细判定项」，后者防「写份分则就把条目升成 L1」。按层级切开后两件事都保住了。

**同一类型在不同客户下的差异必须显式可见**——例如 `T11` 控制计划在 UAES 要求「图纸 + PFD + PFMEA + PGQP1 四件齐全」（规则 7/8/9/10/12/13），在理想只要求被检文件自身结构（规则 1–6），在蔚来要求 PFD + 特殊特性清单 + PFMEA 三件同批（规则 6/7/8/9）。**三者不可互换判定基准**，这正是把客户并进判定主键的原因。

> **L2 条目可配「结构判定分则」，但不改变判定源。** 为 L2 条目编写的分则只判结构存在性与必填性，属 L2 的文档形态（如 `PPAP-E03` 包装方案；**本期 22 条 L2 已按字典号归并为 17 份结构判定分则，全部到位**，见总纲附录 A）。判定源仍标 `L2`，判据本体仍以 §2 的 `required_structure` 为准（总纲 4.7 加载纪律第 6 条）。**不得**因写了分则就把条目升为 L1——否则三级判定源会随文档增删而抖动。
>
> **适用范围限于 L2 条目（v1.3 明确）**：以上「以 `required_structure` 为准」只管 22 条 L2。**L1 的 19 条恰相反**——它们有完整深度分则，判据本体是**分则判定项**，`required_structure` 只作补充；冲突时以分则为准（纪律 3 的分层表）。旧文只在 L2 语境里说这句话，却未标明范围，读者容易推成「全库都以 `required_structure` 为准」。

> **`E12` 采购件质量计划（PGQP1）不在 41 条目内，这是刻意的。** 41 份客户规则中 UAES 未单独给出 PGQP1 的审核规则；它只被 UAES 的 `T11` CP、`T10` PFMEA、`T07` MSA、`T08` 过程能力四条规则**作为跨文件对端引用**（见 §4.1）。因此：
>
> - 供应商若**单独提交**一份 PGQP1 → 按总纲 4.5 识别为 `E12` → 4.7 路由落 **L3**（本期无规则覆盖）→ 记 `S02`，**不做内容级校验**，**不返回「未执行」**（总纲 4.8 / 5.1）；
> - 它在本期的唯一作用是**同批关联的对端**（§4.1）：缺失时记 `W01` 并写明缺哪一件，**不阻断**；
> - **不得**因「§1 路由总表里查不到 `E12`」判定为登记遗漏而自行补一条 L1/L2 条目——那会让一个无规则的类型凭空获得判定权。

### 4.2 与规则原文的口径校准（必读，防误判）

客户规则是**正式审核规则**，其「不通过」是**业务结论**；预检只判「能否被可靠审核」。以下三类处置共同构成本期校准，均已于 2026-11-02 评审确认。**4.2.1 为本次评审的四类，4.2.2 为同一逻辑下的其余三处，4.2.3 是与它们反向的、不得放宽的四类。**

> **本节不是「级别调整」，不受总纲 8.4「禁止降级」约束。** 8.4 约束的是「已按 8.1 正确判定的级别，不得因普遍性或整改成本而下调」；本节处理的是**从未达到阻断条件**的情形——按 8.1 的唯一判据（是否使某条规则**无法得出唯一结论**），下列四类都能得出唯一结论（值就是值，只是不值得那个分），因此本就不构成阻断。用「降级」描述会让人误以为违反 8.4，故本节统一改称「不构成阻断」。
>
> 与之相对，4.2.3 的四类是**结构不可判或代数不自洽**，压根得不出唯一结论——那才是真阻断，且**不得**以本节为由放宽。

| 情形 | 定级 | 判据 |
| --- | --- | --- |
| 冲突的是**文件版本日期**（表头日期 ↔ 变更履历首末行、CP 版本 ↔ 图纸版本） | `B06` | 无法确定该文件属于哪个版本，版本有效性判定失据 |
| 冲突的是**签署 / 批准顺序**（如批准日早于编制日），两日期本身都可读 | `W06` | 内部不自洽，但「这份文件是否被批准」仍可判 |

> 这一条是为消除分则间口径漂移而补：`E11 顾客工程批准` 的「签名日期颠倒」记 `W06`（§4.2.2），`09 / 10` 的「履历末条日期 vs 表头日期」记 `B06`（本节）——两者看似矛盾，实为上述两类不同事实。

> 这套校准是**本期最容易被误用的一处**：执行者若照抄规则原文的「不通过」，会把 UAES 控制计划的所有供应商文档判成不通过（因为几乎没人一次交齐图纸 + PFD + PFMEA + PGQP1）。预检的价值恰恰是先告诉他们「缺哪一件」，而不是先判它死刑。

本矩阵涉及的「缺项」全部是**跨文件对端未提交**，按总纲 3.1 / 3.2 / 7.2 / 10.5 拆成两个码、三个落点，缺一不可：

**判据（⑥ 步顺序不可颠倒）**：

| 序 | 情形 | 归口 |
| --- | --- | --- |
| ① | 对端在 `SRC-2`（受控提供源）内**已存在** | **正常比对，不记 `S04`**——这一步缺失是 v1.1 的方向性错误 |

1. **不得只记 `W01` 不记 `S04-S`**——那会让「这份文件有 3 条规则实际没审」这一事实从报告中消失，六章状态登记形同虚设。
2. **不得把 `S04-S` 记成 `S01`**——等于宣告「本不该有这比对」，缺件从此不进整改单（这是 v0.5 之前的口径，已废止）。
3. **不得把 `S04-C` 记成 `S04-S` 或 `S01`**——改记 `S04-S` 会把「补交图纸」派给无权出图的一方，改记 `S01` 会让「这条没做成」从状态登记里消失。两者都会让报告失去可信度。
4. **不得把 `S04` 记成阻断**——`S04` 不产生级别，结论仍按「无阻断即通过」（总纲 8.2）；也不得先判阻断再调成 `S04`（总纲 8.5 明令 `S04` 不在任何级别调整路径内）。

### 4.4 客户受控模板登记表

**用途**：总纲 3.1 的 `B05` / `S05` 三分界要用它。判 `B05` 前的第二问是「客户受控模板本体里有没有这一栏」——本表回答「**该组合到底有没有受控模板**」，模板文件本体回答「**模板里有没有那一栏**」。两问都答完，才可落 `B05` 或 `S05`。

**登记依据**：`PPAP模版&规则/模板/{UAES,理想,蔚来}/` 实际文件（2026-11-02 版本，共 29 份），逐份打开核对页签结构、表单编号与表头后登记。**不以文件名推定**——例如文件的 sheet 结构才是判定依据。

**三档读法（v1.5 由两档扩为三档）：**

| 登记值 | 含义 | 缺栏时 |
| --- | --- | --- |
| **有** | 该组合下甲方发布 / 认可了一张表单，**电子模板已在库、可打开核对**，其结构是可判定的基准 | 打开模板本体：**模板也没有该栏 → `S05`**；**模板有该栏 → `B05`** |
| **有（待补登记）** | 该组合下甲方**确有其表**（以图纸 / 口头 / 内部系统 / 往期样件方式指定了格式），但**电子模板未提供**，无法打开核对 | **暂记 `S05` 并标「待核」**——不阻断、进报告 7.2c（标注「模板待补」）；**模板补登后须复核**：若模板确有该栏，改判 `B05`（供应商删列）。约束见 §4.4.8 |
| **无** | 该组合下甲方**不限定表单格式**，提交方可自选或自建表 | **一律 `B05`**，不得记 `S05`、不得以「甲方没给模板」免责 |

> **「待补登记」不是「无」，也不是「有」，是「有而未取证」。** 它把「客户有没有定表」（业务事实）与「我能不能打开核对」（取证状态）分开：前者决定**责任在谁**，后者决定**结论可不可靠**。责任在客户时不该打回供应商，所以暂按 `S05`；取证没做到，所以标「待核」并在报告里声明。**这正是总纲「没拿到模板本体 ≠ 模板没有该栏」那条纪律的落地形态**——不是把未知当已知，而是把未知标出来、给出补登路径与时限。

#### 4.4.5 三点必须记住的观察

**① 「覆盖率」与「严格度」的关系（v1.5 结论已定，不再是待确认项）。**

| 情形 | 缺栏结论 | 严格度 | 谁整改 |
| --- | --- | --- | --- |
| 有模板（库内可核对），模板缺该栏 | `S05` | 宽 | 甲方改模板 |
| **有模板（待补登记），模板未取到** | **`S05` + 待核** | 宽（结论可靠性待补） | **甲方补模板** |
| 无模板（不限定格式），供应商自选表 | `B05` | 严 | 提交方 |
| 有模板且模板有该栏，文件没有 | `B05` | 严 | 提交方 |

**真正需要盯的不再是「谁更严」，而是「待核条数」。** 13 个组合（UAES 的 13 个类目）在模板补登前，其 `S05` 结论都带「待核」标记；补登后必须逐条复核，其中若有模板本来就有该栏的，要改判 `B05`。**这批结论不是终局，是待验证的暂定值。**

**② 模板族 ≠ 客户，模板不得用于反推客户。**

蔚来 `9 潜在过程失效模式及后果分析` 的表单编号是 **`JL-APQP-3-04/V1.0`**，与理想 `APQP-潜在过程失效模式及后果分析（PFMEA）` **完全相同**；两家的控制计划（单页 `控制计划`）、特殊特性清单（单页 `特殊特性清单`）、过程流程图（含 `更新履历` 页）页签结构也一致。

> **结论：这套 `JL-APQP-*` 表单在多客户间通用。** 因此模板结构**只能**回答「这个结构是不是甲方认可的基准」，**不能**用来推定客户（总纲 4.5 / 4.6 的识别规则不受影响，01-2 §6.2「禁止由族反推客户」继续有效）。

**③ 模板本身可能带缺陷，`S05` 正是为它准备的出口。**

已在模板库中发现三类模板侧缺陷，它们都会导致合规文件被判 `B05`：

| 现象 | 位置 | 对判定的影响 |

| 同一文件内两代际并存 | `APQP-模具验收报告`：`JL-APQP-3-10-01/V2.0` 与 `V2.1` | 取哪一代际决定通过与否（动态验证缺口 `B12`） |
| 表单编号重号 | `JL-APQP-4-07` 同时用于 `L15` 项目问题清单与 `L16` 年度试验要求 | 按编号定位会串类目 |
| 表单编号版本落后于实际 | `APQP-检具认可报告` 库内为 `V3`，动态验证样本用的是 `V2.1` | **版本差会被误读成「供应商删列」**——须先比模板版本再判 `B05` |

#### 4.4.8 「有（待补登记）」的四条约束（防滥用）

这个登记值把「暂不清楚」变成「可以先不改判供应商」，因此必须同时把出口收紧，否则它会变成一个万能免责键。

| # | 约束 | 违反的后果 |
| --- | --- | --- |
| 1 | **只能由规则运营登记**，须同时记「指定依据」（图纸编号 / 会议纪要 / 客户邮件 / 往期样件批号之一）与登记日期，**逐条登记在 §4.4.9 台账**。**提交方不得发起、不得自证**。 | 供应商一句「客户口头说过」就能免掉全部结构整改 |
| 2 | **有补登时限**：自登记日起 **60 天**内须取得电子模板并改为「有」或「无」。**逾期未补，自动回落为「无」**，缺栏一律 `B05`。**逐条的登记日、截止日、当前状态见 §4.4.9 台账**——时限以台账为准，不以口头记录为准。 | 长期挂「待补」等于永久豁免一类结构要求 |
| 3 | **报告必须声明**（**报告 10.3 待确认清单**，不是总纲 §10.3「跨文件比对项的缺陷归属」——v1.6 改正一处张冠李戴的引用）：凡因「待补登记」记 `S05` 的，逐条列出「客户 / 文件类型 / 缺失结构 / 待核 / 截止日」，并写明「该结论以客户模板补登后复核为准」。**不得与已取证的 `S05` 混在一起统计**。 | 读者会以为模板已核对过，结论已定 |
| 4 | **不适用于「模板有而文件没有」**。若已确认客户模板含该栏（无论从哪个版本取得），一律 `B05`，不得用「待补登记」覆盖。 | 把供应商删列洗成客户模板问题 |
| 5 | **放行口径**：待核项**不阻断、允许该文件通过并进入下一阶段审核**；但须同时做到三件事——① 报告 **7.2c** 单列该行（核对状态 `待核` + 待核截止日）；② 报告**一章结论摘要**写「**重点关注 N 项**」并注明「该项信息是否存在缺失尚待核实」；③ 报告 **10.3** 声明并写明**下游阶段审核承接复核责任**。**三条缺一即视为用状态码放水。** | 文件「通过了」但没人知道有一条判定根本没做成——问题从视野里消失 |

> **一句话**：「有（待补登记）」解决的是**责任归属**（不打回无权改表的一方），**不解决结论可靠性**（仍标待核、仍有补登时限、仍在报告里单列）。两者不能混。

3. **补登成功 → 打开模板本体逐条复核**：模板确实没有该栏 → 复核结论写「已核对·模板缺该栏」，`S05` 由「待核」转「已核对」；模板本来就有该栏 → 复核结论写「改判 `B05`」，该组合此前因此条记的 `S05` **全部撤回**，改记 `B05` 并派整改。
4. **本表不改变判据。** 它只回答「这条待补登记到没到期」，`B05` / `S05` / `S02` 的三分界、`S05` 的「不阻断」属性、41 条目路由一律不动。
5. **放行的三条配套**：本表条目对应的判定**一律不阻断**，文件可按其余判定项给结论并**进入下一阶段审核**；报告侧须按 §4.4.8 约束 5 的三处落点写全（7.2c 行 / 一章重点关注 / 10.3 声明），并在 7.2c「建议方案（含放行口径）」列写明「**本项不阻断，已放行**」与「下游须复核该文件是否缺少该栏信息」。**补登后发现模板确有该栏的，撤回 `S05` 改判 `B05`，重新预检——放行不等于终局。**

## 5. 范围外条目的行为（L3）

本期范围内无 L3 条目。**范围外**指不在 §1 的 41 条内的（客户 × 类型）组合，例如：

- 向蔚来提交「检具验收报告」（蔚来只提供 5 份规则，不含检具）
- 向 UAES 提交「设备清单」（UAES 19 份规则不含设备清单）
- 向理想提交「实验室资质证书」

**统一行为（总纲 4.8 + 0.1.4）**：

| 步 | 行为 |
| --- | --- |
| 1 | 格式级门禁照常（加密 / 不支持格式 / 扫描件 / 损坏 / 超大小） |
| 2 | 识别五要素照常执行，未识别项记 `—` |
| 3 | 路由结果 = **L3 无规则覆盖**，记 `S02`，**不返回「未执行」** |
| 4 | 报告提示：「该客户 × 类型暂无审核规则，可能因规则覆盖有限导致，请使用标准模板或反馈对应模板扩展规则」 |
| 5 | 用户仍可勾选送审；确认动作时该文件自动移除（`remove_reason = 未匹配到规则`），不计费、不送审 |

**升级路径**：规则文档到位 → 在 §1 对应客户表登记该条目 → 从 L3 升 L2；若该条目另有**具备完整判定深度**的分则（可判正确性 / 完整性 / 一致性），再升 L1。仅有结构判定分则的，不升（总纲 4.7 纪律第 6 条）。
