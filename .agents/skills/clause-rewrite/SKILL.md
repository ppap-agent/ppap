# 条款改写

目的是得到一版**干净、可单独读懂、意思不走样**的条款。只改依据要求改的地方；其余每一句都在新文里有对应。原文没说清的地方不在改写时补上，单独列出，交给 [clause-check](../clause-check/SKILL.md) 审查后进问卷。

整条改写由 agent 逐条读原文后亲手写出。不能用脚本生成、套用、分发或沿用条文和审查记录。脚本只用于写完之后的格式核对、提交和导入导出。

## 输入

只用这几样：

- 该条的原文；
- 答复人对该条卡片的原话（选项与附言）；
- 产品负责人在对话里明确给出的裁定；
- 条款点名的条文以外的那段内容（例如被引用的平台口径）。

不读检查程序及其测试、人工真值、旧修订的正文、以前的审查记录、样本和评测结果。它们是别人对条款的理解，会替客户做掉本该问的选择。

## 不加

- 原文没有的不补：结论句（如「全部满足才通过」「否则通过」）、例子、定义、比较方式、先后步骤都不补。
- 原文列举末尾写「等」或用「如」引出的，保持开放，不写成封闭清单。只有原文逐项列全的，才能整理成固定清单。
- 只在原文明确写了先后时才写顺序（如「核对前先按日期重排」），不从句子先后推出步骤。
- 答复只回答它问的那一处。可以用条文的说法写进去，不必照搬原话；但意思只能来自答复，不推到它没问到的情形，也不替它补判法。

## 不减

- 有判定意义的句子一律不删，包括理由句和执行说明：依据怎么写、提示项、未审、不适用、缺陷落在哪、只记一次、严重度。
- 只删说来历的字眼：编译侧、客户原文、卡片编号、第 N 轮、经裁决、源侧、补充判据，以及指向条文以外文件的引用。
- 来历和「对外怎么说」写进该条的修订说明，不进条文。
- 一句话里既有来历又有规则时，只删来历那几个字，规则照留。

## 照抄

- 引号里的字、数字、比较词（不低于、晚于、≥、＜）、单位，原样照抄。
- 「须」「可」「不得」「才」「即」「之一」「全部」这类词的强弱和范围不变：不把「可」写成「须」，不把「才通过」写成「即通过」，不把只管某一项的例外写成管全条。
- 条款编号与交叉引用（「规则 2」「本条与规则 3」）原样照抄。
- 原文用的词不换成同义词。被引用的口径写进条文时，其中的规则不删减、不增添。
- 条款指向条文以外的一整节时，哪几段要写进来，看每一段在这个操作里起的作用，不看字面像不像：操作开始前的准备步骤属于这个操作，要写（例如「配对方式见……跨文件比对」，比对前先核对是不是同一个零件，就是配对的第一步）；与这个操作无关的段落不写。拿不准的，列出来问产品负责人。

## 不解决

原文的模糊和冲突照原样留着，不靠换说法或重新排版让它看起来确定。规则可以模糊，检查程序也可以按模糊的写法实现。结果不合用户预期时，等用户反馈，或下一轮发卡片问用户；绝不替用户做任何判断。

在产出里单独列出：哪一句、哪里没说清、会让哪类文件的结论不同。我写的句子不能比依据更模糊；但依据本身的模糊，不由我消除。

## 写法

- 用中文和业务词，不用英文记号和技术词。条款要给客户读。
- 整理分节时，小标题只用原文已有的部分：适用、要求、不通过、不适用、例外、记录与提示、定义。原文没有的部分不加。
- 固定清单（占位词、等价写法、列名对应等）在用到它的每一条里各写一份。同名清单在各条之间逐字一致。
- 每条自足：不把别条的规则搬进来，也不引用条文以外的文件。
- 不以省字为目标。省字不能成为删句子的理由。

## 流程：写的人不核对自己

每处改动都带上从依据里摘出的原文，由没参与编写的 agent 独立核对；只有核对通过的改动才进正文，落稿后再由另一个 agent 逐条复核，复核通过的才交付。编写者自己确认不算核对。

工作区按 [workspace/AGENTS.md](workspace/AGENTS.md) 组织：每条条款、每张卡片、每条裁定、每节口径各一个文件；落稿先写候选新文 `draft/<组>/<序号>.md`，复核通过的才交付到 `out/<组>/<序号>.md`。各角色自己读文件，不靠在提示词里转抄原文。

1. **拆成改动单元**（编写者）。每处改动一个单元：
   - 条款；
   - 原句：被改的整句，逐字取自原文。纯新增也带上相邻的那句原句，用来定位；
   - 新句：改后的整句。纯删除时为空；
   - 类型：
     - 照依据：写入答复或裁定；
     - 写入口径：条款点名的条文以外的那段内容；
     - 删来历；
     - 连带改：答复让原句与它冲突时，对原句做的最小调整；
   - 依据：依据编号（卡片编号、裁定日期、被点名的那段），以及从中**逐字摘出**的原文。删来历时，依据就是该条原文，摘出被删的字眼；
   - 说明：一句话说清改了什么。

   交给编写者的每张答过的卡片，都要给出处理结论：已改（有单元引用它），或不需要改（写明原因）。一张卡片涉及的条款分给了几位编写者时，各自只就自己的条款给结论，交付时再合并（见第 7 步）。原文和答复里没说清的地方另列「没说清」，不写成单元。
2. **结构预检**（脚本）。下列单元在核对前直接剔除，记入「未纳入」：
   - 原句、摘录或说明为空；
   - 依据编号不认识；
   - 类型是「删来历」，新句却不是从原句删字得来的。

   原句、摘录是否真在文件里，由核对者打开文件确认。
3. **独立核对**。另起至少两个没参与编写的 agent，分片进行。只给它们改动单元和要读的两个文件（条款文件、依据文件），不给编写者的说明和推理。先确认原句和摘录确实在文件里，再逐个判断：
   - 照依据：依据直接支持新句相对原句的确切意思。没有多出的条件、情形、例子，没有扩大范围，「须、可、不得」等的强弱不变，也没有漏掉依据里的规则；
   - 写入口径：新句写出了被点名那段的全部规则，不删也不增；
   - 删来历：删掉的只有来历字眼，没有删有判定意义的话；
   - 连带改：原句确实与答复冲突，新句只消除这个冲突，不加别的；
   - 删来历和写入口径的单元意思应当不变：设想几份具体文件（含恰好等于阈值、缺件、空白、占位、例外刚好适用这类边界），按原句和新句各判一次，结论必须相同。

   核对时不修补、不放宽单元，判不过就判否，并写一句理由。判通过时，核对者要从依据里**自己逐字摘出**支持这处改动的原文，不能照抄编写者的摘录；摘不出，或摘录在依据里找不到，就算不通过。脚本检查每个单元恰好得到一个结论；编号缺失、重复或出界的那一片整片作废。
4. **落稿**：只用核对通过的单元写出各条候选新文，写到 `draft/`，其余一个字不改，并列出用到的单元。未通过的单元保留原句，连同理由列入「未纳入」。脚本检查列出的单元恰好是该条通过核对的那些。落稿不写 `out/`，所以复核退回或中途失败的条款不会留在交付目录里。
5. **复核**（另起的 agent，分片进行）：逐条读原文、候选新文、该条通过核对的单元和它们的依据文件，判断三点：
   - 新文与原文的每一处差异，都对应一个通过核对的单元；
   - 每个单元都体现在新文里；
   - 没有单元以外的改动、增补或推测。

   不通过的条款退回原文，记入「退回原文」。脚本检查每条条款恰好得到一个复核结论。
6. **交付**：另起一个 agent，把复核通过的候选新文原样搬进 `out/`；再另起一个只读的 agent 列出 `out/` 里实际有的条款文件，确认恰好是复核通过的那些，并且与候选新文一字不差。确认不了的条款记入「退回原文」，写明候选新文在哪里；`out/` 里多出的文件写进「覆盖缺口」。
7. **报告**：先按卡片对账。有改动引用一张卡片的，看这些改动是否都落进了交付的新文；没落进或只落进一部分的，写明卡在哪一步（预检剔除、核对未通过、所在条款退回原文）。一张卡片分给几位编写者时合并成一个结论：只要有改动引用它就按已改对账；每位都判不需要改，才列进「不需要改的卡片」，且只列一次。

   状态写「全部通过」或「部分」。只要有下面任一情况，就是「部分」，并写进「覆盖缺口」（被剔除的改动和退回的条款逐条列在「未纳入」「退回原文」，覆盖缺口里写明各有几处）：
   - 有单元被剔除或核对未通过；
   - 有卡片没有处理结论，或者对不上任何条款；
   - 有卡片标为已改，它的改动却没有全部落进新文；
   - 有编写、核对、落稿、复核、交付失败，或有条款退回原文；
   - 有单元超过数量上限。

   没有缺口时，明确写出：每张卡片都有处理结论，标为已改的都落进了新文；每个改动都通过了预检、核对、落稿、复核和交付。没有一个单元通过预检或核对时，跳过后面几步，照样对账并交出「部分」报告。

[workflow/clause-rewrite.rhai](workflow/clause-rewrite.rhai) 是这套流程的脚本版本，按 grok-shell 工作流的写法编排编写、核对、落稿、复核、交付几类 agent，只做结构检查（编号、覆盖、上限、按卡片对账），不写、不改、不判条文。参数只是条款编号、卡片对应的条款和依据编号这几张短清单，条文由 agent 自己读工作区的文件。脚本自己只能写运行目录里的文件：报告和完整结果写在运行目录的 `scratch/clause-rewrite.md`、`scratch/clause-rewrite.json`，由启动它的一方原样复制为 `out/report.md`、`out/result.json`。改了脚本，先在 grok 里用 `workflow` 工具的 `validate_only` 校验，参数用虚构的编号。没有这个运行环境时，按同样的分工手动进行。

## 产出

每条改动写一节：

- 依据：卡片编号与所选选项、答复原话，或裁定原话及日期；
- 意思：变了／不变；
- 改动：逐处说明改了什么，标明类型；
- 修订说明：来历和「对外怎么说」，没有就不写；
- 正文：完整条文。

最后单独列出：

- 「不需要改的卡片」：以及理由；
- 「未纳入」：被剔除或核对未通过的改动，以及理由；
- 「覆盖缺口」：见流程第 7 步；
- 「没说清」：原文和答复里没说清、本版没有消除的地方。

每处改动同时列出编写者和核对者各自摘出的依据原文。

## 之后

1. 改写后，该条原文的摘要会变，要用 clause-check 重新审查，审查记录逐条手写。
2. 按 [docs/rules.md](../../../docs/rules.md) 的澄清循环提交：改写写明依据的卡片或裁定，再提交新写法的审查记录。
