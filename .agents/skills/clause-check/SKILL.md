# 条款语义审查

目标是减少无效客户问题。只有条款原文不足以决定某个具体场景时，才把问题交给客户。Agent 自身的误读、漏读和建模困难不属于条款缺陷。**工具校验成功不能证明自然语言理解正确。**

本技能不使用 OWL、ROBOT、HermiT、Java，不生成形式化文件或推理缓存。不修改规则原件、审核程序、真值表，也不代替客户作出答复。

## 输入输出

输入是一条规则文件中 rules[].id 和 rules[].rule_to_check；判定只依据这条条款的原文，条款需要的口径必须写在条文里。不要用以前的报告或检查器实现替代原文。工作目录由调用方指定，默认使用 .local/clause-check/<类型>/。

每条规则写一份 <条款序号>.review.json；运行：

    python3 <技能目录>/scripts/check.py <工作目录>/X01-1.review.json

仅依赖 Python 标准库。输出同目录的 X01-1.report.md（白话报告）与 X01-1.report.json（问卷数据）。退出码 0 只表示输入结构、引用、例子差异等机器可检查项合格；1 表示审查记录不合格；2 表示输入或来源不可用。结构校验合格后仍需完成以下语义复核，不能称为「已经证明条款存在冲突」。

先阅读 examples/X01/rules.json 和 examples/X01/X01-1.review.json，再照格式写。--report 和 --data 可以自定义输出路径。报告只能由脚本生成，不手改。

## 1. 逐句建立来源与作用域

完整读完原条款，列出所有明确要求、对象、字段、条件连接词、例外、否定与结论，不能漏掉条款后面的补充限制。在 requirements 中对每项记录 quote（逐字引用原文）、role（条件角色）、scope（作用域）和 meaning（白话含义）。

| 条款用语 | 含义 | role |
|---|---|---|
| A 才通过、只有 A 才通过 | A 是必要条件；满足 A 不必然通过 | necessary |
| A 就／即／则通过、只要 A 就通过 | A 是对应作用域的充分条件 | sufficient |
| 须／必须 A、不得 B | 强制义务或禁令；如何判失败还应核对原文 | necessary / prohibition |
| 否则不通过、任一缺失不通过 | 依照所在前件和作用域确定不通过 | outcome |
| 若 X 则 Y、仅在……情况下 | 条款适用前提 | applicability |
| 某种情况下允许缺项 | 只豁免被明确指向的对象／检查点 | exception |
| 字段别名与等价定义 | 定义而非另一个合格条件 | definition |

**防误报底线**：

1. 「七项全部满足才通过」绝不等于「七项满足即通过」。签字、盖章等独立必要条件仍然有效，不能凭自造的通过结论制造冲突。
2. 某字段或检查点「即通过」不意味着整条规则通过；局部豁免不能抵消其他检查点失败。
3. 只有「须／必须」但没有显式充分条件，不自动得出「原文没给结论」。先核对本条的失败判定；只有真实具体场景仍无法裁定，才可能是缺口。
4. 「找不到证据」「看不清」「软件提取失败」与「原文没有定义」是不同事实；不得互相替换。
5. 不自行增补原文没有的字段、常识、惯例、阈值及对端文件。

## 2. 发现候选问题，并主动试图否证

只记录四类问题：

- ambiguity（歧义）：同一原文确实允许两个以上互相不同、且未被其他明确约束排除的理解；用**同一份具体文件**证明理解不同导致结论不同。
- undefined（未定义的情况）：原文使用的概念、取值或比较方式缺少足以判定的定义；必须关联实际情形。
- gap（缺口）：原文对一个具体适用场景没有给出可用结论，不能因为缺少「否则」二字就认定缺口。
- conflict（冲突）：对同一个文件，同一层级、同一作用域下的两个实际适用结论互相否定。局部条件通过与整条规则不通过并非冲突。

每处候选都必须写 example（具体文件事实）和 challenge（尝试推翻该候选的复核理由）：重新通读条款，核查未参与争议的必要条件与否决项；解释每种理解为何不违反原文，为什么原文尚未排除该解释；核查作用域。如果其中一种理解违背明确的原文，**直接排除问题，不要交客户选择错误理解**。可以把此类被排除疑问及原因写在 excluded 中。找不到真正的发现时，findings: [] 是合格结果。

## 3. 结构化审查记录

输入 JSON 的 schema 为 clause-check-review-v1，source 指向「规则文件路径#条款 ID」，例如 X01/rules.json#X01:1。数据结构：

    {
      "schema": "clause-check-review-v1",
      "source": "X01/rules.json#X01:1",
      "requirements": [
        {"quote": "批准日期不得早于编制日期", "role": "necessary",
         "scope": "日期先后", "meaning": "批准日期不得早于编制日期。"}
      ],
      "findings": [
        {
          "id": "1", "kind": "ambiguity", "quotes": ["已签名"],
          "title": "签字方式", "question": "电子签名算已签名吗？",
          "example": "三方均签名且填日期，批准人为电子签名。",
          "challenge": "原文未限定签名介质，其余签署及日期要求在两种理解下均满足。",
          "readings": [
            {"label": "电子签名也算", "meaning": "电子签名构成已签名。",
             "basis": "原文未限定签字载体。", "verdict": "通过"},
            {"label": "仅手写算", "meaning": "电子签名不能代替手写。",
             "basis": "原文亦未明确电子签字可用。", "verdict": "不通过"}
          ]
        }
      ],
      "excluded": []
    }

全部引文必须能从对应原文找到（忽略空白差异）。每个 finding 必须有 id、kind、quotes、title、question、example、challenge。歧义另需 readings 2～10 项，每项有 label、meaning、basis、verdict；对同一个 example 的 verdict 必须有差异，允许值为「通过」「不通过」「原文未定」。

使用原问卷定位编号：歧义为 1/2，未定义为 1.1/2.1，缺口为 G1，冲突为 C1；问卷键为 X01:1#1 等。不要重复提出同一个问题。排除候选的格式为 {"quote":"逐字引文","issue":"疑似问题","reason":"为什么不是有效问题"}。

客户本人答复后，可在 finding 添加 "resolution":{"answer":"客户原话","source":"答复人和答复渠道"}，保留发现但不再生成待答卡；不得由 Agent 猜测或代填答复。

## 4. 校验、报告与问卷

执行 check.py，仔细阅读它生成的白话报告。脚本检查条款 ID、引用、输入结构、问题与例子的完整性以及读法判定差异，**不检查解释是否符合自然语言逻辑**。这一步必须靠上面的全文审查，并用「才／就」「局部豁免」「多必要条件」「强制项缺充分条件」等已知误报作为回归。

在规则澄清循环里（经 MCP，见 docs/rules.md「规则处理 SOP」），每条审查记录直接作为 `submit_review` 的输入提交：服务端用本技能的 check.py 校验，用 questionnaire.py 的同一个卡片生成函数出卡片，由平台负责人确认发送。下面的问卷整理与 SQL 导入流程用于线下：给另一个企业导入同一批问题，或整理共性问题。questionnaire.py build 读取 *.report.json：

    python3 <技能目录>/scripts/questionnaire.py build <工作目录> <工作目录>/问卷整理.json <工作目录>/问卷导入.json

问卷整理用 customer_id、rule_version、title、common、relayed、applied、conclusion、clause_order 等字段，另加 rulebook_version、rulebook_revision 写明问卷针对规则库的哪个修订（如 v1.0、0；rule_version 须以该版本结尾），规则页按这两个字段把问卷挂到修订上；items 引用发现 ID（如 CP:8#1）。已被排除的旧问题必须同时从整理配置中删除，不能恢复误报只为了凑齐旧列表。

load/export/close SQL 命令需用迁移身份运行；**不要在同一企业的同一规则库修订上直接重新导入**。线上问卷与已保存答复的替换是独立的迁移任务，本技能不自动删除或覆盖。产品负责人确认后才可发布新的问题数据。

导出答复后运行：

    python3 <技能目录>/scripts/questionnaire.py answers <工作目录>/问卷导出.json <工作目录>

脚本仅生成按条款整理的回填清单；由人根据客户原话向对应 .review.json 写 resolution，再重新生成报告。答复有冲突时交产品负责人，不替客户选择。

## 交付标准

客户报告只写原文、具体案例、合理的不同解释、争议造成的判定差异和一句可答复的问题；不写工具术语、推理程序或实现猜测。**条款没有真实问题就明确报告没有发现，不为数量制造问题。**
