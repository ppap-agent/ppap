# 规则处理 SOP

根目录 [AGENTS.md](../AGENTS.md) 的「规则」只给摘要；三种规则的权威、版本与修订、澄清一轮怎么走、用户看到什么和当前不足在这里。

**三样东西，各有一个权威，不要混用**

| 是什么 | 权威 | 谁改、怎么改 |
|---|---|---|
| 审核用的规则（受理时冻结进轮次） | 检查程序目录叶子的 `packages/audit/src/audit/checkers/<公司>/<叶子>/rules.json` → `scripts/compile_v4_presets.py` 编译成 `packages/audit/src/audit/preset_rules.json`（CI 用 `--check` 防漂移）→ 企业成员登录时装进 `product.rule_versions` | 线下改叶子并编译，随发布生效；产品内没有入口 |
| 检查程序 | 目录叶子的 `checker.py`/`resources.py`，按客户成组；官方版本经 `product.seed_standard_suites` 与 `python -m scripts.official_suites` 验证、发布（见 [tests/README](../tests/README.md#官方-suite-验证与发布)） | 线下改叶子，每次部署由 Job `ppap-current-seed-suites` 写入（仓库默认的官方指针随之更新，经语料证明发布的不被替换）；企业采用版本经 `PUT /suites/{key}/active`（只给平台运营，无网页入口；成员可用 `GET` 读当前版本；无指针时返回 `candidate_only`，未验证候选须确认风险；发布回执未知只读回） |
| 规则库修订（澄清中的客户规则） | `product.rulebook_revisions`（每个企业一份；条款存在 `rule_versions`，带 `rulebook_revision_id`，不进入审核匹配） | 规则澄清循环（MCP）或导入命令；写入后冻结 |

另外两条独立路径：企业自定义规则经 `POST /rules`、`/rules/parse`（只给平台运营，无网页入口；发布为企业自己的不可变 Suite，条款先全部为未检查，检查程序由平台线下准备后作为新修订提供；同一前置规则已有后继时返回 `suite_head_conflict`），数据标准化预检（`product.precheck*`）不读规则、不调检查程序。网页规则页对这些都只读，唯一的写是客户成员作答问卷。MCP 的审核流程只按客户 key 选规则组，不改规则。

**版本与修订**
- 版本（v1.0、v2.0……）由条款集合决定：增、删、拆分、合并条款就升版本，只升第一位。修订（修订 0、1、2……）是同一版本内只改条款内容。客户的新稿也按这条判断。
- 条款标识是「客户 + 版本 + 文件类型缩写:编号」，缩写和编号照抄客户原件；同一版本各修订的编号集合相同。
- 修订写入后冻结，只能之后记下「已澄清」。每处改动都要写明意思变没变和依据（卡片与答复人，或客户裁决原话）；说不出依据的改动不进修订。经他人转达、没有客户原始答复的口径不算客户已确认。
- 确认人是产品负责人（平台运营身份 `PPAP_PLATFORM_OPERATORS`，格式 `tenant_key:open_id`，空即无人可写）。受委托的审查方（`PPAP_CLAUSE_REVIEWERS`）只准备、不确认、不作答。

**澄清一轮怎么走**
1. **收规则**：客户规则线下发来。平台按原件拆成修订目录 `<客户>/rulebook/<版本>/m<修订>/rules/<缩写>.json`，用 `python -m product.rulebook_import check <目录> --original <原件>` 逐句核对原文（不调模型；Markdown 排版与空白不计）；通过后 `bundle` 输出请求体（stderr 给出路径），平台运营身份登录 PPAP 后在同一站点把它 POST 到 `/ppap/rulebooks/<客户>/revisions`（Cookie 会话）。也可由 Claude 经 MCP 提交拆好的条款，审查、解读在冻结前就准备（见下）。不做在线导入。随产品发布的规则库目录（`assets/<客户>/rulebook`）在企业成员登录时原样写入。
2. **审查**：经 MCP `prepare_rule_clarification` 打开这个版本的澄清任务（一个企业对一个客户的一个版本只有一个），按 `next` 走。审查的是下一次确认要冻结的写法：草稿、改写后的下一修订，或当前修订。每条条款用 [`clause-check`](../.agents/skills/clause-check/SKILL.md) 审查并提交审查记录，没有问题也要提交；服务端用该技能的 `check.py` 校验，不合格之处一次列全。效果用 [`bench/clause-check`](../bench/clause-check/README.md) 对比。
3. **发问卷**：发现由该技能 `questionnaire.py` 的同一个函数做成卡片（修订 0 的卡片编号是发现编号如 `CP:8#1`，之后的修订带修订号如 `CP:8#r1.1`）。卡片在下一次确认里作为单独一步，标着「会发给客户」，默认不勾，平台负责人勾选并确认后才进入问卷，可分批追加；答复过这个版本问卷的人收到飞书通知，第一次发时没人答复过就不通知。要让另一个企业也作答，用 `questionnaire.py` 以迁移身份线下导入，各企业答复分开保存。答复按人分开、追加保存，不设最终答复。客户成员保存答复时（#354），这个版本澄清任务的准备人和平台负责人收到飞书通知（答复人自己除外），点开是规则页上那张卡片；同一修订每人 10 分钟最多一条，其间的答复到点合并成下一条。没有澄清任务的问卷不通知；规则页上可按人、按版本点「这个版本不再提醒」，答复仍在规则页可看。MCP 等答复时的 `next.wait` 也这样说明，客户端不必反复查看。
4. **处理答复**：对有答复的条款，按答复改写并写明依据的卡片，或说明不需要改，或追问（`follows` 指向原卡片）。答复不一致由产品负责人取舍。条款依赖平台已确认、但条文没有写进去的口径时，也可以按平台裁定改写，依据写裁定原文；只在没有待处理的答复时可用，同样在冻结前重新审查。改写按 [`clause-rewrite`](../.agents/skills/clause-rewrite/SKILL.md) 做；改写和改写后的审查记录都由 agent 逐条读原文、答复或裁定后亲手写出，不用脚本批量生成、套用、分发或沿用；脚本只做格式校验、提交、导入导出这类流程，不参与语义。
5. **出新修订**：改写后的条款在冻结前就重新审查（只审原文改过的），已答清的不再问，没人答的卡片进入新问卷。冻结后上一修订的问卷关闭、答复保留。
6. **收敛**：每条都已审查、没有未决问题时，这一修订会在同一次确认里标为「已澄清」（不能从已答数量推断），所以先逐条配好解读（查什么、何时通过、何时不通过、何时转人工），保留原文的引号用语和数字，原文仍是唯一判定依据。

**一次确认**（#351）：Claude 把到下一个只有客户才能推进的点（等答复）之前、不需要人的步骤都准备好，再经 MCP 提议一次；平台负责人在规则页的面板里按步骤勾选后确认。
- 步骤按依赖排列：冻结修订 → 发卡（会发给客户，默认不勾）或已澄清 → 发布解读。内部步骤默认勾选；取消上游会同时取消下游。
- 勾选的步骤经 `POST /rulebooks/<客户>/plan` 在一个事务里全部生效或都不生效。没勾的步骤连同已准备的内容，作为下一次计划退回给 Claude，可附原因。
- 一轮没有发现：一次确认完成（修订 0、已澄清、解读）。一轮问答：两次（修订 0 加发卡；修订 1、已澄清、解读）。复审又发现问题时，第二次变为「修订 1 加新卡片」，进入下一轮。
- 单步接口（修订、已澄清、解读、发卡）保留给线下与网页直接使用。
7. **检查程序与澄清并行**：检查程序不等条款冻结，有了条款写法就可以写；客户和平台的反馈，很多来自对真实检查结果的观察，等澄清完再写会晚一轮暴露问题。
   - **对着哪一版写**：检查程序目录叶子的 `rules.json` 逐条写明它实现的条款标识和条款原文（`id`、`rule_to_check`），可以是已冻结的修订，也可以是还没冻结、准备进下一修订的写法。规则页按「条款标识＋原文摘要」与已安装叶子比对，显示每个修订「检查程序 N / M」和每条「有检查程序／暂未检查」（`product.checker_wordings`）；写法改了，摘要对不上，这条回到暂未检查，要对着新写法重写。不另建对齐台账。
   - **在哪里跑**：对着未冻结或未澄清写法的检查程序是候选，放在 `assets/<客户>/rulebook/<版本>/candidates/<客户目录>/<叶子>/`，不在已安装目录里，不会写入 Suite，不进入客户的审核受理，也不扣点、不出报告。用 `uv run --no-sync python -m corpus_contracts.candidate_run <候选目录> --part <样本零件目录>`（或 `--file`、`--reference` 指定文件）按产品路径跑真实文件、看逐条结论；它只替换同名的已安装叶子，结果只显示，不记验证。
   - **观察到的问题回到澄清循环**：某类真实文件按现有写法判不出来，或结论和预期相反，属于写法的问题，按条款检查做成发现进入下一轮问卷，或按平台裁定改写；程序没读到、读错，在检查程序里修，不改条款，也不问客户。
   - **人工真值跟着写法走**：真值绑定判定时的修订和条款；意思没变可以沿用，意思变了原件可以复用，但要对着新写法重新判定，不改写旧真值。
   - **不做**：不为了程序好写而改条款；不用程序的结果替客户回答问题；对着未冻结写法验证通过的程序不能直接用来切换。
8. **切换审核**：把审核改用新修订是单独的发布决定，由产品负责人确认，同时满足：
   1. 修订已标记「已澄清」；
   2. 每条条款要么有对着这一修订写法验证过的检查程序（已对齐），要么明确登记为「未登记检查程序，暂未检查」，在审核结果里显示「规则已更新，暂未检查」，不算通过也不算出错；
   3. 有对着这一修订建立的代表性样本和预期结果，按官方流程验证、发布 Suite；旧修订的回归通过不等于新修订验收；
   4. 切换前核实官方默认、各企业绑定的版本、未检查项在客户那里怎么显示、受影响的在途任务；运行库或执行器变了，先停掉旧版本受理并处理完已受理的任务，或让它们仍走原来的执行环境。

   切换要改目录叶子的 `rules.json`、编译预置规则并按官方流程验证发布，代价高，离线进行。

**用户看到什么**：规则页按客户列出修订（「v1.0 修订 1」），标出已澄清、每条相对上一修订的改动与依据（可跳到对应卡片）、解读和待确认问题。

**现在实现的不足**（做相关工作前先看）
- 已澄清的修订不会自动流向审核：审核规则的权威仍是目录叶子的 `rules.json`，修订在数据库里且按企业保存；没有把修订导出成目录叶子的工具，切换全靠线下手工。
- 修订按企业保存：同一客户的规则在 A 企业澄清过，B 企业看不到；随产品发布的规则库在每个企业各复制一份。
- 解读只显示在规则页：检查程序和深度审核还不读它；检查程序版本变化不会让解读重新打开。
- 「有检查程序」只表示已安装叶子实现了这段写法，不等于已验证：验证仍按官方流程。候选运行目前只接 UAES 样本批次的产品路径。
- 澄清任务里已审过的条款只有写法变了才能重新审查，观察到检查结果后发现的问题还不能作为新发现补交。
- 受委托审查方的权限只在本地测试验证过；线上目前审查方就是平台负责人本人。
- 澄清没有网页入口，进度只能经 MCP 查看；测试用的修订和问卷没有删除入口，只能用数据库管理身份手工清理。

UAES 规则库的目录、标识和当前状态见 [assets/uaes/AGENTS.md](../assets/uaes/AGENTS.md)。
