# 迁移与退出

目标是尽快把已有 PPAP 能力收敛进本仓并让客户使用，而不是重新证明旧资产是否可用。

## 默认资产权限

`ppap-agent` GitHub 组织中的代码、配置、文档、测试、样本和我们可访问的远程环境，默认都是本项目授权资产，除非之后明确排除某项。

因此迁移时：
- 不等待额外“许可证明”再开始使用组织内资产；
- 不因为业务样本、客户环境或旧仓标签默认把资产判为不可用；
- Secret 和业务对象权限仍按真实安全边界处理。

## 迁移原则

- 优先复用已经工作的能力，而不是为了架构纯净重写。
- 来源仓只作为一次性迁移来源；有长期价值的代码、tests、fixture、oracle、配置和 helper 迁入本仓。
- 一个内聚模块整体迁入更快、更少上下文时，可以整体迁入；KISS 不要求把迁移人为切成最小碎片。
- 迁入后本仓成为唯一当前 authority，持续删除跨仓 import、checkout、旧 HTTP wrapper 和无消费者代码。
- 旧实现输出不是天然 oracle；已有人工 expected 继续独立。
- 新旧 ID 映射保持来源系统、租户和对象类型，避免错误合并。
- 切换期间只保留必要的单一写入 authority，尽量缩短双系统共存时间。

## ppap-agent

`ppap-agent` 是明确 sunset 目标。#3 迁测试资产，#6 可以按最快交付方式迁现成检查能力。完成后开发、CI、测试、构建、部署和 runtime 都不再依赖旧仓。

## 其它旧路径

组织内其它 PPAP 资产同样可以直接用于迁移。只有确认存在其它真实消费者的共享系统才保留兼容；不要因为“可能有人用”无限期维持双系统。

涉及真实外部写入时保留必要回切和 readback；纯内部代码/测试迁移不需要为“完整证据”增加额外流程。
