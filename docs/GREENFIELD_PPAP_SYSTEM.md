# 从零设计 PPAP：量产批准的证据工作台

状态：已授权推进的产品与交互原型设计；生产实现与真实批准制度尚未验收。本文从用户任务推导产品，不以旧页面、流程或后端架构为约束。旧系统能力仅用于检查遗漏；生产系统现有合同仍见 [Northstar](NORTHSTAR.md)。日期：2026-10-13。

## 1. 要解决的问题

PPAP 的工作对象不是一摞文件，而是一个可审查的问题：**针对某客户、供应商、零件版本、生产地点和工艺，现有证据是否足以支持量产批准决定？** 行业 PPAP 的目标涉及在实际生产条件下持续满足设计与规范要求；文件只是这种能力的证明材料，不能代替真实生产事实。[AIAG PPAP](https://www.aiag.org/training-and-resources/manuals/details/PPAP-4)

系统应缩短“首次提交 → 找到差异 → 补充或改正 → 人工决定”的完整周期，而不是只缩短一次模型调用。其核心承诺是：每项要求都有清楚的适用范围、证据、结论边界和下一步；任何人都能重建某次决定依据了哪些版本。

**不作出的承诺**：仅凭文件自动证明产线真实能力；任意格式和任意规则都能自动审核；AI 自动作出正式批准；把未读取、未覆盖或证据不足转成通过。

## 2. 用户与工作边界

首版只有**内部审核团队**一种系统用户。供应商通过系统外渠道发送资料与说明，不登录产品。审核员上传初次资料和后续补件，核对归属、确认要求、复核发现、记录对外沟通及收到的答复，最后由组织有权人员形成决定。同一用户可以完成整条原型旅程；岗位责任不强制变成角色切换或交接页面。

**文件上传是唯一文件输入入口**。初次来件与后续补件均先上传，再核对。审核员可以先暂存一包陌生资料，不必先知道零件号或建完事项；系统建议分类与归属，人确认后才将资料用于检查。没有新文件的澄清或异议可以直接登记说明，不要求伪造附件。

进入产品需有组织身份，账号可访问的事项范围仍须明确。身份与权限的失败需要可理解的恢复路径；不在原型阶段扩建通用组织管理平台。允许读取与允许作正式决定是不同授权，原型用固定模拟身份演示。

## 3. 产品的中心对象

| 对象 | 含义与关键约束 |
| --- | --- |
| **批准事项** | 客户、供应商、零件号、图纸/产品版本、生产地点、工艺、提交目的组成的持续工作对象；可经历多次提交和决定。 |
| **要求合同** | 本事项适用的通用、客户特殊及项目要求的版本化快照，含来源、适用条件、冲突和获准例外；不能靠模型猜测冲突优先级。客户要求确实存在差异。[IATF 客户特殊要求目录](https://www.iatfglobaloversight.org/oem-requirements/customer-specific-requirements/) |
| **主张** | 可被审查的具体问题，例如“过程流程图与控制计划的工序一致”。一项主张可依赖多个资料、生产记录或人工确认。 |
| **证据版本** | 一次提交的不可变原件及身份、来源、时间、哈希和授权范围。解析数据、OCR 与模型提取是派生物，不冒充原件。 |
| **审核轮次** | 固定要求合同、证据版本、审核方案和执行版本的一次评价；技术重试不是新轮次。 |
| **检查发现** | 对一项主张的机器判断、覆盖范围、原件定位、推理边界和待办动作。 |
| **澄清/改正事项** | 发给明确责任人的问题，说明缺什么、矛盾在哪里、需要何种答复或新版本。 |
| **人工复核与批准记录** | 人的复核和正式批准独立于机器判断保存，明确操作者、时间、范围、条件与依据。 |
| **模板方案** | 经验证的读取、关联和检查方法，附客户/供应商、结构、规则版本等适用条件；失配即停止复用。 |

这里的“主张—证据”关系是领域模型，不要求先建设通用知识图谱产品。首先实现审核所需的少量明确关系。

## 4. 完整工作流程

这是一条**审核员接收资料、明确依据、系统辅助调查、审核员核实并决定**的闭环。用户每天进入时需要找到下一项工作；第一次收到陌生资料时需要立即上传。两个入口都落在同一个持续事项中，不需要重新建立文件或要求。

| 阶段与负责人 | 用户任务及当前优先动作 | 完成条件；不能偷换的失败状态 |
| --- | --- | --- |
| 1. 打开与继续；审核员 | 首次进入说明产品用途并登录；有会话时进入工作台。工作台列出待核对来件、待复核问题、待补件和待决定事项；能上传新资料或继续上次位置。 | 空工作台有直接上传入口；过期会话恢复后回到原事项；无权访问说明原因与可返回位置，不丢弃未提交输入。 |
| 2. 上传资料；审核员 | 将系统外收到的 Excel、Word、PDF 上传；已有事项可直接添加来件，也可先上传再确定归属。 | 每份文件显示接收结果；失败只重试对应文件。重复件需核对，陌生格式不能假装读取成功。暂存不等于纳入审核。 |
| 3. 上传后核对；审核员 | 核对客户、供应商、零件、修订、地点及文件类型；将这次来件关联到已有事项或新事项，指定待审资料与仅供参考的资料。 | 未确认建议与人工确认分开。错版本、缺页、不可读和资料缺失分别可见。缺口可以保留；事项归属不明的文件先暂存，不混入已确认事项。 |
| 4. 确认审核依据；审核员 | 查看建议适用的要求及来源，上传新要求或复用已有版本，核对解析出的条款、适用范围和冲突；明确本次要检查什么。 | 每项要求可回到来源，客户差异不靠名称猜测；冲突不得自动选优先级。未确认要求可以保存，但不能据此宣称全部要求已检查。 |
| 5. 开始检查；审核员 | 同处核对纳入的原件、要求版本、已知缺口、检查覆盖范围及预计用量，启动检查。 | 形成固定依据，重复点击只产生一次受理；结果未知先查询。资料缺口不必阻断其他已确定要求的检查，但未覆盖项必须保留。 |
| 6. 调查与检查；系统 | 显示“识别资料 → 建立关联 → 检查要求 → 核验证据”的可理解进度；只在需要人提供事实时提出澄清。 | 每条适用要求有覆盖状态和可定位证据；未覆盖、无法判断、执行失败分别保留。超时或工具故障结束为显式失败/待处理，不是假完成。迟到结果不能覆盖新提交。 |
| 7. 逐项复核；审核员 | 按下一步动作看差异、证据不足、资料问题及未覆盖项；从结论直达原件。可核对机器意见，也可依据原件独立完成某条要求的人工审核。 | 独立人工判断记录文件版本、原件位置、摘录及理由，确认后才计为已核对；修改依据须重新确认。机器原结论不被改写。文件描述一致不能证明真实工艺已执行。 |
| 8. 联系供应商与登记回件；审核员 | 将核实后的问题整理成清单，复制或下载，经系统外渠道联系供应商。新附件先上传、再核对版本及问题关联，然后记录供应商原话和修改原因；说明或异议可单独登记。 | 生成清单不等于已发送；登记沟通不声称系统送达。允许部分答复，未答复项继续保留。新文件不覆盖旧版本，也不自动关闭问题。 |
| 9. 差异复审；审核员/系统 | 看哪些事实、要求和结论受到影响；针对新依据重查，再记录是否解决及理由。 | 复用旧结论须确认要求、文件和关联前提未变；不能只按文件名判断。新回件、重查完成、问题关闭分别展示。 |
| 10. 形成决定；有权审核员 | 核对批准范围、依据版本及剩余问题；条件满足时可批准，不满足时保留待处理或明确不批准。 | 批准要求全部必需要求有当前有效依据，并经人工确认满足。机器未知、未覆盖或失败保持原状；独立人工审核可另行建立依据，不能只点确认就绕过缺口。人工仍无法判断时不能批准。附条件批准需要另行确认组织政策。 |
| 11. 交付结果；审核员 | 查看本次决定与复核报告，生成固定版本的报告及资料包；按需要交付下载件或飞书报告。 | 报告注明范围、依据、机器结果和人工判断；生成不等于送达。生成失败可恢复，结果未知先查状态。后续复核不静默改写已经交付的版本。 |
| 12. 再次回来与处理变化；审核员 | 从工作台继续未完成事项，查阅已交付结果；收到图纸、工艺、地点或要求变化后，先上传再核对，查看影响。 | 保留原决定及其依据，当前事项显示待评估范围。变更不自动撤销或继承旧批准；需要新依据的判断重新进入检查与复核。 |

### 4.1 贯穿旅程的状态与权责

**批准事项**是长期容器，可有多次来件、检查和决定。对用户呈现当前下一步：`待核对`、`待确认要求`、`检查中`、`待复核`、`待补件`、`待决定`、`已决定`、`变更待评估`。这些是工作摘要，不替代每条问题的事实。一个事项可以同时有待复核与待补件项，工作台不能用一个状态隐藏另一项工作。

**身份与权限**按组织和事项限定。系统只产出机器发现；内部审核员确认要求、复核并在获准范围内记录决定。供应商是资料与陈述来源，不是系统操作者。权限失效后保留工作上下文，但不能用旧页面执行已无权进行的动作。

**版本与并发**按提交切开：草稿可修改；正式提交不可变。文件重传产生新证据版本；规则修订产生新要求版本；人工更正文件身份/关联也使依赖它的结论失效。技术重试沿用审核轮次，真正变更输入才创建新提交和轮次。旧 Worker 可以完成旧轮次的历史记录，但不能成为当前结论或新决定的依据。

**失败与恢复**必须指向可做的动作：不可读→登记清晰件或核对原文；身份不明→暂存并确认；缺证据→补件；内容冲突→人工复核；检查失败→恢复受影响检查或转人工；受理/报告结果未知→读取状态。供应商陈述、系统建议和已核实事实分别保存。关闭网页后可回到同一工作；刷新恢复不重新受理检查。

**结束与纠正**是显式分支：未采用的暂存资料可移出；已用于检查的原件与决定保留历史。若业务项目取消，可记录关闭原因；关闭不等于批准。决定有误时追加纠正或取代记录，不静默编辑旧决定。对外已交付的结果需要另行说明变更；首版不声称自动通知收件人。

### 4.2 代表性闭环

审核员收到“支架 P-204”的资料包，先上传，再核对“修订 B / 苏州”及客户要求。系统发现第 17 道工序的跨文件矛盾、扫描工序号无法判断、尺寸报告 A 未覆盖 B。审核员核对证据，下载问题清单并在系统外联系供应商。后来只收到清晰扫描件：登记回件后先重查可读性，另两项仍未解决。再次收到修正控制计划、对应 B 的尺寸报告及随件说明后，核对新版本与问题关联，检查一致性及尺寸结果，再逐项复核。

成功分支提供完整模拟依据：工序一致性要求得到当前两份原件支持；模糊工序号可定位核实；尺寸要求的实测值及范围均符合已确认要求。若要求实际生产记录，还须有对应记录，不能用两份文件相同代替。全部必需要求复核完成后，模拟授权审核员作出批准并生成报告。此结论只对声明的模拟要求范围成立，不表示已证明所有行业 PPAP 要素。随后图纸变为 C，工作台出现变更待评估，B 的批准报告仍可查阅。

## 5. 审核与 Agent 的分工

未知资料的审核采用一个有界调查循环：

```text
读取要求与资料 → 提出适用性/布局/关联假设 → 调用工具检查
        ↑                                      ↓
   修正或询问人 ← 寻找反例并核验证据 ← 形成暂定结论
```

- 强模型负责理解新模板、解释新规则、选择工具、发现矛盾、修正计划和提出澄清问题；不是最终事实来源。
- 确定性工具负责数值与公差、日期、集合、表格连接、版本比较和已知 checker。一个固定 checker 只有在文件结构和条款语义都满足其前提时才能调用；名称相似不是前提证明。
- 每项主张单独记录 **通过、不符合、无法判断、不适用、未覆盖、执行失败** 及原因。资料缺失只有在适用规则明确将其定义为不符合时才判不符合；解析失败不是业务不符合。
- Agent 在提交前检查：条款是否遗漏、引用是否真实可定位、跨文件关联是否成立、结论是否超出证据。允许有限补查和修正；预算耗尽或验证失败时如实结束，不伪装完成。
- 经人确认且通过反例测试的读取/审核方案可以复用。复用须检查内容和结构、要求版本、供应商/客户范围及方案版本；失败则回到探索。人一次纠错先成为回归样例，不立即变为全局规则。

自主性应投入在**调查和补查**，不投入在伪造确定性或绕过正式批准。模型生成的摘要、建议和置信度永远与原始证据分层显示。

## 6. 界面：熟悉的业务语言，新的工作方式

全局导航采用“工作台、事项、要求”，账号菜单承载身份、用量和退出。工作台回答现在做什么；事项承载持续工作和历史；要求提供可复用的审核依据。已完成决定属于事项历史，不另造一套记录。传统制造企业熟悉的审核单、资料版本、检查要求、异常和处理意见继续保留。

一个事项页面只有三种主要工作模式，而不是把后端的每个状态做成一个页面：

- **资料与依据**：当前原件、待审/参考用途、事项范围、要求来源和已知缺口。上传后的核对在这里完成，补件沿用相同操作语言。
- **检查与复核**：进度、覆盖情况与待处理问题；选择一项时并排或切换展示要求、机器判断、人工判断和原件定位。补正清单及供应商答复靠近问题；长正文与执行细节按需展开。
- **决定与交付**：当前依据、未解决条件、批准范围与决定人，随后生成报告。历史版本在同一事项可查，进入历史时明确显示所看的版本。

手机适合确认、澄清和处理单项异常；复杂跨文件比对优先使用宽屏。两端共享同一业务状态，不把桌面表格机械缩到手机，也不另造一套事实系统。默认不出现聊天框；只有确实需要人回答时，系统以具体、可回答的问题发问。

这里把“Steve Jobs 式体验”落实为**从用户要完成的决定倒推、敢于删掉无关步骤、细节一致且结果可信**，不是模仿某一代 Apple 的外观。与此相符的可检查准则是：

1. **一眼知道下一步**：审核员进入事项时，首屏回答“现在能否决定、是什么阻碍、接下来做什么”。主动作只对应当前最高价值任务；其他动作可见但退居次要。不要用一排同权重按钮或“AI 正在思考”代替业务进度。
2. **复杂性留在系统里，不丢给用户**：自动关联、定位和差异摘要先展示可验证结果；长规则、模型轨迹及文件技术细节按需展开。简洁不是删掉审计证据，关键原文始终可达。这与 Apple 对[简洁、层级和清楚反馈](https://developer.apple.com/design/human-interface-guidelines/design-principles)的公开原则一致。
3. **用熟悉概念完成认知升级**：保留“批准事项、提交、审核要求、差异、补件、批准范围”等制造业词汇；让“证据链、覆盖范围、版本影响”在操作中逐步可见，不强迫用户先学习 Agent 术语。
4. **每次操作有诚实回音和可恢复路径**：上传后逐文件反馈；正式提交前显示冻结清单；受理或报告交付结果未知时显示“待确认”，不显示成功；处理失败给出可执行动作。系统外联系只记录沟通事实，不声称系统已送达。高风险决定明确确认，草稿与误操作可恢复。反馈强度随风险变化，符合 Apple 的[反馈建议](https://developer.apple.com/design/human-interface-guidelines/feedback)。
5. **用任务完成检验设计**：上线前由开发团队走查完整故事，上线后再请真实审核员观察。检查能否找对原件、区分不符合与无法判断、恢复未完成工作，以及是否误以为 AI 已批准。内部走查不冒充用户验证。若失败，先重做信息结构和状态语义。

**入口组织**：首次使用有直接上传入口及可选的演示事项；返回工作台优先展示可继续工作。上传可从工作台或事项发起，已有事项预填归属但仍在上传后核对。**移动端**可以完成同一任务，跨文件比对改为保持条款上下文的切换阅读，不能删掉关键原件和判断依据。桌面用并列原件、平板用按需展开的上下文、手机用单项焦点；三者共享业务事实。

**原型说明**集中在预览台或首次入口：“交互原型，使用模拟数据”。固定演示包可生成限定范围的模拟检查结果；自己上传的资料可接收、阅读并逐条人工核对，不套用固定机器结论。人工判断与决定同样属于原型记录，不是正式批准。具体失败与缺口在对应操作处反馈，不将模拟声明重复写成每个区域的注释。

**工程准则**采用 [UI Engineer](https://github.com/ronhuafeng/skills-release/blob/main/agents/ui-engineer.md) 中适用的任务链检查：意图 → 控件 → 状态变化 → 反馈 → 恢复。新视觉参考先经 Stitch 建立，再用本项目 React、TypeScript、shadcn 原语及统一 token 实现。生成稿可以改变布局，但不得自行决定业务政策、编造批准事实或增加用户角色。桌面、平板和手机用同一套组件语言；模拟状态支持返回、刷新与继续工作。

## 7. 原型需要表达的数据与行为

前端就绪前不接后端，也不预先选择服务划分、数据库或队列。界面只依赖可说明用户行为的数据关系：事项包含多次来件及要求版本；检查引用明确依据；发现关联原件位置；人工复核、供应商陈述、补正请求、决定和交付记录相互关联。

同一事项应通过一个共享的模拟状态在各工作区连续传递。视图切换不复制业务记录；切换场景是显式的预览操作，不在正常工作中重置状态。浏览器本地保存用于模拟离开后继续；提供清除演示数据入口。演示附件与任意本地选择文件须区分，刷新后若真实文件字节不在本地，显示需重新选择文件，不声称已上传。

模拟动作包括上传完成/失败、核对归属、确认要求、开始检查、检查结局、保存复核、登记沟通、登记回件、重查、形成决定、生成报告及恢复未知结果。每个动作必须改变对应记录并让下游读取；按钮变色或切换静态页面不算实现。新的原件或要求不会修改历史结果，旧检查迟到时只归入旧依据。

## 8. 不变量与验收

系统必须始终保持：事项权限隔离；历史输入版本不可变；机器判断与人工决定分离；未知/空覆盖不能通过；外部失败不伪装成功；正式批准有明确的主体和范围；所有重要结论可定位原始依据。

原型阶段用标明来源的模拟资料与确定的期望结果走查；真实解析准确率在后端接入后另行验收。交互至少覆盖：

1. 相同零件的多个版本、重复件和错误关联；
2. 无边框/合并单元格 Excel、扫描 PDF 与无法读取文件的局部失败；
3. 客户条款名称不同于 checker 名称、客户要求冲突及不适用情况；
4. 流程图、控制计划、FMEA、尺寸报告之间的跨文件矛盾；
5. 修改一个关键值或规则后，相关结论改变，未受影响的结论保持；
6. 长任务、预算耗尽、工具失败和重试后，没有缺项或虚假通过；
7. 外部补件、内部复核及正式决定都能追溯到当时版本；
8. 首次进入、空工作台、登录失效、刷新恢复、返回列表后继续原事项；
9. 全部必需要求满足后批准、交付报告、再次打开历史决定，随后收到新修订进入影响评估；
10. 只收到部分补件、只收到说明、供应商有异议，未解决事项仍保持可见；
11. 规则来源不明或要求冲突时能保存准备工作，但不能伪装已确认依据；
12. 上传、检查、保存或报告结果未知时，先核对状态再继续，不能重复创建同一业务效果。

核心指标是**错误通过率、证据定位正确率、未覆盖项暴露率、首次提交可接受率、补件轮数、从首次提交到可作决定的时间**。模型 token、调用速度和表面“自动化率”只是成本与运行指标，不能替代质量指标。

## 9. 设计依赖、能力承接与边界

先确定完整旅程和关键状态，再按任务依赖形成 Stitch 参考并实现：统一入口与继续工作 → 上传后核对和要求确认 → 检查与证据复核 → 补正与差异复审 → 决定与交付 → 后续变更。每轮可以复用已认可的第一性原理设计，但新增或实质改造的工作区仍须先有 Stitch 参考。未形成参考时继续完善交互合同，不跳过设计直接写页面。

### 9.1 旧能力只用于查漏

“用新方式承接”保留用户可完成的任务，不承诺保留旧路由或按钮位置。下列能力按默认保留处理；标为建议的取舍未获确认前不能作为删除依据。

| 既有能力 | 处置 | 新产品承载及可操作检查 |
| --- | --- | --- |
| 登录、会话恢复、退出、访问拒绝 | 保留 | 统一入口与账号；恢复后返回原事项，不重复检查。 |
| 上传、识别元数据、文件移除、待审/参考用途 | 用新方式承接 | 先上传再核对；建议可纠正；参考资料不被声称完整审核；历史采用的原件仍可查。 |
| 保存与继续草稿 | 用新方式承接 | 工作台的未完成准备工作；离开、刷新、再次进入均保留已保存部分。 |
| 客户规则上传、解析核对、编辑保存 | 用新方式承接 | 要求库与事项依据确认；原文和提取条款关联，解析失败不产生假规则。 |
| 规则客户/文件适用范围、新旧版本 | 用新方式承接 | 显示适用理由和冲突，当前审核引用确认版本，新版本不改历史。 |
| Standard 与 Deep 的审核能力 | 保留能力，重新设计入口 | 先说明覆盖范围与限制；检查方式可在开始前选择。保留已有适配检查和完整要求调查两种承诺，不把未支持条款当通过。原型不确定生产默认模型或价格。 |
| 排队、进度、执行失败、重新读取状态 | 用新方式承接 | 事项中的检查进度；区分等待、局部失败、完成及未覆盖，离开后可回来。 |
| 审核历史搜索、筛选、继续复核 | 用新方式承接 | 工作台与事项列表；待复核和待补件可同时存在，能回到具体判断。 |
| 机器结果、覆盖情况、人工判断/理由/下一步 | 用新方式承接 | 检查与复核工作区；机器与人工分开，保存状态明确，可继续下一项。 |
| OnlyOffice/原件、文字摘录、工作表导航、来源定位与下载 | 保留用户任务 | 证据工作区支持完整原件和局部定位；预览失败仍能下载，摘录不冒充全部原件。具体预览技术待后端阶段决定。 |
| 修改后重审、历史依据固定 | 用新方式承接 | 来件与变更复审；显示改变了什么及哪些判断需重做。 |
| 报告、打包下载、飞书报告/授权/状态查询 | 保留 | 决定与交付；模拟下载件和飞书目标，生成、成功、失败、未知分别有交互。 |
| 飞书结果写回 | 保留至明确取舍 | 交付中的可选目标，不能将文件输入渠道等同于结果交付渠道。 |
| 用量、剩余额度、预计消耗、额度不足 | 保留 | 账号用量与开始检查前确认；同一技术恢复不显示第二笔受理消费。 |
| PWA 安装、有限离线查看 | 保留至明确取舍 | 账号入口与全局连接状态；离线不声称上传或检查已执行。原型先模拟这些状态。 |
| 飞书导入及其他文件输入渠道 | 已确认取消首版输入入口 | 首版全部文件通过上传获取；不影响飞书身份或结果交付。 |
| 供应商登录与系统内双角色交接 | 已确认不进入首版 | 审核员登记系统外陈述与回件；无需供应商账号。 |
| 旧版切换入口 | 建议在新系统完成替代后移出主导航，待确认 | 影响旧路径访问；原型不依赖该入口，生产切换另行决定。 |

附条件批准不是旧 Web 已有能力，也不是当前可批准成功路径的必要条件。当前原型先验证明确范围的批准与不批准；若需要附条件批准，先确认条件、期限和责任规则。账号层面的付费套餐、自助充值、通用审批流和组织树也不从旧用量页自动推导为本轮需求。

**不先做**通用 QMS、任意行业 Agent 平台、所有客户共用的巨大 checker、按客户训练独立模型，或用一张“综合置信度”掩盖不同类型的不确定性。这个系统的护城河应是可核实的质量判断闭环，而不是更大的模型对话窗口。

上线前尚需确认真实组织的批准权限、可信生产证据来源、模型成本和额度政策。它们不阻止使用明确标注的模拟事实检验完整交互；原型也不据此宣称自动 PPAP 批准。

## 10. 状态合同与形式验证边界

[要求级 TLA+ 模型](models/GreenfieldApproval.tla)来自较早的抽象设计，覆盖**一个事项、至多两次提交、至多两个要求/资料修订**的部分交错。下列结果是历史的有界检查记录，不是本轮新旅程或 React 原型的证明。模型中的客户/供应商动作尚未映射到当前单角色工作流，通知发送也不代表首版系统具备对外发送能力。登录、OCR 内容、规则语义、文件字节、完整工作台、报告交付和浏览器恢复不在该模型中。

| 检查义务 | 可发生的错误及规定行为 | 模型结果 |
| --- | --- | --- |
| 冻结输入不变 | 提交后篡改要求或文件版本；只能新增提交，不改旧快照。 | `FrozenInputsStable`；故障配置会抓到改写。 |
| 当前结果来自当前提交 | 提交 2 后提交 1 的 Worker 迟到；可存旧历史，不能覆盖当前结果。 | `CurrentResultFresh`；迟到提交故障给出反例。 |
| 空覆盖/未知不能通过 | Worker 输出“通过”但并未覆盖全部适用主张；不能据此直接批准。 | `NoEmptyPass`、`DecisionSound`；空覆盖和机器越权批准各有反例。 |
| 决定属于授权人和固定快照 | 此早期模型仅覆盖机器辅助路径：当前机器通过、覆盖完备、人工清除阻碍。独立人工审核见下述局部模型。 | `DecisionSound`；不是身份服务或真实证据正确性的证明。 |
| 未知送达不可盲重发 | 补正请求已到达但回执丢失；先对账，再确认或重试。 | `NoDuplicateDelivery`；盲重发故障给出反例。 |
| 待执行审核最终有可见结局 | 外部 Worker 可以不返回；本地截止动作将该轮结束为失败，不伪装成功。 | `AuditEventuallyStops`，依赖截止动作的弱公平性；不证明真实墙钟时长。 |

**检查范围**：正常配置无对称化、状态约束或抽样，穷举 13,540 个不同状态，最深 18 步；五个负向配置分别在预期不变量上失败。关闭死锁报告，因为开放工作流的完成/等待状态允许静止；审核进度另以时态性质检查。`MaxSub=2` 可表达“新提交与旧结果并发”，两个修订可表达变更前后；不能据此声称任意数量事项、并发操作者或无界历史均已证明。

**独立人工判断**：[局部模型](models/GreenfieldManualReview.tla)覆盖一条适用要求、两个文件版本及两个要求版本。机器保持未知或失败；人的判断、引用、理由及决定独立记录。正常配置穷举 226 个不同状态、1,430 个生成状态、深度 7；跳过依据要求的负向配置命中 `EvidenceRequired`（68 个不同状态、深度 4），沿用旧版本引用的负向配置命中 `EvidenceFreshAtDecision`（192 个不同状态、深度 6）。使用技能固定 TLC 1.8.0 预发行版（revision `0894c34`，Java 26.0.1），耗时分别为 520、486、491 ms。无约束、对称化、覆盖或采样；允许用户停止，关闭死锁报告，不声称最终一定批准。代码中的 `judgmentComplete` / `requirementSatisfied` 另经受控探针检查空引用、要求变更、文件变更和部分复核；一条上传后人工决定的浏览器路径已走通。此模型没有形式细化到 React，也不证明人工摘录真实、判断正确、多条要求相互独立或操作者确有批准权限。

**部分回件与重新复核**：[局部模型](models/GreenfieldSupplementReview.tla)覆盖两个独立请求、至多两批回件，区分上传草稿、核对、登记、人工判断、检查运行、结果待使用和批准。两项请求可表达部分回件，两次登记可表达旧判断遇到新依据；收到不等于满足，完成检查不等于新结果已经复核。应用结果时，改变的判断失效，未改变的判断保留。正常配置穷举 631 个不同状态、1,691 个生成状态、深度 14。四个故障配置分别命中预期：自动解决 `CurrentHumanJudgment`（15/20 个不同/生成状态、深度 4），沿用旧判断同一不变量（41/57、深度 5），忽略草稿 `NoDecisionWithDraft`（45/68、深度 5），跳过新结果 `NoDecisionWithPendingCheck`（95/142、深度 6）。最后一个反例为两项已判断 → 开始检查 → 新结果就绪但未使用 → 错误批准。

五份配置经技能固定 `tla-check` 重跑，均符合声明预期；TLC 1.8.0 预发行版（revision `0894c34`，Java 26.0.1），正向、自动解决、旧判断、草稿、新结果配置耗时分别 573、486、547、851、496 ms。无状态约束、对称化、语义覆盖或抽样；允许用户静止及终态，关闭死锁报告，不检查活性。结果属于有限范围的局部检查义务，不是 React 细化证明；省略具体条款语义、跨条款依赖、尝试代次隔离、原件真实性、存储事务、权限、不批准决定与外部发送，不证明任意批数。实现中的待处理结果由 `receiptReviewState`、`decisionContinuation` 与决定入口共同约束；浏览器受控探针检查返回待处理结果、批准阻断和不批准路径，报告包另作内容核对。这些证据不外推为真实审核准确性或后端正确性。

**补件后的轮次延续**：[局部模型](models/GreenfieldRoundContinuation.tla)覆盖两个轮次、每轮至多一次回件登记，以依据代次代表文件版本和说明。正常配置穷举 9 个不同状态、12 个生成状态、深度 6；错误沿用旧起点命中 `LatestRegisteredBase`（6/7 个不同/生成状态、深度 4），跳过未登记回件命中 `NoInheritedDraft`（5/7、深度 3），允许历史回件写入命中 `HistoricalInputFrozen`（8/13、深度 4）。使用同一技能固定 TLC 1.8.0 预发行版（revision `0894c34`，Java 26.0.1），四次耗时分别 487、620、493、494 ms。无状态约束、对称化、语义覆盖或抽样；允许静止，关闭死锁报告，不检查活性。实现对应 `decisionContinuation` 读取当前登记依据、`freshChange` 固定下一轮起点、`newChangeInput` 建立新版本，以及未登记草稿阻断和历史只读入口；另有两轮实际浏览器走查及函数探针。该模型没有形式细化到 React，不证明文件内容正确、浏览器多窗口原子性、授权或持久化事务。

**请求修订与晚到答复**：[局部模型](models/GreenfieldRequestHistory.tla)覆盖一条要求、一个原请求及其一次修订、一个独立追加请求，以及答复与撤销的交错。原问题不可改写；答复保持当时的请求身份；追加、修订或撤销不能代替已验证的满足判断。正常配置穷举 120 个不同状态、569 个生成状态、深度 9。三个故障配置分别命中 `ReplyKeepsTarget`（14/15 个不同/生成状态、深度 3）、`NoAdministrativePass`（5/5、深度 2）、`OriginalRequestUnchanged`（3/3、深度 2）。四份配置均经技能固定 TLC 1.8.0 预发行版（revision `0894c34`，Java 26.0.1）运行，耗时分别为 629、526、534、523 ms，无语法错误或诊断截断。无状态约束、对称化、语义覆盖或采样；允许静止，关闭死锁报告，不检查活性。实现对应 `saveRequest`、请求身份关联的答复及 `currentRequest` 的当前清单；浏览器另检查草稿恢复、旧答复不迁移和撤销不批准。该模型省略持久化、权限、跨窗口更新、外部发送、条款语义和无界历史，不是 React 实现的形式细化证明。

**尚未得到形式证明的边界**：真实身份提供者和事项授权、文件归属与证据坐标的真实性、规则冲突裁决、多条主张的依赖/增量失效、附条件批准的组织政策、外部通知的真实对账接口、数据库原子性和崩溃恢复。这些需要后续的细化模型、受控测试和真实工作流证据；不能因本模型通过就把实现标为“已验收”。本轮设计暂定**允许披露缺口后的正式提交**，但不允许无身份、无规则快照或无可追溯资料提交。首个客户试用须验证这一取舍是否符合其质量体系。
