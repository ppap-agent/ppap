# 从零设计 PPAP：量产批准的证据工作台

状态：产品与系统设计提案，尚未批准实施。本文不描述当前代码，也不以现有系统或迁移范围为设计约束。它不是当前 [Northstar](NORTHSTAR.md) 的替代文件。日期：2026-10-13。

## 1. 要解决的问题

PPAP 的工作对象不是一摞文件，而是一个可审查的问题：**针对某客户、供应商、零件版本、生产地点和工艺，现有证据是否足以支持量产批准决定？** 行业 PPAP 的目标涉及在实际生产条件下持续满足设计与规范要求；文件只是这种能力的证明材料，不能代替真实生产事实。[AIAG PPAP](https://www.aiag.org/training-and-resources/manuals/details/PPAP-4)

系统应缩短“首次提交 → 找到差异 → 补充或改正 → 人工决定”的完整周期，而不是只缩短一次模型调用。其核心承诺是：每项要求都有清楚的适用范围、证据、结论边界和下一步；任何人都能重建某次决定依据了哪些版本。

**不作出的承诺**：仅凭文件自动证明产线真实能力；任意格式和任意规则都能自动审核；AI 自动作出正式批准；把未读取、未覆盖或证据不足转成通过。

## 2. 用户与权限

- **客户质量工程师**定义或确认要求、审查例外、提出补件请求、记录复核意见。
- **供应商提交人**准备资料、运行提交前预检、回答澄清问题、上传改正版本。
- **质量负责人/授权批准人**依据明确的范围和版本作出批准、附条件批准或拒绝；AI 只能提供建议。
- **规则管理员**维护客户与项目的规则版本、适用条件和已确认的例外。供应商不能自行改变客户要求。

同一组织可以同时扮演上游客户和下游供应商，但权限以具体批准事项为边界。外部分享只开放被授权的事项、文件和问题，不开放整个租户资料库。

## 3. 产品的中心对象

| 对象 | 含义与关键约束 |
| --- | --- |
| **批准事项** | 客户、供应商、零件号、图纸/产品版本、生产地点、工艺、提交目的组成的持续工作对象；可经历多次提交和决定。 |
| **要求合同** | 本事项适用的通用、客户特殊及项目要求的版本化快照，含来源、适用条件、冲突和获准例外；不能靠模型猜测冲突优先级。客户要求确实存在差异。[IATF 客户特殊要求目录](https://www.iatfglobaloversight.org/oem-requirements/customer-specific-requirements/) |
| **主张** | 可被审查的具体问题，例如“过程流程图与控制计划的工序一致”。一项主张可依赖多个资料、生产记录或人工确认。 |
| **证据版本** | 一次提交的不可变原件及身份、来源、时间、哈希和授权范围。解析数据、OCR 与模型提取是派生物，不冒充原件。 |
| **审核轮次** | 固定要求合同、证据版本、审核方案和执行版本的一次评价；技术重试不是新轮次。 |
| **检查发现** | 对一项主张的机器判断、覆盖范围、原件定位、推理边界和待办动作。 |
| **澄清/改正事项** | 发给明确责任人的问题，说明缺什么、矛盾在哪里、需要何种答复或新版本。 |
| **人工复核与批准记录** | 人的复核和正式批准独立于机器判断保存，明确操作者、时间、范围、条件与依据。 |
| **模板方案** | 经验证的读取、关联和检查方法，附客户/供应商、结构、规则版本等适用条件；失配即停止复用。 |

这里的“主张—证据”关系是领域模型，不要求先建设通用知识图谱产品。首先实现审核所需的少量明确关系。

## 4. 完整工作流程

这是一条**客户定范围、供应商交证据、系统辅助调查、人作决定**的闭环，不是“上传文件 → AI 给总分”。登录只是进入事项的门；登录后按权限显示本人待办或受邀事项，而不是强迫所有角色先经过同一个文件上传首页。

| 阶段与负责人 | 用户任务及当前优先动作 | 完成条件；不能偷换的失败状态 |
| --- | --- | --- |
| 1. 进入与受邀；客户/供应商 | 通过组织身份进入，或接受指向**特定事项**的邀请；看见自己能处理的事项。客户可新建事项。 | 未受邀者不能看到事项或文件；邀请过期、账号不匹配须可恢复，不产生孤立的提交。具体 SSO 供应商待选。 |
| 2. 建单与定范围；客户 | 确认客户、供应商、零件及修订、地点/工艺、提交原因、适用要求和截止时间，再邀请提交人。 | 客户要求冲突、适用性不明时先由有权人裁定。没有确定的事项身份与规则范围，不得启动正式审核。可保存草稿。 |
| 3. 收件与归属；供应商 | 上传/导入资料；系统建议文件类型、修订、所对应的要求及跨文件关系；人能更正关联而不改动原件。 | 各文件分别标明可读、部分可读、不可读、身份不明、版本不符、重复或疑似冲突。局部失败不阻断其他文件；不能把 OCR 猜测当作原件事实。 |
| 4. 提交前预检；供应商 | 看“可提交什么、还缺什么、哪项需要确认”，补充资料或回答一个具体问题。 | 缺项和不确定性不自动变成业务不符合。允许带已披露缺口提交；但事项身份、适用要求快照、提交人及至少一份可追溯资料必须存在。预检不是正式审核结论。 |
| 5. 正式提交；供应商 | 确认本次提交清单和已披露缺口，执行“提交审核”。 | 原子地生成不可变提交号，冻结要求版本、原件版本、文件关联和提交人；异步任务绑定此提交号。重复点击只产生一个提交，失败后可安全重试或查询结果。 |
| 6. 调查与检查；系统 | 显示“识别资料 → 建立关联 → 检查要求 → 核验证据”的可理解进度；只在需要人提供事实时提出澄清。 | 每条适用要求有覆盖状态和可定位证据；未覆盖、无法判断、执行失败分别保留。超时或工具故障结束为显式失败/待处理，不是假完成。迟到结果不能覆盖新提交。 |
| 7. 例外复核；客户质量工程师 | 按下一步动作看已证实差异、证据不足、资料技术问题及未覆盖项；从结论直达两侧原件。 | 人可维持、推翻或暂缓机器意见，但要记录理由、身份与时间。机器原结论和证据版本不被改写；不能从错误的原件跳到“通过”。 |
| 8. 定向补正；客户 → 供应商 | 客户确认收件人、问题、原文位置、期望答复或新文件；供应商按问题逐项答复。 | 发送是单独的外部效果。发送结果未知时先对账，不盲目再发；请求仍可显示“待确认送达”。补交建立新证据版本，旧提交不变。 |
| 9. 差异复审；系统/客户 | 对新提交创建新轮次，仅重新评估受影响的主张；客户复核解决项及新问题。 | 复用旧结论须证明规则、文件及关联前提仍成立。关键内容变化后旧结论不得直接继承；审核完成不等于可批准。 |
| 10. 正式决定；授权批准人 | 核对批准范围、提交/规则版本、未解决例外和条件，签署批准、附条件批准或拒绝。 | 机器不能签署。无条件批准须所有必需主张有充分有效证据且无未处理阻碍；附条件批准须事先定义授权政策、明确条件/有效范围/到期或复核责任，不能用它掩盖未知和执行失败。决定永久指向当时快照。 |
| 11. 后续变更；客户/供应商 | 报告图纸、材料、工艺、地点、规则或关键生产事实变更；看受影响的既有批准依据及应补的证据。 | 系统标出“待影响评估”，保留历史批准原貌；不自动宣称旧批准仍适用或已撤销。新的正式决定要有新范围和新提交/审核依据。 |

### 4.1 贯穿旅程的状态与权责

**批准事项**是长期容器，可有多个提交、轮次和决定；它不是单个上传任务。对用户只呈现当前下一步：`准备资料`、`等待审核`、`客户复核`、`等待供应商答复`、`待授权决定`、`已决定`、`变更待评估`。这些是投影，不替代底层的提交、审核和通知状态。一个事项可以有多个并行问题；首页应显示责任人和阻碍，而不是凭单一状态隐藏它们。

**身份与权限**按事项限定：客户定义要求和发补正，供应商只管理其获准提交的资料，审核系统只产出机器发现，授权人签决定。一个人可以兼任多个角色，但每个动作仍检查当时对该事项的授权；邀请和登录不授予整个组织资料库的可见权。权限收回后，未完成操作不因旧页面仍打开而获得提交权。

**版本与并发**按提交切开：草稿可修改；正式提交不可变。文件重传产生新证据版本；规则修订产生新要求版本；人工更正文件身份/关联也使依赖它的结论失效。技术重试沿用审核轮次，真正变更输入才创建新提交和轮次。旧 Worker 可以完成旧轮次的历史记录，但不能成为当前结论或新决定的依据。

**失败与恢复**必须指向可做的动作：不可读→重传/给清晰件；身份或对应关系不明→请提交人确认；缺证据→补件；内容冲突→客户复核；模型/工具失败→重试或人工处理；通知结果未知→核对送达。不能把这六类都写成“审核失败”，也不能把处理完成写成“审核通过”。

**撤回与关闭**是显式分支：未提交草稿可放弃；已提交资料不得删除历史，只能由有权人记录“撤回”并停止其作为当前决定依据。客户可因项目取消而关闭事项，说明原因并保留历史。签署有误时应追加撤销/取代决定及其责任人，不静默编辑旧签署。关闭不等于批准，重新启动须明确新的范围和提交。通知已发出的撤回还须另行告知收件人；本轮形式模型未覆盖这些外部效果。

### 4.2 代表性闭环

客户建立“支架 P-204 / 修订 B / 苏州”的事项并邀请供应商。供应商交一份可读但有合并单元格的控制计划、一份扫描流程图和只对应修订 A 的尺寸报告。系统继续处理可读部分；流程图模糊工序号标为**无法判断**，旧尺寸报告标为**修订 B 未覆盖**。正式提交后，系统在可定位的第 17 道工序发现流程图“热处理”与控制计划“表面处理”不一致，标为**不符合**。客户确认原文并发三条不同的补正请求。供应商补交清晰扫描和修订 B 报告、修正控制计划；新轮次重查受影响要求。授权人确认所有必需主张的当前证据、例外和范围后作决定。随后图纸变为修订 C，系统提示评估影响，不能复用修订 B 的批准声明作为 C 的批准。

## 5. 审核与 Agent 的分工

未知资料的审核采用一个有界调查循环：

```text
读取要求与资料 → 提出适用性/布局/关联假设 → 调用工具检查
        ↑                                      ↓
   修正或询问人 ← 寻找反例并核验证据 ← 形成暂定结论
```

- 强模型负责理解新模板、解释新规则、选择工具、发现矛盾、修正计划和提出澄清问题；不是最终事实来源。
- 确定性工具负责数值与公差、日期、集合、表格连接、版本比较和已知 checker。一个固定 checker 只有在文件结构和条款语义都满足其前提时才能调用；名称相似不是前提证明。
- 每项主张单独记录 **通过、不符合、无法判断、不适用、未覆盖、执行失败** 及原因。资料缺失只有在适用规则明确将其定义为不符合时才判不符合；解析失败不是业务不符合。
- Agent 在提交前检查：条款是否遗漏、引用是否真实可定位、跨文件关联是否成立、结论是否超出证据。允许有限补查和修正；预算耗尽或验证失败时如实结束，不伪装完成。
- 经人确认且通过反例测试的读取/审核方案可以复用。复用须检查内容和结构、要求版本、供应商/客户范围及方案版本；失败则回到探索。人一次纠错先成为回归样例，不立即变为全局规则。

自主性应投入在**调查和补查**，不投入在伪造确定性或绕过正式批准。模型生成的摘要、建议和置信度永远与原始证据分层显示。

## 6. 界面：熟悉的业务语言，新的工作方式

主导航以“待处理事项、批准事项、要求、已完成决定”为主，不以模型、Agent 或文件格式为主。传统制造企业熟悉的审核单、资料版本、检查要求、异常和处理意见继续保留。

一个事项页面只有三种主要工作模式，而不是把后端的每个状态做成一个页面：

- **准备**：当前资料、要求范围、缺口和正式提交动作。
- **复核**：按下一步动作排列的异常；选择一项时并排或切换展示要求、机器判断和原件定位。长规则正文与执行轨迹按需展开。
- **决定**：已核实内容、仍有条件/例外、批准范围及签署者；每个决定可回到当时的证据版本。

手机适合确认、澄清和处理单项异常；复杂跨文件比对优先使用宽屏。两端共享同一业务状态，不把桌面表格机械缩到手机，也不另造一套事实系统。默认不出现聊天框；只有确实需要人回答时，系统以具体、可回答的问题发问。

这里把“Steve Jobs 式体验”落实为**从用户要完成的决定倒推、敢于删掉无关步骤、细节一致且结果可信**，不是模仿某一代 Apple 的外观。与此相符的可检查准则是：

1. **一眼知道下一步**：每个角色进入事项时，首屏回答“现在能否决定、是什么阻碍、轮到谁做什么”。主动作只对应当前最高价值任务；其他动作可见但退居次要。不要用一排同权重按钮或“AI 正在思考”代替业务进度。
2. **复杂性留在系统里，不丢给用户**：自动关联、定位和差异摘要先展示可验证结果；长规则、模型轨迹及文件技术细节按需展开。简洁不是删掉审计证据，关键原文始终可达。这与 Apple 对[简洁、层级和清楚反馈](https://developer.apple.com/design/human-interface-guidelines/design-principles)的公开原则一致。
3. **用熟悉概念完成认知升级**：保留“批准事项、提交、审核要求、差异、补件、批准范围”等制造业词汇；让“证据链、覆盖范围、版本影响”在操作中逐步可见，不强迫用户先学习 Agent 术语。
4. **每次操作有诚实回音和可恢复路径**：上传后逐文件反馈；正式提交前显示冻结清单；发送结果未知时显示“待确认”，不显示成功；处理失败给出责任人和可执行动作。高风险决定明确确认，草稿与误操作可恢复。反馈强度随风险变化，符合 Apple 的[反馈建议](https://developer.apple.com/design/human-interface-guidelines/feedback)。
5. **不以视觉漂亮代替可用性**：让真实客户质量工程师、供应商和批准人分别完成任务。测能否找对原件、能否区分不符合与无法判断、是否知道下一步及是否误以为 AI 已批准。若失败，先重做信息结构和状态语义，不先加提示段落或装饰。

**入口组织**：客户首次进入看到“待处理事项 / 新建批准事项”；受邀供应商直接落在对应事项的“准备资料”；批准人落在“待决定”。返回用户保留上次上下文，但不把已失效的权限或旧结论当作当前状态。**过程组织**：准备模式侧重文件清单、归属和缺口；复核模式侧重一项差异与可定位原件；决定模式侧重版本、范围、例外和签署。**移动端**仅承担单项确认/答复/签署前核对，不以小屏完成复杂并排原件比对。

## 7. 最小技术骨架

先用**模块化单体 + 异步审核 Worker**，而不是从第一天拆分大量微服务。事务数据库保存事项、权限、要求、版本、任务、发现、复核与决定；对象存储保存不可变原件和必要派生工件。审核轮次记录冻结输入和工具/模型版本，保证重放与审计。

模块边界是：身份授权、要求管理、资料接收与解析、审核编排、证据定位、人工协作、决定与报告。模型通过受限的工具接口读取本事项资料；上传文件、规则正文和模型输出不能提升权限。昂贵或长时间工作由 Worker 执行，续租、超时和晚到结果保护是正确性要求。

只为真实消费者缓存解析快照与模板方案。结构化抽取可加速审核，但必须能回到原件坐标；一旦原件、规则或方案语义变化，相关结果失效。通知和外部系统连接使用明确的事件/出站任务，不让外部失败制造虚假的批准状态。

## 8. 不变量与验收

系统必须始终保持：事项权限隔离；历史输入版本不可变；机器判断与人工决定分离；未知/空覆盖不能通过；外部失败不伪装成功；正式批准有明确的主体和范围；所有重要结论可定位原始依据。

首批验收用真实而不整齐的资料，不只用整洁模板。至少覆盖：

1. 相同零件的多个版本、重复件和错误关联；
2. 无边框/合并单元格 Excel、扫描 PDF 与无法读取文件的局部失败；
3. 客户条款名称不同于 checker 名称、客户要求冲突及不适用情况；
4. 流程图、控制计划、FMEA、尺寸报告之间的跨文件矛盾；
5. 修改一个关键值或规则后，相关结论改变，未受影响的结论保持；
6. 长任务、预算耗尽、工具失败和重试后，没有缺项或虚假通过；
7. 供应商补件、客户复核及正式决定都能追溯到当时版本。

核心指标是**错误通过率、证据定位正确率、未覆盖项暴露率、首次提交可接受率、补件轮数、从首次提交到可作决定的时间**。模型 token、调用速度和表面“自动化率”只是成本与运行指标，不能替代质量指标。

## 9. 建设顺序与边界

先证明一个客户与供应商之间的完整闭环：要求合同、资料预检、一轮真实审核、证据定位、异常复核、精确补件、版本差异复审和人工决定。然后扩展模板复用、复杂跨文件推理与更多格式。最后才考虑连接 MES/QMS/生产记录，使批准依据能随真实工艺变化持续更新。

**不先做**通用 QMS、任意行业 Agent 平台、所有客户共用的巨大 checker、按客户训练独立模型，或用一张“综合置信度”掩盖不同类型的不确定性。这个系统的护城河应是可核实的质量判断闭环，而不是更大的模型对话窗口。

尚需产品选择的关键问题：首个正式客户和零件类型、需要支持的批准/附条件批准权限制度、供应商是否直接进入同一产品、哪些实际生产记录可作为可信证据。没有这些选择，不应宣称“完整自动 PPAP 批准”已被定义。

## 10. 状态合同与形式验证边界

[要求级 TLA+ 模型](models/GreenfieldApproval.tla)检查**一个事项、至多两次提交、至多两个要求/资料修订**的关键交错。它不是当前代码的实现模型；[正常配置](models/GreenfieldApproval.cfg)和五个故障配置均由 `model-with-tla` 的固定工具链运行。业务动作被抽象为：客户确认/更改范围、供应商上传并提交、Worker 完成或超时、客户复核、授权人决定、补正通知发送/丢回执/对账。登录、OCR 内容、规则语义与文件字节不在模型中。

| 检查义务 | 可发生的错误及规定行为 | 模型结果 |
| --- | --- | --- |
| 冻结输入不变 | 提交后篡改要求或文件版本；只能新增提交，不改旧快照。 | `FrozenInputsStable`；故障配置会抓到改写。 |
| 当前结果来自当前提交 | 提交 2 后提交 1 的 Worker 迟到；可存旧历史，不能覆盖当前结果。 | `CurrentResultFresh`；迟到提交故障给出反例。 |
| 空覆盖/未知不能通过 | Worker 输出“通过”但并未覆盖全部适用主张；结果应降为无法判断，不得批准。 | `NoEmptyPass`、`DecisionSound`；空覆盖和机器越权批准各有反例。 |
| 决定属于授权人和固定快照 | 人工复核与机器结果分开；无条件批准要求当前通过、覆盖完备、人工清除阻碍。 | `DecisionSound`；不是身份服务或真实证据正确性的证明。 |
| 未知送达不可盲重发 | 补正请求已到达但回执丢失；先对账，再确认或重试。 | `NoDuplicateDelivery`；盲重发故障给出反例。 |
| 待执行审核最终有可见结局 | 外部 Worker 可以不返回；本地截止动作将该轮结束为失败，不伪装成功。 | `AuditEventuallyStops`，依赖截止动作的弱公平性；不证明真实墙钟时长。 |

**检查范围**：正常配置无对称化、状态约束或抽样，穷举 13,540 个不同状态，最深 18 步；五个负向配置分别在预期不变量上失败。关闭死锁报告，因为开放工作流的完成/等待状态允许静止；审核进度另以时态性质检查。`MaxSub=2` 可表达“新提交与旧结果并发”，两个修订可表达变更前后；不能据此声称任意数量事项、并发操作者或无界历史均已证明。

**尚未得到形式证明的边界**：真实身份提供者和事项授权、文件归属与证据坐标的真实性、规则冲突裁决、多条主张的依赖/增量失效、附条件批准的组织政策、外部通知的真实对账接口、数据库原子性和崩溃恢复。这些需要后续的细化模型、受控测试和真实工作流证据；不能因本模型通过就把实现标为“已验收”。本轮设计暂定**允许披露缺口后的正式提交**，但不允许无身份、无规则快照或无可追溯资料提交。首个客户试用须验证这一取舍是否符合其质量体系。
