# 真实 Deep 审核：实施范围与验收合同

本文件记录产品负责人已确认的本轮范围、实施顺序与验收要求。它不是完成报告，也不是第二套任务状态台账；开发进展仍由 owning Issue / PR 管理。

本轮目标：保留新版 PPAP 的产品模型和部署骨架，接入真实语义审核执行链，并补齐理解进度、结论、证据和下一步所必需的 UI。不重做通用 Agent 平台。

本文中的源码和运行观察来自实施前的只读调查。实现后必须重新验证，不能把本文、已关闭 Issue、提交说明或旧完成报告当作能力证明。创建本文件不代表启动开发、发布或验收已通过。

## 2. 设计原则与边界

1. 强模型负责未知模板和客户规则的理解、探索及修正；确定性工具负责可靠计算、比较和已知检查。
2. 共享工具、来源证据和产品合同，不把客户差异不断写入全局 checker 源码。
3. 统一基础能力不等于 Deep 和 Standard 执行同一算法。Deep 可调用 checker，但不能把固定检查集整体冒充客户规则审核。
4. 规则、资料、计划和检查结果必须可重新读取；模型对话上下文不是唯一事实来源。
5. 复用必须检查租户、版本、内容及适用范围。通过一次校验的计划不等于已经获得客户确认，更不等于适用于另一种模板。
6. 证据可定位、计数可重放和输出类型正确，是必要条件，不是业务结论正确的充分条件。
7. 保留现有任务和产品不变量；选择最短正确实现，不为预想需求建设通用框架。

相关约束继续由 [Northstar](NORTHSTAR.md)、[数据模型](DATA_MODEL.md)、[架构](ARCHITECTURE.md)、[安全边界](SECURITY.md) 和 [测试策略](TESTING.md) 拥有。本文定义本轮待实现的增量，不将其中描述的当前行为改写成“已经完成”。

## 3. 能力差异与证据

### 3.1 当前 Deep 的实际行为

当前链路是：Worker → Deep Controller → ProcessRuntime → `audit_spec()` → `run_round_from_bytes()` → 固定检查引擎。

调查中的真实控制计划轮次包含 11 条客户规则：2 条被映射，9 条标为不支持，最终保存 2 条 finding，任务标为成功。底层可能运行了更多内置检查，但产品层只投影已映射条目；不能把这个事实表述成“11 条全部经过语义审核”。

模型配置正确不会改变上述调用链。当前问题不是仅缺少一个模型名称或开关。

### 3.2 已存在，但不能直接当作“已验收”的旧能力

- `semantic_audit` 已实现规则计划编译、模型审核、结果校验和有界修正。其模型包含 PASS、NG、UNABLE、NA 及结构化引用。
- `grok-build` 集成已有读文件、目录检索、终端执行、写文件、修改文件、后台命令等待/取输出/终止等工具；不需要另造 Agent 循环。
- 旧运行器先让模型写完整结果工件，再返回小型完成凭据，随后重新读取并校验。存在结果文件不等于任务成功。
- 旧 PPAP 使用分阶段工作目录，禁用跨任务记忆、网页搜索和子代理。无需为了本轮开启它们。
- grok-build 源码有上下文压缩和溢出恢复；旧镜像固定的 CLI 版本与调查到的源码版本不同。当前部署组合能否完整工作仍需实测，不能仅凭模型接口 ping 或新版本源码证明。
- 旧可重放查询计划主要是简单谓词及量词，不是完整 SQL/ORM 审核语言。复杂关系和语义判断仍需模型、工具和人工预期验证。
- 旧运行记录出现过超时、人工续跑和有结果文件但非成功退出。因此旧代码是可复用实现，不是稳定时延或准确率保证。
- integration/4.0 的 [阶段进度](../../hax/repos/integration/4.0/ppap-web/src/shared/utils/auditTaskProgress.ts) 可作为交互参考；其模式传递、预览和结果表格不证明 Deep 算法完整。只借鉴必要语义，不迁入 Vue/Java 产品层。

## 4. 本轮必须实现的后端范围

### 4.1 一条真实端到端 Deep 链

1. 从现有 round/job 获取本轮文件版本、角色和规则版本，并验证授权与完整性。
2. 读取全部目标与参考文件及有效规则正文，生成或复用匹配版本的文档快照。
3. 为全部条款形成有来源、适用范围、判断条件及缺证据处理的计划。条款不因无对应 checker 而消失。
4. 通过 grok-build 调用文档、查询、计算、比较及适用的已有 checker 工具完成审核。
5. 校验目标/条款集合、来源、覆盖、计数、证据及结论；允许旧核心已有的有限修正，不用无限重试掩盖失败。
6. 只有正常结束且通过验证的结果才能提交到现有产品结果模型；错误或不完整工件不能被当成成功。

Deep 不受固定 checker 名称限制，也不静默退回 Standard。当前固定引擎或隔离 smoke guest 不能继续作为“真实 Deep 已完成”的依据。

### 4.2 沿用产品身份与任务模型

| 现有对象 | 承接方式 |
| --- | --- |
| 文件版本 | 保持 `file_version_id` 为产品身份；内容 hash 用于完整性与缓存。快照和引用必须回到该版本。 |
| 规则版本 | 使用本轮有效正文、稳定条款 ID、版本和原始来源。修订规则需有与修订内容一致的执行输入，不能伪造原件定位。 |
| round | 保留本轮目标/参考角色与规则匹配。技术恢复不产生新轮次；用户显式重审才创建新轮次。 |
| job/attempt | 继续使用现有队列、租约、attempt fencing。阶段、心跳、失败原因属于执行诊断，不另建任务系统。 |
| finding | 保留稳定目标/条款身份；扩展必要的结论原因、计数和类型化多来源引用。被审目标与引用参考文件必须分别表达。 |
| review | 人工判断独立保存；机器结果不改写人工复核，人工复核也不改写机器事实。 |
| object storage | 存放有消费者的快照、计划、执行结果与诊断工件，关联现有执行身份。不建立额外工件注册平台。 |

受理与入队的原子性、租户/对象授权、历史版本稳定、幂等重放和晚到结果保护均不能弱化。需要扩展字段时采用最小适配，不先重建领域模型或数据库。

### 4.3 结果语义与失败恢复

- 明确区分通过、不符合、无法判断、不适用和执行失败。可以在现有状态字段上添加结构化原因和覆盖信息，不预先要求重构全部枚举；API、页面与报告必须表达一致。
- PASS 必须具有完整的已声明检查范围和可验证证据；未知值、未知公式缓存、解析失败或未核实关系不能自动转成 PASS。
- “必需参考文件缺失”只有在规则明确要求该文件必须存在时才据此判 NG；关系不明或解析能力不足通常是无法判断，不能偷换成业务不合格。
- 任务结束不等于全部条款已得出业务判断。有效报告可以包含明确的 UNABLE/NA；缺项或验证不通过的报告不能伪装成有效的部分成功。
- 审核全过程续租和更新心跳；失去租约或终止后停止相关模型/工具工作，拒绝晚到提交。不得声称外部模型调用 exactly-once。
- 明确区分输入、解析、模型协议、预算、运行环境和输出校验失败。只有明确可安全恢复的情况可在预算内重试，禁止失败后无界付费重跑。

### 4.4 工具执行边界

现有 Deep sidecar 可接触应用配置和 Secret，不能把这些凭据直接继承给模型终端。产品负责人补充确认：能力完整性优先，本轮采用最小的容器级执行边界即可；强文件系统隔离、独立内核及完整出站网络策略不作为交付门槛。

- 可信 Controller 按本轮身份读取授权资料；只向模型工作进程交付本轮输入、工作目录及必要模型授权。使用低权身份和清空后的环境，避免继承 Controller 凭据。
- 不向模型工作进程提供数据库、S3、飞书管理凭据或主机控制 socket；Worker 不持有 Docker socket。
- 文件内容、客户规则和模型输出均不能提升工具、网络或挂载权限。
- 限制运行时间、回合、token、进程和输出大小；收尾时终止子进程并处理工作目录。
- 优先复用容器和 grok-build 已有机制，验证实际内核支持；不支持严格 profile 时必须显式选择容器级模式，不能静默关闭隔离或冒称 gVisor。其限制是共享容器内核、未保证严格文件系统和网络隔离；不为本轮另建通用沙箱平台。
- Deep 能力检查要覆盖真实执行器、模型协议和必要运行依赖；只配置 socket 或开关不是能力证明。Deep 不可用不能拖垮无关 Standard/Core 路径。

### 4.5 版本与缓存的最小范围

- 模型上下文窗口和自动压缩使用 grok-build 的模型默认配置，不另设压缩阈值、不强制触发压缩。PPAP 的单轮累计用量与时长预算不等同于模型上下文窗口；压缩后仍从原始工件核对规则与证据。
- 先复用相同来源与版本的快照、规则计划；复用时校验租户、规则有效正文、源内容和编译/引擎版本，必要时包含模型修订。
- 规则正文变化、文件关键内容变化或执行语义版本变化后，相关缓存必须失效或重新验证。
- 模板绑定含供应商具体行号、列名和文件关系时，不能直接升级成跨模板通用规则计划。
- 本轮不建立自动学习的模板库；也不把“自动验证通过”标为“用户已确认”。跨模板经验复用留到确有样例与确认机制后。
- 大文件和长规则必须有明确预算与超限行为，不能截掉后半部分却显示全部审核完成。首批长上下文样例若被现有入口长度限制阻断，应解决该样例所需的最小读取/分段能力，不顺带建设通用文档平台。

## 5. Standard 与 Deep 的关系

Standard 的承诺是执行已声明、已验证适用范围的内置检查集，不是理解任意客户条款。

- 保留当前已支持格式、检查能力及可见结果基线。
- 对已知内置规则使用明确身份、版本和经过确认的对应关系；显示标题不应决定是否可执行。
- 对没有确认对应关系的客户条款明确说明未覆盖；不能把其他内置检查结果冒充该条款的结论。
- 区分已确认对应、已确认有语义差异、尚未确认对应。标题不同、相似度不足或未匹配，均不能证明“不等价”；标题相同也不足以证明等价。确认对应需核对适用对象、量词、阈值、例外、缺失资料及未知值语义，并有正反例依据。
- 保留 Standard 既有语义，不新增通用等价判定器、模糊匹配或按序号强行绑定。无已确认对应的客户条款由用户选择 Deep 按有效正文执行；不能静默更改用户选择的模式。Deep 调用 checker 时也不能把局部检查通过当成整条客户规则通过。
- Deep 可按需调用字段完整性、频次完整性、数值比较及跨文件一致性 checker。只有工具前提和当前规则语义相容时才能使用其结果。
- 包含固定模板假设的 checker 不能被标成通用工具；无法满足假设时 Deep 应继续使用合适工具，或明确无法判断。
- 本轮不扩大 Standard 的规则语义承诺；名称门槛修复与 Deep 语义执行是两个不同问题。

## 6. 必要产品界面范围

### 6.1 进度与概览

- 显示真实阶段：读取资料、理解规则、执行检查、验证结果。只在后台确有数据时显示条款计数和进展，不使用假百分比。
- 用户可以离开后回到同一轮；显示阶段、心跳/耗时及可执行的恢复动作，不展示内部思维链或原始模型日志。
- 显示总条款、已判断、无法判断、不适用等覆盖信息；技术执行失败单独表达。不得只按已生成 finding 的数量暗示完整覆盖。
- 机器检查覆盖与人工复核进度分开计数，不把人工复核等同于问题解决或正式批准。

### 6.2 结果、证据和下一步

- 条款列表使用短标题、稳定编号和明确状态；完整规则只在相关详情中展开阅读，不在下拉框、提示块、标题和无障碍文本中反复堆叠。
- 详情分开呈现规则要求、机器判断、实际来源证据和处理建议。模型解释不是原文。
- 支持一个结论引用多个文件的工作表/单元格、页码/文本块、段落/表格单元格；区分目标文件与参考资料。
- 有结构化位置时准确定位；OnlyOffice 或格式不支持精确跳转时，提供明确位置和可核对摘录，不把全文检索包装成已定位证据。
- 缺资料说明补什么；规则歧义说明确认什么；系统失败说明能否重试。报告和现有导出/分享内容同步保留未解决项与覆盖限制。
- 保留原件预览、人工复核、修改后重审及既有产品路径，不因界面简化而删除功能。

### 6.3 响应式与设计约束

- 桌面和 iPad-like 布局采用适度密度的列表—详情；手机采用列表—详情切换。保留筛选、选择、滚动上下文和未保存复核提示。
- 修复本流程相关的重复表述、过深嵌套、对齐、等高、长文本溢出和空白失衡，不扩大成全产品重新设计。
- 使用 shadcn/ui 基础组件、Tailwind v4 主题和本仓领域布局组合，并由 `pnpm lint` 约束组件重绘、颜色、任意值和内联样式。图标用于通用动作，保留可访问名称；关键状态和业务歧义不能仅用陌生图标表达。
- 验证键盘、焦点、触控目标、读屏语义与减少动效。视觉上的短标题不应造成完整规则不可访问。

外部参考仅吸收必要交互：[Polar LLM-safe design system](https://polar.sh/blog/orbit-llm-safe-design-system) 的约束式组件、[Beautiful UI](https://www.beautifului.dev/#thinking-state) 的任务状态和 [AI Elements](https://elements.ai-sdk.dev/) 的来源引用。本轮不需要引入 [json-render](https://github.com/vercel-labs/json-render)、模型生成页面或第二套样式体系。

## 7. 明确非目标

- 通用 Audit VM、完整规则 DSL/ORM、独立 Agent 平台或多 Agent 调度框架。
- 新数据库、新队列、独立产品台账，或取消现有有意共享的数据环境。
- 小模型训练、强化学习、模型蒸馏、跨客户自动学习和通用模板记忆管理。
- 任意模板、任意客户规则、所有扫描件/视觉符号都正确处理的保证。
- 新增聊天主入口、第二套前端、Vue/Java 产品层迁入或全站视觉重做。
- 重新设计计费/正式审批制度、自动迁移旧审核历史或拆除 ppap-agent。
- 仅为证明工作量新增测试平台、状态台账、证据注册系统或大批重复 E2E。

## 8. 最小实施顺序

以下顺序是技术依赖，不要求拆成多套平台或人为串行的 Issue。

1. **选定真实样例和预期**：确定规则有效正文、文件角色、条款身份、人工预期及证据合同；确认预算和可用隔离运行时。
2. **形成最小真实端到端路径**：一份 Excel、一份客户规则，经现有 Product API/队列进入 grok-build，经过证据验证，进入现有 finding 和页面。同步完成必要隔离、续租与失败终态。
3. **补齐联合审核及工具**：接入 CP/PFD/PFMEA 参考关系、规则原始来源、适用 checker、确定性查询、诊断和有界修正；覆盖其他首批格式的代表样例。
4. **验证长上下文和复用**：实际触发压缩，检查工件重读、条款/证据完整、版本失效和成本边界。不得用更大 prompt 代替压缩验收。
5. **完成必要 UI 与整体验收**：贯通进度、覆盖、证据、复核和报告；验证桌面/平板/手机；确认 Standard 不退化。

尽早取得第一条真实审核证据，再扩展覆盖。不要等全部工具迁完才运行第一次端到端，也不要先做纯视觉重构。验证优先复用现有测试入口和资产，增加必要的少量边界回归，不建设新测试平台。

### 9.3 证据要求与完成定义

- 每个业务样例先确定人工 expected；关键条件要有正反对照。模型生成的 expected、模型自评或格式校验不能替代独立判断。
- 记录实际执行器、模型/CLI 版本、输入/规则版本、结束原因、用量和必要工具证据。敏感日志和客户原文只留在已有授权存储边界，不写入通用日志或提交。
- 确定性边界复用现有 unit/integration 测试；真实 Deep 用实际模型与工具运行；浏览器只保留少量完整流程，不重复堆积测试平台。
- API 连通、出现“深度”标签、生成报告、通过 mock 测试或旧 Issue 关闭，均不能替代真实端到端验收。
- 本轮完成要求：上述业务样例与必要边界通过，Standard 无新增 regression，必要 UI 可用；所有未支持项都有明确边界，不存在伪装成成功的遗漏条款。

## 10. 待验证项与执行前提

以下事项属于实施时需要验证的工程事实，不是已经完成的能力：

1. 固定 grok CLI、Responses 网关与选定模型能否连续调用工具、压缩上下文并正确返回结构化终态。
