# 首轮原型任务书：从异常到补件

状态：一次性概念原型，不是 PRD、界面规范或真实审核能力证明。依据：[从零设计提案](GREENFIELD_PPAP_SYSTEM.md)。Stitch 项目：`projects/13261964020862199279`（Greenfield PPAP · 量产批准证据工作台）。

## 要回答的问题

客户质量工程师面对一包质量不齐的资料时，能否在没有培训的情况下分清**已证实的不一致、证据不足和资料技术问题**，定位原件，向供应商发出准确补件请求，并理解正式批准仍由人决定？这是首轮原型唯一要验证的产品问题。

本轮不验证模型准确率、扫描件解析能力、真实文件编辑、权限或后端性能。Stitch 屏幕使用模拟但自洽的数据，不导入客户原件。

## 唯一场景与模拟事实

- 批准事项：客户“北辰汽车”、供应商“明川精密”，零件“P-204 支架”，图纸修订 B，生产地点苏州。名称与数据均为虚构。
- 文件：`控制计划_B.xlsx`（合并单元格较多）、`过程流程图_B.pdf`（扫描件）、`尺寸报告_A.xlsx`（旧修订）。本轮要求包括流程/控制计划工序一致、当前修订尺寸报告有效。
- 已证实的差异：流程图第 17 道为“热处理”，控制计划对应工序为“表面处理”；两处原文均可定位。显示为**不符合**，不是笼统“AI 发现风险”。
- 待澄清：扫描件中有一处无法可靠读出的工序号，不能据此给通过或不符合。显示为**无法判断**，并要求更清晰原件或人工确认。
- 缺资料：尺寸报告只对应修订 A，不能证明修订 B 的尺寸结果。显示为**需补件/未覆盖**；不能把旧报告当作修订 B 的业务 NG。
- 其余已核实要求可以单独显示为通过，不因局部不确定而整包失败；整包也不能标为“全部通过”。

## 用户任务与屏幕状态

1. **批准事项概览**：用户一眼看到本次提交是否可作决定、三类问题各有多少、最先处理什么。主操作是“复核差异”，不是再次上传或打开聊天。
2. **差异与原件**：选择第 17 道工序后，看到适用要求、两份原件的具体位置、机器结论和待确认边界。能从结论返回原文。
3. **补件请求**：将已证实差异、扫描件澄清和新修订尺寸报告分别分配给供应商；文案明确“要改什么/要提交什么”，允许客户编辑后发送。
4. **新版本差异**：供应商补交后，系统显示哪些问题已解决、哪些仍未解决、哪些检查需重跑；历史结论和原件版本仍可查看。最后只能由授权人决定是否批准。

四个状态组成一条连续故事；Stitch 只生成视觉屏幕，不宣称它们已实现可点击的业务流。首个“概览”屏幕应比较结构上不同的方向：**行动清单优先、要求矩阵优先、证据关系优先**。不以改颜色或换文案冒充设计变化。后续屏幕在选定方向后保持同一视觉语言。

## 观察与判定

请真实质量人员用原型完成三个任务：指出最重要的阻碍及原因；找到第 17 道工序的两处原文；说出需要供应商提供什么、自己现在能否批准。观察误读和犹豫，少问“喜欢吗”。

通过标准：用户不把“无法判断/旧报告”误读为已证实 NG 或 PASS；不用解释即可找到原文与责任人；能说出补件后的下一步；知道机器建议与正式批准的区别。若失败，先改信息结构或术语，不先增加说明文字。

## 原型边界

这是一份可丢弃的探索材料，不进入生产代码。首轮只检验工作流与信息层级；视觉偏好单独收集。原型结论形成后，再把经过验证的决定写进正式 PRD，并用真实资料建立审核能力验收。没有观察结果前，不以精美画面宣称产品方向已验证。
