# PPAP 交互原型任务书

状态：第一性原理旅程已成为产品主入口；未接入服务器的后续环节仍为交互原型。依据：[从零设计提案](GREENFIELD_PPAP_SYSTEM.md)。Stitch 项目：`projects/13261964020862199279`（Greenfield PPAP · 量产批准证据工作台）。下述探索记录不等于真实审核能力证明。

## 产品接入边界

- 唯一实现位于 `apps/web/src/journey/`；产品入口与开发预览复用它。`preview/` 只保留入口和预览台，不保留第二份页面或模拟 Product API。
- 沿用 React + TypeScript、现有 shadcn / Radix 组件和设计 token。不使用原生 `details` / `summary`，不加载原型的独立 CSS。
- 首条真实路径：登录 → 上传资料 → 在同一准备工作区核对资料与事项范围 → 上传或选择审核要求 → 核对来源与本次适用性 → 显式启动并固定规则和文件版本 → Standard 执行 → 同一工作区阅读原件并保存人工复核 → 刷新后继续。
- 准备工作区采用 Stitch 参考 `0a13f18b48164253b361644d2c02d6a0`：主表保留纳入选择、文件和资料类型；选定依据后显示真实待审／参考用途。文件声明修订、可读性标记和随件说明收于“文件信息”抽屉，已知不可读等异常仍在文件行提示；未核对不等于可读。五项事项归属和本次依据确认不取消。已完成轮次查看资料后可直接返回人工复核。
- 来源内容、出处和版本未变时，复用已有来源核对记录；本次适用性仍由审核员确认，可批量将待确认条款设为适用，再逐条排除并说明理由。修改范围不清空来源核对记录，修改条款或出处会使对应来源核对失效。不把选中、已上传或已受理当成质量结论。
- 工作台采用 Stitch 参考 `537ac169f04b40f587c5b59452a7ffba`：先显示执行异常和待复核事项，再显示审核准备、系统处理中；已复核事项收于次级入口，仍可搜索或在“事项”中查看。完成轮次直接进入复核。列表仅在工作台可见时定期更新，保留已展开的分页；一类记录读取失败不清空另一类或上次成功内容，也不显示为空列表。机器未覆盖与有效人工记录分别计数；不适用项、旧格式判断、空理由或缺少有效引用的人工独立结论不计作复核完成。
- 进度采用 Stitch 参考 `f2caf9c26cb14d30aa76e53f5110f904`：显示服务器阶段与已知检查数量，不编造百分比或队列位置。按状态提供返回工作台、开始／继续复核、查看已有结果或核对本轮资料的主要操作；状态读取失败与审核执行失败分开显示。空结果不视为通过，人工记录全部保存不等于问题解决或正式批准。没有真实重试接口时，不提供虚假的“重新执行”按钮。
- 复核采用 Stitch 参考 `1455a90bd66e4891a879ebc715e815a2` 的单条款工作区：桌面 Resizable 分栏，窄屏 Tabs 与明确的“返回判断”；条款目录按需打开，不常驻第三栏或列表滚动区。当前条款、筛选、阅读文件与明确位置可随 URL 恢复，判断保留同一草稿。表格选中单元格可将固定版本、位置与保存值引用到草稿，不代写判断与理由；其他格式仍需人工阅读。切换条款时清除旧定位，不能把无法对应的来源自动替换成上一份文件。
- 任务层级采用 Stitch 参考 `34f7796e5001437da045ab5abdd66a89`：真实人工复核是当前任务，决定与交付保留在次级“后续流程（原型）”入口，不再作为同级主标签；其位置可随 URL 恢复。手机复核用明确返回路径代替重复的全局阶段栏，压紧依据工具条，全轮计数仍可在目录中读取。全部人工记录保存后仍明确未满足条款，不把保存完成称为问题解决或正式批准。
- 保存结果不明时保留原请求和输入，先回读再重试；刷新和切换条款不会丢弃待核对状态。“保存并继续”只在回执与当前输入一致且未离开该工作上下文时进入下一条，迟到回执不覆盖新输入或强制跳转。仅打开旧草稿不向服务器回写。已受理轮次以服务器冻结的资料、范围和依据为准，不由浏览器旧草稿替换；同轮尚未提交的澄清说明可以保留。事项与轮次链接独立可打开；返回或重选后，晚到的读取不得重新打开旧事项。
- 通过现有 Product API、共享存储、数据库与任务队列执行。`case_context` 只承载交互登记信息，不替代文件证据；受理时固定为轮次快照。
- 人工复核与机器结果分开保存。未覆盖条款可以记录人工判断，但不会据此生成机器 PASS。人工独立结论必须含本轮文件版本、出处、摘录与理由。
- 正式批准、报告交付、补件复审和变更流程仍保留原型交互；不得把本机模拟记录称为服务器批准或真实送达。Deep 的算法增强不是首条 Standard 接入的前置条件。
- 新环境需执行 numbered migrations，其中 `0020_case_context.sql` 增加登记快照与人工引用支持。开发预览显式使用模拟资料；普通产品入口不使用模拟登录、额度或审核结果。

开发者使用现有 `1-1规则-尺寸检验报告.docx` 验证了上传、真实条款提取、人工核对与发布；未支持的九条客户条款保留为未覆盖，人工“仍无法判断”保存后刷新可读回。使用 `尺寸检验报告-example.xlsm` 与现有十一项 Standard 内置检查标准，新轮次实际返回五项满足、六项不满足；从第七项读取固定原件，核对 `Gap&Flush-002` 的 `G10:H10` 和 `K10`，并保存人工引用。这些结果只证明此接入路径及代表性资产，不证明任意客户规则可由 Standard 执行，也不证明正式批准与交付已接入。

1440×1000、820×1180 与 390×844 视口检查了多文件准备、复核分栏/切换、原件定位和已保存判断；所查页面没有横向溢出，窄屏切换没有重建 Office 实例。旧草稿仅打开再返回后，服务器更新时间未变。补正、变化、决定与交付的交互入口继续保留，其后端边界仍按上文限定；这些检查不证明任意输入都可正确审核、物理设备的全部手势或完整无障碍合格。

工作台和进度页另用隔离的只读响应检查了状态更新、分页保留、快速搜索的迟到响应、离开页面停止轮询、首次与部分读取失败、执行失败、未覆盖、空结果和人工记录完成。读取故障不触发新审核，人工记录完成仍保留不满足项。该受控检查只证明前端响应与恢复行为，不替代上述真实审核结果或用户验证。

## 要回答的问题

审核团队收到供应商通过系统外渠道发来的一包质量不齐的资料后，能否连续完成事项定界、收件、检查、逐项人工复核、记录对外沟通、登记回件、版本复审、决定与变更影响识别，同时分清**收到新文件、问题已解决、可以批准**三种不同判断？首版只有审核团队一种系统角色；多名审核员可以同属此角色，供应商不登录本原型。

本轮不验证模型准确率、扫描件解析能力、真实文件编辑、权限或后端性能。Stitch 屏幕使用模拟但自洽的数据，不导入客户原件。

- 待澄清：扫描件中有一处无法可靠读出的工序号，不能据此给通过或不符合。显示为**无法判断**，并要求更清晰原件或人工确认。
- 缺资料：尺寸报告只对应修订 A，不能证明修订 B 的尺寸结果。显示为**需补件/未覆盖**；不能把旧报告当作修订 B 的业务 NG。

## 用户任务与屏幕状态

1. **来件登记与批准事项概览**：审核员选择本轮收到的原件，核对归属、修订和可读性，再开始检查。概览显示三类问题和最先处理什么；主操作是“复核差异”。
2. **差异与原件**：选择第 17 道工序后，看到适用要求、两份原件的具体位置、机器结论和待确认边界。能从结论返回原文。
3. **补件请求**：审核员核对并编辑不同性质的请求，通过现有渠道联系供应商；原型只模拟记录对外请求，不声称消息已由系统送达。
4. **回件登记**：审核员填写回件来源，逐项记录供应商说明、新原件或异议；只收到部分答复也可以登记，旧原件不被覆盖。
5. **版本复审**：收到新文件后先标明待重查，再逐项记录已核实的事实、未答复和待审内容；历史结论与原件版本仍可查看。正式批准仍由授权人决定。

上述状态组成一条由审核员连续操作的故事。Stitch 屏幕保留为早期静态视觉探索，其中的双角色设定已废弃；本地 React 原型不接真实后端。概览比较**行动清单、要求矩阵、证据关系**三种结构方向，不以改颜色或换文案冒充设计变化。

## 观察与判定

上线前由开发团队使用模拟故事和代表性资料核对状态、文案及关键边界，不把内部走查称为用户验证。系统原型上线后，再请真实审核人员完成三个任务：指出最重要的阻碍及原因；找到第 17 道工序的两处原文；说出需要供应商提供什么、自己现在能否批准。观察误读和犹豫，少问“喜欢吗”。

通过标准：用户不把“无法判断/旧报告”误读为已证实 NG 或 PASS；不用解释即可找到原文与责任人；能说出补件后的下一步；知道机器建议与正式批准的区别。若失败，先改信息结构或术语，不先增加说明文字。

## 原型边界

早期 Stitch 产物是探索材料；已吸收的交互由产品实现拥有。保留的模拟场景仅用于设计预览，不能证明审核正确性。真实路径以 Product API 回执、固定文件与规则版本、机器结果及人工复核记录为准；没有观察结果前，不以精美画面宣称产品方向已验证。

## 第二轮：审核员收件与预检

在同一虚构事项上增加[统一审核旅程入口](http://127.0.0.1:4185/__preview?page=intake)。Stitch 曾以供应商提交为假设探索资料清单，屏幕 ID：`129a084c1cd642f1a31d85f3e698274b`。现按实际工作模式改为审核员登记外部来件；生成稿自造的准入政策、准确率、哈希签署和多余导航均未采用。

本地旅程改为**先上传，再核对收件**：供应商仍在系统外发送文件，审核员在上传页选择文件，随后核对类型、修订、归属与是否纳入本轮。上传是唯一真实文件输入入口；“加载示例资料包”只是固定演示场景。核对页可切换**资料优先**（当前建议）、**待办优先**、**要求优先**三种结构。固定示例可模拟登记清晰扫描件或 Rev B 报告；浏览器选择的文件只记录名称和人工填写的信息，不读取内容，不给出预设审核结论。收件确认页允许记录供应商随件说明，但不强迫审核员替供应商编造说明。更改声明修订不会改写原件内容，也不会把 Rev A 变成 Rev B 覆盖。登记不产生工艺或尺寸的合格结论。

本轮有浏览器文件选择，但仍无服务端上传、持久化、身份授权、真实规则执行、冻结事务或通知。模拟收件号不是审计存证。真实审核员的可用性观察安排在系统原型上线后；上线前由开发团队检查流程与状态正确性。

## 第三轮：审核进度与定向澄清

审核员登记来件后，进入[检查进度原型](http://127.0.0.1:4185/__preview?page=progress)，再衔接人工复核。Stitch 早期探索屏幕 ID：`cec030a204194df7b5c1466b6923fe38`。它自造的工序号、图幅坐标、附件政策及“澄清立即解除阻断”的承诺，本地原型没有采用。

本地共用收件页的模拟原件选择。三个结构方向为**行动优先**（当前建议）、**进度优先**、**要求优先**，可切换审核中、需澄清、局部失败、待人工复核四种模拟状态。页面按“识别资料 → 建立关联 → 检查要求 → 核验证据”显示进展；工序差异、扫描件无法判断、Rev A 未覆盖 Rev B 与技术执行失败保持不同含义。审核员可以记录从系统外收到的供应商说明；说明不改写已登记版本，也不自动使该项通过。同一会话进入人工复核时，原件、缺口与说明一同带入。技术失败不能伪装成业务结论；检查结束不等于批准。

内部验证重点：审核员能否分辨系统已完成的步骤与仍未核实的条款，并知道哪些澄清须通过系统外渠道取得；局部失败或资料未覆盖时，不能误以为整包通过。此页仍没有真实审核、任务执行、事件记录、澄清通知或原件持久化。默认布局与措辞待上线后观察真实任务再定。

## 第四轮：外部补正与内部复审

审核员准备定向补正请求，通过现有渠道联系供应商，并在原型中模拟记录这次对外请求。供应商回件后，审核员进入[回件登记原型](http://127.0.0.1:4185/__preview?page=amendment)，再进行版本复审。沿用早期请求与版本差异的视觉探索；本轮未生成新的 Stitch 屏幕。三个可切换结构为**请求优先**（当前建议）、**原件优先**、**逐项引导**，共用同一份页面内存状态。

| 接收一包陌生文件 | 上传按文件反馈；核对类型、修订、归属和待审/参考用途；可保留未确认资料。 | 显示哪些已纳入、哪些暂存、哪些需要重传，不把接收完成写成审核通过。 |
| 明确审核依据 | 从已有要求选择或上传要求文件，核对来源和解析条款，确认适用性及版本。 | 每条要求有来源；冲突有具体待确认项；修改依据后旧检查不会显示为当前有效。 |
| 开始并跟进检查 | 确认覆盖范围、资料缺口和预计用量；开始后可离开、返回、核对未知受理结果。 | 按要求显示已查、未查、无法判断和失败；局部失败仍保留其他结果，恢复不重复建立事项。 |
| 判断一条发现 | 从要求进入一份或多份原件的具体位置，记录人工判断、理由和下一步。 | 保存反馈与下一项可达；机器意见不被覆盖；不能只关掉提示就算问题解决。 |
| 获取并处理补件 | 生成问题清单；登记系统外沟通。新附件先上传再核对，然后关联问题和供应商说明。 | 部分回件显示已收到的部分；未答复继续待补；修改原因随新版本进入复审。 |
| 核实问题是否解决 | 比较新旧依据，重查受影响要求，再记录人工复核。 | 收到、重查、解决独立变化；不相干的新文件不能关闭问题。 |
| 作出决定并交付 | 条件满足时核对批准范围并确认决定；生成报告和资料包，可模拟飞书交付目标。 | 决定与报告固定依据版本；失败或未知有恢复动作；生成报告不声称已对外送达。 |
| 处理之后的变化 | 再次上传来件或核对新的要求版本，查看哪些依据受影响。 | 原批准及交付记录可查；变化范围进入待评估，不自动继承或撤销全部历史决定。 |

### 连续模拟的最小事实

同一事项持有范围、要求版本、每次来件的文件版本及用途、检查记录、人工复核、问题清单、供应商原话、决定与交付记录。页面共享这些事实；选择某个界面方案不重置事项。记录可在浏览器本地恢复，清理须从账号菜单的“本机记录”显式核对并确认。演示文件内容已知；任意选择的真实文件不能获得预设的演示结论。

四个判断必须独立：

| 判断 | 成立依据 | 不足以使其成立的操作 |
| --- | --- | --- |
| 已收到 | 这一批文件或说明已登记，来源和版本可查。 | 点击上传但接收结果未知。 |
| 已检查 | 对确定要求和原件已有检查结果，覆盖与失败明确。 | 文件可读、进度结束或已产生部分结果。 |
| 问题已解决 | 当前依据回答该问题，必要的复查与人工确认完成。 | 收到新文件、供应商声称修改完成、两份文件无差异。 |
| 可以批准 | 所有必需要求均有当前有效依据，必要复核完成，有权人可形成决定。 | 检查结束、没有报错、所有补件已收到。 |

### 可实际操作的代表性故事

1. **完整批准**：首次进入 → 上传固定清晰示例包 → 核对归属 → 确认要求 → 检查 → 逐项复核 → 批准 → 生成并下载报告 → 返回工作台 → 再次打开同一决定。每一步引用同一事项及明确版本。
2. **补正后批准**：P-204 初次出现工序矛盾、模糊扫描、旧尺寸报告 → 确认问题并形成清单 → 先只上传清晰扫描 → 核对并复审，另外两项保留 → 再上传修正控制计划及 B 版尺寸报告，登记修改原因 → 重查并核实 → 条件满足后批准。
3. **无法判断与异议**：原件部分不可读 → 登记供应商说明或异议但没有足够新证据 → 复核仍保留无法判断，不准许批准；用户可以暂存离开并恢复。
4. **局部检查失败**：一项工具失败，其他检查已有结果 → 回到工作台再进入 → 恢复失败部分 → 已有复核保留，失败项取得结果后才进入复核；没有第二笔检查受理记录。
5. **要求与版本变化**：已经批准 B → 收到 C 或新要求 → 上传后核对 → 显示受影响要求 → B 的报告仍可查，C 不能继承 B 的批准 → 新检查使用新的依据。
6. **常见中断**：上传部分失败、规则解析失败、会话过期、受理结果未知、报告生成失败 → 保留有效输入，按对象恢复 → 不重复创建相同资料、检查或报告。

走查同时检查桌面、平板与手机：关键证据可到达，当前事项与版本可辨，触控和键盘可完成主要操作。开发团队操作结果与真实用户可用性观察分别报告；类型检查或截图不能证明整条故事已成立。
