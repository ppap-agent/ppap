# 数据所有权与不变量

这是产品数据语义，不规定具体表名和实现框架。

| 事实 | 唯一拥有者 | 备注 |
|---|---|---|
| 用户、租户、外部身份、成员授权 | product | 不复制通用组织树 |
| 文件与文件版本 | product + object storage | 数据库拥有版本 identity 和对象引用；文件名、大小、类型、可选 checksum 是元数据 |
| 草稿、目标/参考角色、规则版本 | product | 草稿可编辑；受理后引用固定 |
| 审核轮次、结果、依据、人工复核 | product | 机器结果和人工记录分开 |
| 执行工作、尝试、租约、运行诊断 | engine | 绑定既定轮次输入；不等于客户看到的审核任务 |
| 使用事件 | product | 外部账单/权益是确认结果，不由本地估算代替 |

## 用户任务与界面合同

V3.1 的用户任务连接识别、待确认和已受理的轮次，不取代文件版本、轮次或内部执行工作。创建任务与受理付费审核是不同动作；技术重试不创建新的用户任务或审核轮次。

同一任务可以包含多种文件类型；每份进入审核的文件绑定自己的规则版本。单文件结果、报告和费用必须能回到明确的轮次与文件版本，不用文件名或当前选中的页面替代归属。证据可引用多份授权的冻结原件，不能把未选中或已移除文件作为隐藏输入。

Web JSON 类型继续由 Product API 的 OpenAPI 生成；预览与真实界面共用同一合同，不另建前端 DTO 注册表。展示状态可以是前端投影，任务、审核结果、报告和费用事实不能由浏览器缓存或 fixture 充当服务端记录。最小新增字段与稳定映射由 [#164](https://github.com/ppap-agent/ppap/issues/164) 定义；费用与对象权限仍按下文现行边界执行，政策变更须先由 [#163](https://github.com/ppap-agent/ppap/issues/163) 明确确认。

文件识别信息随当次审核依据保留；`Metadata.part` 继续表示零件名称，零件号使用独立的可选 `part_number`。按 #163 已确认的 D8 文件信息更正边界，显示更正必须与原始识别信息分开保存，不改冻结文件、规则、机器结果或既有报告，不重匹配、不重跑审核。此决定不替其他未决政策作选择。

显示更正以 Task、Round、FileVersion 三者共同确定范围，同一文件用于另一任务时不继承更正。保存按已读显示修订作比较并交换；原请求和 saved/conflict/rejected 回执追加保存，后续更正不改写旧回执。当前 Task 返回最新显示值与当前编辑许可；原请求读回只证明该次保存结果，不授予编辑权限，也不能替代当前 Task 读取。

Deep 主机完成来源与执行记录校验后，在既有 coverage 中记录验证方法、执行身份与逐条 proof 类型；它与 Findings、结果 attempt 在同一完成事务保存。Task 和历史 Round 只认可与冻结文件、规则正文、结果键及当前结果执行身份一致的记录；没有该记录的旧结果不补标。Query proof 重放已绑定数据上的谓词，semantic proof 核对来源、记录和聚合一致性；二者都不证明自然语言解释、适用范围或模型业务判断必然正确，也不代替客户质量验收。人工复核不提高机器验证状态。

符合 D1 的新 Task 文件结果在审核完成事务中创建唯一 `report_pdf` 工作；既有 `engine.jobs` 拥有生成状态与产物元信息，不另建报告台账。工作固定本轮文件、规则、机器结果及来源名称，不包含人工记录或显示更正。PDF 对象按报告工作和生成 attempt 隔离，只有获胜 attempt 可发布；对象写入不等于报告就绪，写入后中断的私有对象仍归原 attempt。任务完成等待首次报告就绪或失败，不等待未开放的显式重生成。

报告 ZIP 同样复用 `engine.jobs`：`report_zip_request` 固定创建人、请求与有序报告引用；`report_zip` 固定规范化集合、实际 PDF 产物、规则及生成时间。相同集合的不同创建请求只关联同一个工作，重排或失败都不重建工作。显式恢复绑定原请求、包身份和已读生成 attempt；在同一事务重排原工作并保存恢复回执，不重新选择 PDF。旧失败代次不能启动新恢复，旧 Worker 不能发布。业务计费启用时拒绝新的恢复请求，已有回执仍可读取；不据此确定恢复收费政策。ZIP 是既有报告的交付产物，不创建审核轮次、消费或第二套机器结果。

## 文件版本

每次明确上传或导入创建一个新的 `file_version_id`，关联一个存储对象或 provider version。历史轮次引用 `file_version_id`，而不是文件名、当前 URL 或内容 hash。

已经被引用的文件版本不能被后续上传重定向到另一份内容。新上传使用新的版本记录和对象引用。hash 可以用于内容比较、排障或特定完整性需求，但不是版本 identity，也不是所有正常路径必须理解的字段。

飞书导入可以给文件版本保存 **file origin**（从哪个飞书对象导入）。审核草稿和审核轮次另外保存 **writeback target**（结果应写回哪篇飞书文档）。两者可能不同，不能把导入来源自动当成写回目标。公开 JSON 只暴露是否可写回/来源种类，不返回外部 object_ref。

暂存上传和最终可引用版本应有清晰边界；未完成的暂存不能被审核受理。数据库与对象存储不是同一个事务，失败时只需要保证最终数据库状态和对象清理语义明确，不伪装成分布式原子提交。

```text
audit_round
  -> analysis_mode (standard | deep; 草稿可改，受理后冻结)
  -> target file_version_id + frozen rule_version (id/title/body)
  -> reference file_version_id (无审核规则，仅上下文)
  -> job/attempt（冻结 executor / executor_revision）
  -> machine findings + locators
  -> human reviews
```

`analysis_mode` 属于草稿和轮次，不是文件或规则属性。缺省 `standard`。相同幂等键、相同文件版本/角色/规则绑定、但不同 `analysis_mode` 视为冲突。`request_fingerprint` 仍只覆盖文件版本/角色/规则绑定，不把模式塞进指纹。SHA-256 只用于 Deep 执行完整性校验，不替代 `file_version_id`。

## 受理与重试

每个待审文件在受理时绑定明确规则版本；参考文件不得附审核规则。草稿保存可暂缺规则，受理不可缺。规则的 id/title/body 随每个轮次输入冻结，后续发布不会改旧快照。标准审核还冻结当时的条目执行映射：能映射到内置检查的条目进入机器结果，不能自动执行的条目进入 `coverage.unchecked`，不能把另一套内置检查项伪装成用户清单。

相同租户、相同幂等键、相同文件版本/角色/规则绑定与 `analysis_mode` 返回同一轮次；同键不同请求冲突。幂等键不是授权，返回既有轮次前仍检查对象权限。创建轮次、冻结输入和创建执行工作在一个 PostgreSQL 事务内完成。

Worker 用租约/attempt fencing 防止晚到结果覆盖当前结果。技术重试保持轮次不变；用户主动重审创建新轮次。

外部非幂等调用出现未知结果时先读回/对账，不盲目重发。数据库队列不声称外部模型或计费 exactly-once。

## 授权与用量

所有关联查询都检查租户和对象权限；UUID 不代表授权。已受理审核轮次是租户内企业业务记录，同租户成员可查看和复核；草稿仍是创建者私有工作区。登录不等于跨租户授权。

用量只记录实际发生的业务事件和外部确认状态。企业成员读取同一份 tenant 用量账；Partner AI 上报仍由事件发起人认领结算，不能用查看者的 user token 代报。外部计费/权益未确认时保持未知或待对账，不根据本地 job completed 自动认定已扣费。发起人可对 pending/unknown 显式重试。

受理事务按待审文件数 × 500 点生成用量，参考文件不计费；同租户/用量项目的试用分配串行化，轮次与试用/付费分片唯一。客户端不能指定消费点数或确认状态。显式重审产生新的消费，技术重试和受理回放不产生。

上报在鉴权准备后原子领取发送权；发送后超时或响应不明确标为 unknown，不提供自动重发。reporting 超过 120 秒展示为 unknown，原发送者的明确晚到响应仍可确认。用量页支持日期查询和人工上报；未接入可验证的飞书读回接口，因此不声称自动对账。生产切换前须确认客户既有试用权益，不能把本地默认试用额当成重置授权。剩余试用 = 配置额度 − 已确认 cut-over baseline − current PPAP 已消耗试用。Partner AI 付费余额仍以飞书配额为准，不被本地试用账覆盖。
