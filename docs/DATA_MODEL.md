# 数据所有权与不变量

这是产品数据语义，不规定具体表名和实现框架。

| 事实 | 唯一拥有者 | 备注 |
|---|---|---|
| 用户、租户、外部身份、成员授权 | product | 不复制通用组织树 |
| 文件与文件版本 | product + object storage | 数据库拥有版本 identity 和对象引用；文件名、大小、类型、可选 checksum 是元数据 |
| 草稿、目标/参考角色、规则版本 | product | 草稿可编辑；受理后引用固定 |
| 审核轮次、结果、依据、人工复核 | product | 机器结果和人工记录分开 |
| 执行工作、尝试、租约、运行诊断 | engine | 绑定既定轮次输入；不等于客户看到的审核任务 |
| 使用事件 | product | 外部账单/权益是确认结果，不由本地估算代替 |

## 用户任务与界面合同

V3.1 的用户任务连接识别、待确认和已受理的轮次，不取代文件版本、轮次或内部执行工作。创建任务与受理付费审核是不同动作；技术重试不创建新的用户任务或审核轮次。

同一任务可以包含多种文件类型；每份进入审核的文件绑定自己的规则版本。单文件结果、报告和费用必须能回到明确的轮次与文件版本，不用文件名或当前选中的页面替代归属。证据可引用多份授权的冻结原件，不能把未选中或已移除文件作为隐藏输入。

Web JSON 类型继续由 Product API 的 OpenAPI 生成；预览与真实界面共用同一合同，不另建前端 DTO 注册表。展示状态可以是前端投影，任务、审核结果、报告和费用事实不能由浏览器缓存或 fixture 充当服务端记录。最小新增字段与稳定映射由 [#164](https://github.com/ppap-agent/ppap/issues/164) 定义；费用与对象权限仍按下文现行边界执行，政策变更须先由 [#163](https://github.com/ppap-agent/ppap/issues/163) 明确确认。

文件识别信息随当次审核依据保留；`Metadata.part` 继续表示零件名称，零件号使用独立的可选 `part_number`。按 #163 已确认的 D8 文件信息更正边界，显示更正必须与原始识别信息分开保存，不改冻结文件、规则、机器结果或既有报告，不重匹配、不重跑审核。此决定不替其他未决政策作选择。

显示更正以 Task、Round、FileVersion 三者共同确定范围，同一文件用于另一任务时不继承更正。保存按已读显示修订作比较并交换；原请求和 saved/conflict/rejected 回执追加保存，后续更正不改写旧回执。当前 Task 返回最新显示值与当前编辑许可；原请求读回只证明该次保存结果，不授予编辑权限，也不能替代当前 Task 读取。

Deep 的执行身份、来源及运行记录与 Findings、结果 attempt 在同一完成事务保存。Task 和历史 Round 只认可与冻结文件、规则正文、结果键及结果执行身份一致的记录；没有对应记录的旧结果不补标。验证含义必须对应实际执行路径：当前固定 Python checker 不使用旧 `host_source_trace_v1`，产品映射的 `evidence_verified` 为 false。旧 Query/semantic proof 记录保留原方法与边界，不能给新 checker 补标。可执行、可重放、引用有效均不证明规则解释或业务结论正确；人工复核不提高机器验证状态。

Deep 的规则附录是明确输入，由用户确认的解释、映射或标准修改构成，带内容、文件/条款作用范围和确认来源；候选、聊天与人工复核不自动进入附录。每次后续分析冻结基础规则来源及当次完整附录，复用现有规则 packet 摘要区分实际输入，不修改已发布的租户通用规则或旧轮次快照。文件限定确认不推广到其他资料；删除附录后新计算不读取旧确认。

附录范围中的 `document_ids` 指被解释的来源文件；`rule_targets` 用 `{document_id, rule_id}` 明确受影响的目标文件和条款。目标文件 ID 是文件版本 ID。两个文件都含 `R1` 时，确认一个目标的条款不影响另一个目标；跨文件来源范围不因此扩大。

形式化与 ontology 接入后的目标合同如下。条款语义确认已经落在 `product.rule_formalizations` 与确认指针上，绑定已发布规则版本，不另建 ontology 服务。Checker 仍不执行 OWL/CLIF。已确认快照只在显式交接时进入 Suite candidate 的 `rules.json`。


- 原规则正文及来源、结构化解释、回译展示和用户确认各自可区分。回译是同一解释的展示投影，不是第二份可独立修改的权威规则；确认记录必须能还原用户实际看到并提交的内容。
- 已确认的实体/属性含义、身份与关系、合法值或主数据引用，以及文档投影约定，作为显式审核依据进入现有规则 packet。引用必须固定作用范围、来源与版本；不能在执行中读取“最新”定义改变历史输入。仅有外部名称或可变链接不构成可重放依据。
- 模型候选、原件观察值与合法值分开。候选保留来源和建议作用；确认可以新增、替换或移除，不能默认采用“最后一条优先”消解冲突。值域不完整时保留未知，确认概念映射不自动确认该值合法或两个实例相同。
- `resources.py` 中的布局绑定及派生投影随 checker 产物固定，引用实际文件版本和原件位置；用户确认的语义约定另有产品确认来源。任务产物不是第二份可独立修改的产品事实。
- 这些生效内容及版本参与现有输入摘要和产物适用性判断。规则文本相同而含义、值域或投影约定变化时，旧程序只能作适配起点。短期复用附录、packet 与 attempt 产物，按真实消费者扩展原类型，不预建 ontology 服务或另一套确认账本。

此目标的数据含义与工程接口分别由本文件和 [Deep DESIGN](../packages/agent/DESIGN.md) 拥有。已实现的是：已发布 `rule_version_id + clause_id` 上的 OWL 2 公理、OWL 不能表达时的 CLIF、同源 CNL，以及用户确认。不执行 OWL/CLIF。OWL 2 DL 是开放世界，不能单独表达跨记录数据值相等或封闭唯一匹配；这些义务用同一规范里的 CLIF，未声明的政策不能变成默认结论。模型语义质量未验收。Ontology 投影和值域约束仍未实现。已确认且完整的快照只在用户明确交接时写入指定 Suite candidate，且不自动发布。没有这份快照时，Checker 仍按原规则路径工作。

条款或其中一部分没有可程序化的判定标准时，用户可以在澄清环节拒绝它，并必须写明原因（哪些部分没有判定标准）。拒绝不调用模型：它是基于最新解释的新不可变解释，`rejections` 记录范围（`clause` 整条或 `part` 部分）、被拒绝的部分与原因；部分拒绝移除用户点名的要点或待选问题，其余要点照常确认和检查。拒绝计入形式摘要，和其他解释一样经用户确认、可撤销，源规则变化后失效重来；后续模型改写保留部分拒绝，并要求模型不再为这些部分写要点。整条拒绝确认后的状态是 `rejected`。交接进 Suite 的快照带上 `rejections`：生成 Checker 时被拒绝部分不写检查逻辑、不调用模型；审核时整条拒绝不运行程序，固定 UNABLE；部分拒绝的其余要点不符合仍是 NG，否则 PASS 改为 UNABLE。两种 UNABLE 都写明拒绝原因并提示人工复核，拒绝不能变成 PASS。形式化生成（OWL 或检查要点整理）是排队的离线工作，审核路径只读取已冻结的确认快照，不同步生成。保存上传规则的版本后，API 在同一事务里为所有有正文、还没有解释、也不能沿用上一版确认的条款各排一次整理，归入同一个 `batch_id`（每个版本一批，重放不重复排队；没有可用文本模型时不排，仍可逐条手动整理）。批内最后一条整理结束（成功、失败、停止或未知）时排一条 `formalization_ready` 飞书通知，只发给保存版本的人，发送时按其当前权限重读。条款列表的 `attention` 表示条款等人做什么：`question` 要选择、`review` 要补充标准、`ready` 可以直接确认、`failed` 没整理出来、`waiting` 还没整理、`running` 还在整理、`decided` 已确认或已拒绝；通知和规则页按这个分类汇总，不替人确认。整理不挤占审核：Worker 认领时审核等前台任务排在整理之前；整理线程池满了只停止再接整理，审核照常认领；用户自己发起的整理排在自动批次之前，每个 Worker 最多同时跑 2 条批次整理，给用户的整理留出位置。`RuleInput.appendix` 继续传入已有附录，不替代形式规范。

连续 Deep 工作区以其原轮次为关联入口，计算仍由既有 Round、Job 和 attempt 拥有。一次规则变更操作拥有唯一回执，记录已读修订、实际保存内容及可选的新分析引用；相同操作重放返回原效果，不同内容冲突，并发变更按修订校验。保存与受理/入队可在同一事务完成，未知响应先读回原操作。仅保存不入队；明确继续分析才创建新轮次，旧轮次与人工判断保留原归属。工作区不是另一套任务或执行账本。

当前保存并分析会对工作区全部待审文件创建新轮次；附录按文件/条款限制作用，不代表已有选择性重跑。语义建议的影响预览与实际执行范围分别表达。仅保存后旧结果继续对应旧依据；确认不直接修改机器判定，已存在的跨文件原值冲突不因实体合并而消失。

未解决的类型化缺口与候选随实际执行结果保存于既有 coverage。问题身份绑定当前输入、内容和范围，输入改变后重新校验；协议问题 key 与业务缺口身份分开。新分析不继承未确认候选或旧问题的默认答案。新的 Deep 反馈轮次沿用工作区的显式对象授权，读取回执、原件与结果仍分别检查权限。

新的结构化语义候选须复用当前问题 fingerprint 与工作区修订校验，绑定当时展示的候选、证据、范围及实际修改；输入或候选变化后不能直接应用旧确认。文件范围不会自动提升为客户或全局范围；扩大复用必须明确确认并检查目标权限。它不授予原件之外的新数据访问权。

训练准备复用运行和变更记录，可导出输入依据、缺口、确认范围、新旧计算关联及有界用量。导出不包含任意运行字典、Secret 或隐藏推理；未知用量不补零。局部确认不是整轮正确标签，构造测试记录保持 `human_gold=false`、`training_eligible=false`。

符合 D1 的新 Task 文件结果在审核完成事务中创建唯一 `report_pdf` 工作；既有 `engine.jobs` 拥有生成状态与产物元信息，不另建报告台账。工作固定本轮文件、规则、机器结果及来源名称，不包含人工记录或显示更正。PDF 对象按报告工作和生成 attempt 隔离，只有获胜 attempt 可发布；对象写入不等于报告就绪，写入后中断的私有对象仍归原 attempt。任务完成等待首次报告就绪或失败，不等待未开放的显式重生成。

报告 ZIP 同样复用 `engine.jobs`：`report_zip_request` 固定创建人、请求与有序报告引用；`report_zip` 固定规范化集合、实际 PDF 产物、规则及生成时间。相同集合的不同创建请求只关联同一个工作，重排或失败都不重建工作。显式恢复绑定原请求、包身份和已读生成 attempt；在同一事务重排原工作并保存恢复回执，不重新选择 PDF。旧失败代次不能启动新恢复，旧 Worker 不能发布。业务计费启用时，新的恢复请求重新检查可用额度；已有受理回执仍可读取，不再次检查或记费。ZIP 是既有报告的交付产物，不创建审核轮次、消费或第二套机器结果。

## 文件版本

每次明确上传或导入创建一个新的 `file_version_id`，关联一个存储对象或 provider version。历史轮次引用 `file_version_id`，而不是文件名、当前 URL 或内容 hash。

已经被引用的文件版本不能被后续上传重定向到另一份内容。新上传使用新的版本记录和对象引用。hash 可以用于内容比较、排障或特定完整性需求，但不是版本 identity，也不是所有正常路径必须理解的字段。

飞书导入可以给文件版本保存 **file origin**（从哪个飞书对象导入）。审核草稿和审核轮次另外保存 **writeback target**（结果应写回哪篇飞书文档）。两者可能不同，不能把导入来源自动当成写回目标。公开 JSON 只暴露是否可写回/来源种类，不返回外部 object_ref。

本地审核文件先选择个人飞书目录，默认「我的文件夹」。目录和文件内容随原上传请求固定；每次明确的新上传创建独立飞书文件，不按同名覆盖。飞书创建回执与内部冻结版本绑定后才进入核对；删除飞书源文件不删除冻结字节或历史审核。完成回执未知时保留原请求，不盲目重传；分片中断只在服务允许时继续同一上传计划。用户可从飞书核对后按新导入处理，再明确排除原传输；新导入独立冻结，不改写原未知回执或按同名自动认领。

暂存上传和最终可引用版本应有清晰边界；未完成的暂存不能被审核受理。数据库与对象存储不是同一个事务，失败时只需要保证最终数据库状态和对象清理语义明确，不伪装成分布式原子提交。

固定模板文档不在产品内产生模板目录、反馈记录或审核用量。已应用的模板缓存、反馈及分享迁移和既有文件版本继续保留，不因入口取消而清空数据库或对象存储。

```text
audit_round
  -> target file_version_id + frozen rule_version (id/title/body)
  -> reference file_version_id (无审核规则，仅上下文)
  -> job/attempt（冻结 executor / executor_revision）
  -> machine findings + locators
  -> human reviews
```

深度模式（2026-11-12 产品负责人决定）：任务级开关 `audit_drafts.deep_mode`，受理前可改（按 `input_revision` 冲突校验，不触发重新识别），受理时冻结到 `audit_rounds.deep_mode` 并写入确认依据摘要；重审任务默认关闭。深度模式需要 Deep 运行环境和企业的编码模型，不可用时拒绝开启和受理（`deep_mode_unavailable`），不静默按标准受理。执行时每份待审文件以其 Suite 程序为起点开发一份任务专用程序；生成程序保存为不发布的 Suite revision，`deep_round_programs` 按轮次、文件和结果 attempt 记录，结果 coverage 的 `checker_execution.targets[].deep_review` 记录该文件深度复核完成或未完成（`degraded` 及原因）。开发失败或超时的文件执行原 Suite 程序。计费：受理时每份 500 点（`usage_events.charge='audit'`）；某文件的深度结果提交时，在同一事务另记 250 点 `deep_surcharge`，未完成深度复核的文件只计 500。模型可判 PASS 或 NG，但须有可定位证据；未知仍不变成 PASS。migration 0070 删除了旧 `analysis_mode` 列、`deep_rule_changes` 与 `checker_round_artifacts` 表（0072 因此用新名，避免每次重放 0070 时被删）。`request_fingerprint` 只覆盖文件版本/角色/规则绑定。SHA-256 只用于执行完整性校验，不替代 `file_version_id`。

新 Deep 受理将 `DeepExecutionPolicy` 的实际配置摘要写入既有 job 的 `executor_revision`；`protocol_revision` 仅标识传输协议。API、Worker 与 runtime 共用非密钥策略字段及计算方法，包含应用、模型配置、隔离与资源配置和显式标签。执行端在读取缓存、启动 guest 或模型工作前核对实际摘要；配置变化不能自动替换旧轮次的策略。原确认重放返回原回执，旧结果不补标或重写；旧标签本身不能证明配置冻结。模型配置摘要不保证远端权重不变或输出逐位复现。

新 Standard 受理在同一事务的现有 job 中保存 `execution_policy` 及 `standard-v1:` 配置摘要，并由同一 Round 和 attempt 读回。标识覆盖应用构建、实际 checker 模型选项及 OCR／转换工具配置；端点、任意 provider 选项和本地工具路径只参与摘要，不公开原值，不保存密钥。缺少构建身份时明确为空，不伪造 Git SHA。Worker 与 checker／OCR 共用启动时的 Settings，配置更换需重启进程；执行前不一致则终态失败，不读取原件、不调用模型或自动重排。原确认重放不重新计算策略。旧 `in-repo-engine-v1` 记录保留原标签与执行兼容，不补写历史策略。配置身份不证明远端工具／模型版本、派生缓存来源或输出逐位复现。

## 受理与重试

新轮准备复用草稿创建 API，可用 `request_id` 固定草稿身份，并在同一事务保存初始文件绑定与上下文。回执丢失先读原草稿；继续操作沿用原身份。重放仍检查创建人、租户、草稿当前对象权限与前轮权限；明确提供的文件绑定或上下文与既有记录不一致时冲突，不覆盖已保存内容。页面保留原轮每份文件的角色和规则，不因单一显示依据或资料信息编辑重新绑定。创建草稿不受理审核、不入队、不产生用量。此入口仅承载合法旧轮次；V3 Task 来源轮次不能经此路径创建旧式重审草稿，`review_failed` 仍是本任务内终态。

#163 D9 的关联重审通过 `GET /rounds/{id}/reaudit-inputs` 读取完整冻结文件组，读取本身不新建业务。用户明确新建 Task 后，沿用既有 `audit_drafts.predecessor_id` 和受理后的 `audit_rounds.predecessor_id` 记录真实来源。每个 Task 仍只受理一次；新任务不复制人工判断或机器结果。原文件可明确沿用原已发布规则，较新版由用户选择；替换文件用 `replacement_of_file_version_id` 明确对应原轮输入，并重新识别文件类型。新增文件、类型或客户范围变化需匹配。旧已发布版本的显式沿用校验不等于普通自动候选永不过期。

每个待审文件在受理时绑定明确规则版本；参考文件不得附审核规则。草稿保存可暂缺规则，受理不可缺。规则的 id/title/body 随每个轮次输入冻结，后续发布不会改旧快照。标准审核还冻结当时的条目执行映射：能映射到内置检查的条目进入机器结果，不能自动执行的条目进入 `coverage.unchecked`，不能把另一套内置检查项伪装成用户清单。

规则客户范围区分指定客户、明确不限客户和范围未确认。仅确认范围也保存新规则版本，可继承既有正文、原件及出处记录，不伪造重新核对条款的记录。旧版空客户列表不能推导为不限客户；已保存的明确范围声明随识别候选冻结。多候选冲突不按上传时间或另一个客户静默消解，须先确认依据再重新识别。

按 #163 最新 D1，Standard 将用户确认的条款按原顺序绑定到该类型、该 profile 的固定顺序检查器，不做条款全文或语义裁决。条款编号、分类和原文原样保留；超出可用检查器的条款仍标为未覆盖。此变更只影响新受理的映射，已有轮次继续使用其冻结的执行映射。

实际返回的 PASS/NG 决定计数、文件结论和报告。证据核验标记、定位、摘录及检查范围说明是独立信息；缺失不抹掉实际结果，也不阻止完整结果生成报告。真正缺少结果、UNABLE 或 ERR 仍不能生成完整 PASS/NG 报告。人工复核与机器结果分开保存。

相同租户、相同幂等键、相同文件版本/角色/规则绑定与前轮返回同一轮次；同键不同请求冲突。幂等键不是授权，返回既有轮次前仍检查对象权限。创建轮次、冻结输入和创建执行工作在一个 PostgreSQL 事务内完成。

Worker 用租约/attempt fencing 防止晚到结果覆盖当前结果。技术重试保持轮次不变；用户主动重审创建新轮次。

外部非幂等调用出现未知结果时先读回/对账，不盲目重发。数据库队列不声称外部模型或计费 exactly-once。

## 授权与用量

所有关联查询都检查租户和对象权限；UUID 不代表授权。既有企业共享审核轮次允许同租户成员查看和复核；新版 Task、其受理生成的 Round 和原件不因同租户身份自动开放，仍检查各自对象权限。上传准备继续使用创建者私有 Draft。报告分享独立鉴权，不反向开放私有任务或原件。登录不等于跨租户或私有对象授权。

用量只记录实际发生的业务事件和外部确认状态。企业成员读取同一份 tenant 用量账；Partner AI 上报仍由事件发起人认领结算，不能用查看者的 user token 代报。外部计费/权益未确认时保持未知或待对账，不根据本地 job completed 自动认定已扣费。只有 pending 可领取发送权；unknown 保留待对账，不允许再次上报。

`external_confirmed_at` 记录 PPAP 保存成功外部回执的时间，不代表飞书实际扣费时间，也不决定跨月统计归属。历史成功记录缺少该时间时保留空值，不以受理或请求发送时间回填。

`GET /audit-usage` 将同一轮次、文件版本的免费/付费分片投影为一笔 500 点费用，读取不发起外部上报。消费次数、已扣与待扣均按冻结轮次的受理时间归入 `Asia/Shanghai` 受理月，不按账本写入或补扣时间改月。补扣只更新原月份的结算，不新增消费；技术重试保留同一费用身份。明细按受理自然日筛选，与固定当月汇总分开。文件档案与审核次数只在现有权限及真实飞书身份关联成立时提供；撤权不删除企业费用。历史汇总或不完整分配单独提示，不猜测拆成文件费用；存在这类当月记录时，消费次数保留未知。

飞书用量回执不是订单号或实际扣费凭据。实际付费凭据单独保存在原用量分片的 `debit_order_id`、`debited_at`，必须成对存在；不从上报回执时间回填。尚未接入可验证的实际扣费凭据来源。未取得可核对的订单时保持空订单；成功上报仍显示实际扣费待对账。回执未知不表示已扣或确定未扣，当月存在这类费用时，已扣／待扣合计保持未知。免费额度已分配部分计入已扣；确认尚未上报的付费部分计入待扣；有完整实际扣费依据后，付费部分由待扣转为已扣。免费额度沿用当前配置、cut-over baseline 和现有消耗，不重置权益。

收费开启时，新建任务与新受理均由服务端读取飞书 AI 开关和原发起人的额度；开关开启且免费或付费至少一池有正余额即可，不要求足额覆盖全部文件。受理持有同租户/用量项目的事务锁直到试用分配、冻结与入队提交；该锁不承诺冻结飞书远端余额。受理事务按匹配且选中的待审文件数 × 500 点生成用量，参考文件不计费。新记录按轮次、冻结文件版本与试用/付费分片唯一，文件与规则依据通过该轮次的冻结输入追溯；同一文件的两种分片是一笔业务费用的分配，不是两次审核。历史汇总记录保留空文件版本，不猜测拆分。客户端不能指定消费点数或确认状态。显式重审产生新的消费，技术重试和受理回放不产生。原受理回放不再次查询额度；PDF/ZIP 失败恢复重新检查额度，但只恢复原工作、不增加审核费用；已生成报告读取与分享不检查欠费。

上报在鉴权准备后原子领取发送权；发送后超时或响应不明确标为 unknown，不提供自动重发。reporting 超过 120 秒展示为 unknown，原发送者的明确晚到响应仍可确认。收费开启时 API 后台从同一账本选择 pending，使用原发起人仍有效的授权；缺授权等待本人重新登录，缺额度等待充值，再继续原费用的首次上报，不依赖用量页访问者。收费关闭时后台和手动入口都不发送付费用量。旧 UAC 的 `ai_item_uses/search` 是飞书查询商户本地上报账本，不是商户查询飞书实际扣费结果，不能用它消除 unknown 或生成扣费订单。未接入可验证的外部扣费读回接口，因此不声称自动对账。生产切换前须确认客户既有试用权益，不能把本地默认试用额当成重置授权。剩余试用 = 配置额度 − 已确认 cut-over baseline − current PPAP 已消耗试用。Partner AI 付费余额仍以飞书配额为准，不被本地试用账覆盖。
