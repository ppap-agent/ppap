# Deep 产品设计：一个可澄清、可改进的审核工作区

这是未来产品的目标设计，允许重构 UI、应用接口和服务边界。当前页面、数据库形状、SDK、网页批准及 ASGI 转发仅是迁移起点，不是产品原则。算法核心见 [DESIGN.md](DESIGN.md)；现有 MCP 行为见 [docs/MCP.md](../../docs/MCP.md)。本文没有宣称目标能力已经实现。协议核对日期：2026-10-29。

## 1. 产品承诺

**给出规则和资料，得到有依据的判断；遇到真正需要用户决定的问题，给出清楚的选择；用户确认后，直接看见分析如何改变。**

用户使用一个持续的审核工作区。规则及补充说明、文档、解释问题和分析结果都在同一上下文中。Web、MCP 和支持富交互的宿主是平等入口，不要求用户先理解 ontology、MCP 或执行轮次。

体验的主线是“提交资料 → 查看判断 → 澄清歧义 → 得到更新结果”。规则管理、文件浏览和运行记录服务于这条主线，不把内部模块逐个变成客户导航。

产品必须做到：用户在任一时刻都能回答“发现了什么、为什么需要我、我的操作会改变什么、现在是否完成”。界面简洁不能以隐藏未知、冲突或实际作用范围为代价。

## 2. 未来用户旅程

### 准备：给出依据，直接开始

在一个工作区中加入规则与文档，核对系统理解的规则适用对象，查看本次明确使用的补充说明，然后开始分析。文件关联和布局可以由系统提出，用户不手工配置 ontology 或解析流程。

输入不完整时，只指出缺少什么及其影响。可以分析的范围先开始，不把完整配置表作为所有用户的起点。

### 分析：问题在有用的时候出现

进度围绕实际工作表达，例如“正在核对工序对应关系”。同时显示已经得到的判断和真正需要用户处理的解释问题。

一个歧义可能影响很多检查，产品按含义合并成一个问题。优先呈现影响大的问题，并给出为什么现在值得回答；不按每个单元格或每次模型调用打断用户。

用户可以立即处理，也可以让其余分析继续。尚未处理的问题不会被默认回答；分析结束与解释全部确定是两个事实，可以显示“分析已结束，2 项解释待确认”。

### 澄清：在证据旁边作决定

打开问题后，用户同时看到：

- 原规则及本次已确认补充说明；
- 定位后的原件，必要时并排显示多个文件；
- 系统当前理解、少量候选及各自依据；
- 每个选择将影响哪些对象、规则和判断；
- 拟写入的补充说明或规则变更，以及适用范围。

默认推荐可以突出，但不能自动提交。用户可以选候选、纠正解释，或说明所有候选都不成立。复杂规则修改可以直接编辑正文，系统展示实际变更及影响，不要求把新含义硬套进已有选项。

### 应用：一个明确动作完成一次意图

处理一个问题时只保留一个主要提交动作：普通解释为“确认解释并继续”，改变审核要求时展开原要求/新要求，并改为“修改规则并重新分析”。次要动作是“仅保存说明”或“稍后处理”；人工判断使用独立入口。用户无需先学习反馈分类，但必须看见实际作用。按钮附近说明内容、范围及是否开始新的计算；发生费用时显示本次执行的计费范围。

用户已经核对了完整内容、范围和执行效果时，一次明确提交可以完成保存与分析。不为了沿用现有实现，额外要求“选答案 → 存答案 → 再批准 → 再应用 → 另找重审”。

保存说明而没有选择重新分析时，不启动新计算。若保存成功但新分析未启动，界面明确显示这两个结果，并提供读回或恢复入口，不能笼统声称全部完成。

### 结果：看见改变，继续前进

输入改变后开始新的计算。工作区保持连续，用户不用重新上传全部资料或重新建立任务。可复用仍适用的观察与计算，但每次结果必须对应明确的输入。

提交成功后，当前问题显示“解释已应用，正在重新核对”。受影响的旧判断标为“此前结果”，不再冒充新输入下的当前结论；已经失效的旧问题退出待处理队列。保存成功但启动结果未知时，显示“说明已保存，分析是否启动正在核对”，下一步读回原操作，不再次保存。

新结果在同一位置说明采用了哪些补充说明、改变了哪些判断、还有哪些缺口。迟到的旧计算结果只更新其所属分析，不替换当前依据下的结果。此前结果仍可对照。确认解释不保证结果变成 PASS。

## 3. 三种用户意图，清楚区分

| 用户意图 | 实际改变 | 提交前必须看见 |
|---|---|---|
| 确认或纠正解释 | 在附录中明确一个概念、关系别名或限定文档的映射 | 问题、证据、解释、范围、是否继续分析 |
| 修改审核规则 | 改变标准、适用条件或要求 | 原要求、新要求、适用对象和预期重算范围 |
| 人工改判 | 增加人工判断及理由 | 原机器结论、人工判断与依据；机器结果不被覆盖 |

人工改判的理由可以成为一次规则修改的起点，但系统不能自动推断用户已同意修改标准。类型别名、实例对应与审核通过也不能相互代替。

跨文件认定同一对象后，仍展示各文件各自的表达与取值，特别是冲突。用户确认一个文件中的解释，不会被自动推广到其他文件；需要扩大适用范围时，用户能明确看见并选择。

## 4. UI 信息结构：围绕当前判断组织

目标是一个审核工作区，不受当前路由或页面分割限制。

桌面默认只维持一个主要处理对象。顶部给出工作区名称、当前输入说明和真实分析状态；紧凑的问题导航可展开。处理问题时主要提交动作只出现在当前判断区域，顶部不再提供竞争按钮；没有待处理对象时，工作区可显示“开始分析”等主动作。主要工作区域是“证据 + 判断”：原件占据阅读空间，旁边呈现当前问题、候选、影响和变更。跨文件比较时，证据区域可并列两个相关片段，不要求用户在文件页来回记忆。

```text
当前资料与规则                    分析状态 / 待处理数量
──────────────────────────────────────────────────────────
问题导航（可收起） │  当前相关原件 / 跨文件对照  │ 当前判断
                  │                            │ 候选与依据
                  │                            │ 范围与变更
                  │                            │ 确认并继续
```

该布局表达信息关系，不固定为永久三栏。没有待处理问题时，主区域展示审核结论及覆盖范围；需要较长规则编辑时，展开编辑区并保留证据和影响入口。常用路径不依赖层层弹窗，也不把每个字段包装成卡片。

| 意图 | 目标交互 |
|---|---|
| 扫描问题与影响 | 紧凑列表；按同一语义歧义分组，显示状态和影响范围 |
| 比较候选 | 少量互斥选项直接展示，可用 RadioGroup；每项依据就在附近 |
| 给出新解释 | 短文本输入，允许“都不符合”；较长规则修改进入可对照的编辑区域 |
| 选择范围 | 明确说明作用于本文件、本次资料或满足具体条件的后续资料；不用模糊的“记住我的选择” |
| 核对实际变更 | 内联自然语言预览，标准修改显示前后差异 |
| 提交 | 一个名称准确的主要按钮；保存未知、冲突和执行失败在原上下文解释并恢复 |
| 查看技术依据 | 按需展开来源和执行细节；客户主流程不展示 ontology ID、协议 key 或 token 日志 |

移动端跨文件判断默认将当前对应的两段证据上下成对排列，标明各自文件与位置，并保留一句待判断问题。用户可以进入任一原件查看完整上下文，返回后仍回到该证据对及已选候选。需要切换“解释 / 证据 / 变更”时保留候选、草稿和阅读位置，不让用户在整份文件 A/B 之间凭记忆比较。范围与提交摘要清楚可达，不把桌面三栏缩成三条窄列。

键盘可完成选择、编辑、查看证据和提交。关闭面板只关闭当前视图；不确认候选、不取消分析。焦点回到触发位置，刷新或从其他入口回来仍能找到同一个业务问题。

### 状态必须说真话

计算与用户反馈是两个维度，例如“分析中 · 3 项可确认”“结果已生成 · 2 项解释未确定”。界面至少区分：待确认、已编辑未提交、保存待核对、已保存待新结果、新输入分析中、新结果可用。

问题或候选已经变化时，旧回答不能被静默应用。结果可阅读、分析已结束和报告已生成分别表达；不以漂亮的完成动画掩盖 UNABLE、错误或覆盖缺口。

## 5. 目标架构：MCP 原生，计算核心独立

```text
Web / 富交互工作区 ─────────┐
                           ├─→ Audit Application ─→ Deep Core
MCP 客户端 / MCP Apps ──────┘          │              rules + documents
                                      │                    │
                               唯一的业务事实来源 ← 结果 / Hole / 候选
                                      │
                               明确的规则变更与新计算
```

MCP 与 Web 直接使用同一应用语义。MCP 不必穿过为某个网页设计的 HTTP 路由；Web 也不必通过 MCP 才能调用核心。共享的是身份与对象授权、输入组装、规则变更、运行、反馈和结果，而非某个运输协议或框架。

Audit Application 拥有工作区内的输入、运行和反馈事实；Deep Core 只对明确的 rules + documents 计算。规则正文与已确认附录属于 rules，ontology 与逻辑文档仍是中间产物。客户端会话、历史聊天和协议能力不是隐藏的业务输入。

工作区是统一的产品上下文，替代重复的任务/反馈视图，不在旧业务事实旁再建一套同样的台账。模块可以同进程部署，也可以按执行隔离、负载和发布需要拆分；当前进程边界不是原则。无论部署怎样变化，审核输入、确认与结果只有一个业务拥有者。

### 最小应用操作

以下是目标语义，工具名为设计名称，不表示已经实现。

| 操作 | 职责 |
|---|---|
| `start_analysis` | 对明确的 rules + documents 开始分析；首次分析与独立重新分析共用该操作 |
| `read_audit` | 读取工作区输入、实际进度、结果、问题、已保存说明及其应用情况；支持范围化读取 |
| `apply_rule_change` | 以稳定的业务操作 ID 应用用户确认的正文/附录变更，可关联某个澄清问题；显式指定 `save_only / save_and_analyze`，返回实际保存与分析结果引用 |

“回答问题”是 apply_rule_change 的一种入口，直接修改规则也使用同一语义。它校验问题、最终内容、范围与权限，不先保存一份答案、再复制为另一份规则事实。取消分析是独立明确的用户意图，协议请求断开不等于取消业务计算。

该业务操作 ID 覆盖这次保存及可选的新分析，不以整个工作区或协议 Task ID 替代。Web 提交、MRTR 重发或 Tasks 回答均关联对应的同一操作；重复提交读回同一保存与分析结果。部分成功后恢复原操作，不重新执行整个组合。

MCP 应原生提供这些业务能力、可读取的依据和 Elicitation。无需把每个读取器、ontology 修改或求值步骤都变成公开工具；外部 host 不承担内部覆盖统计和判定一致性的责任。单独部署 Deep MCP 入口是允许的，但应调用同一应用与核心，不能复制业务事实或变成平行审核引擎。

## 6. MCP 原生的确认体验

### 简单问题可在宿主内完成

在支持 Elicitation 的客户端中，完整展示问题、候选依据、最终补充说明、范围和执行效果。用户明确提交后，服务端校验当前委托权限与所针对的内容，即可保存附录；若动作明确包含继续分析，也可以启动新计算。

**不强制跳转网页进行第二次批准。** 当前产品的网页确认是迁移机制，不是未来交互原则。协议 accept 也不是无限授权：只能执行已展示且用户提交的内容，不能扩大到共享规则、其他文件或额外分析。

服务端关联自己提出的问题、候选及最终内容，记录实际提交者、委托和交互来源。模型直接拼出的工具参数不能冒充标准 Elicitation 中的用户响应；普通工具方式写入则遵守该调用明确授予的业务权限。不能把协议回应夸大为独立验证过的人类签名。

### 复杂判断使用足够的界面

需要图形、多个原件或大段规则修改时，使用支持的 MCP Apps 或 Web 工作区，并保持同一问题上下文。选择界面由用户需要比较的信息决定，不由当前框架方便程度决定。

URL 跳转后，页面可以直接提交同一应用操作并显示真实保存/执行结果；MCP 客户端随后读回。无需保留“网页只能批准、必须返回客户端重放才执行”的旧限制。服务端仍将用户最终编辑后的内容与提交动作绑定，不能批准一份内容却执行另一份。

### 协议动作的含义

- `accept`：处理用户在这次交互中明确提交的内容，再校验授权、范围和实际业务效果；URL accept 仅表示进入外部交互，完成情况由应用读回。
- `decline`：用户拒绝提供这次信息，缺口保持未解。“所有候选都不对”应是正常提交的一种内容，不用 decline 代替。
- `cancel`：关闭交互，允许以后继续；不默认采纳候选，也不等于取消整个审核。

不支持 Elicitation 的客户端仍能读取问题，在明确的 Web 入口继续。没有 Apps 的客户端不强行接收富界面。能力不足是入口选择问题，不改变审核语义。

## 7. 协议依据与目标版本

以下为截至 2026-10-29 核对的官方事实。目标协议是 **2026-07-28**；客户端兼容通过适配与明确降级处理，旧 SDK 不决定目标产品能力。

| 能力 | 官方语义与设计影响 |
|---|---|
| 基础协议 | latest 指向 2026-07-28，逐请求声明版本/能力并使用 `server/discover`；不能以旧初始化流程冒充新版。[规范](https://modelcontextprotocol.io/specification/2026-07-28)、[版本兼容](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)、[变更](https://modelcontextprotocol.io/specification/2026-07-28/changelog) |
| Elicitation | 提供 form/url 及 accept/decline/cancel；模式取决于客户端声明。受限表单适合选择与短说明，URL accept 不证明外部操作完成。[规范](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation) |
| MRTR | 返回 `InputRequiredResult`，用 `inputResponses` 重发原方法；只有服务器给出了可选 requestState 才原样回传，JSON-RPC ID 使用新值。[MRTR](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr) |
| Tasks 扩展 | 官方 `io.modelcontextprotocol/tasks` 处理异步工作，`tasks/get` 读取，任务中回答走 `tasks/update`，不重发最初的 tools/call。[Tasks](https://tasks.extensions.modelcontextprotocol.io/specification/2026-07-28/tasks) |
| MCP Apps | 独立扩展，可在支持的 host 内承载工具关联的沙箱界面；支持 MCP 不等于支持 Apps。[Apps](https://modelcontextprotocol.io/extensions/apps/overview) |

短操作采用 MRTR 收集必要输入；长分析以 Tasks 扩展作为支持客户端上的原生体验。任务内需要回答时使用该扩展的输入机制。没有 Tasks 支持时，返回应用分析引用并允许读取同一状态；不把长时间 HTTP 请求或模型会话作为业务生命周期。

协议 Task 代表一次已授权的应用交互操作，不强制等同于一次 Deep 核心计算。其中每次计算都有独立的输入与结果引用。任务内的问题只有明确展示“应用修改并继续分析”且用户选择这一作用时，才可通过回答启动新计算；最终结果说明实际采用的输入。界面可以呈现为“继续分析”，但不能隐式修改先前结果的依据。恢复协议请求不重复发起分析；Task 的 completed 不代表 PASS，update/cancel 回执也不代表工作已经完成或停止。

业务 Hole 与协议问题 key 分开：同一 Hole 的含义、候选变化或回答后再次提问时使用新协议 key；任务内旧 key 不分配给另一问题。传输 ID 可变化，业务操作仍可去重与读回。若使用 requestState，它是绑定调用者和原操作的可验证引用，不是授权凭据。

表单不收集凭据；URL 使用正常授权，不携带能冒充用户的预认证访问能力，跳转明确展示目标。见 [Elicitation 安全要求](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation#security-considerations)。这些保护可以由新的认证与提交设计实现，不要求沿用当前网页批准页。

## 8. 必须保持的产品事实

- 每次分析使用明确的 rules + documents；已确认附录显式进入 rules。系统建议、历史聊天和上次结论不能偷偷成为输入。
- 操作权限覆盖当前用户、对象和范围；确认的是实际提交内容，不能以一次局部确认扩大授权。
- 模型解释、用户补充、原文事实和人工判断可区分；引用有效不等于解释一定正确。
- 未知与覆盖不足不冒充 PASS 或已确认违规；跨文件冲突和重复证据不因合并对象而消失。
- 用户修改输入后，旧结果仍对应旧依据；新的结果必须经实际计算生成。
- 同一操作重复提交不会重复保存或开始分析；未知结果可读回，不诱导用户反复新建操作。
- 用户可离开、关闭客户端或从另一个入口回来；已保存的工作和问题不依赖原连接存活。

这些是真正的约束。页面数量、服务部署、SDK、数据库字段、网关方式及批准 UI 都可以为更好的产品重新设计。

## 9. 重构基线与落地边界

本节表格保留设计时基线 `3b4c66c9` 的迁移对照。当前已有规则附录、逻辑对象、类型化 Hole 和 Web/MCP 的首个实际反馈闭环；准备入口为 `/audit?prepareDeep=1`。当前运行边界与验证方法见 [ARCHITECTURE](../../docs/ARCHITECTURE.md) 和 [DEVELOPMENT](../../docs/DEVELOPMENT.md)，不以此声称任意规则、布局或真实模型准确率均已验证。

| 已核对现状 | 到目标的实质差距 |
|---|---|
| 现有 PPAP MCP `prepare_task` schema 已接受 `analysis_mode=deep`，有 confirm_task/get_task/get_round、round Resource 和总结 Prompts | 已有 Deep 业务入口，不等于已经有原生语义反馈；需以目标应用操作完善或重构接口 |
| 当前 MCP 经进程内 ASGI 转发 Product HTTP routes | 可重构为 MCP 与 Web 共用 Audit Application；必须把真正的授权与业务校验下沉到共同边界，不能绕过校验 |
| 当前确认是自定义 confirmation_required + 登录网页批准，网页不执行原操作 | 目标支持宿主内完整确认、Web 直接应用，以及一次明确的保存并分析；需重构确认内容绑定与操作执行合同 |
| FastMCP 3.4.0 / MCP SDK 1.30.0，实际 SDK 最高协议为 2025-11-25，Tasks 关闭 | 整体验证并升级 SDK、服务、网关/代理及客户端；stateless_http 不是新版兼容证明，不应保留 tasks=False 作为产品原则 |
| Web 当前入口为 audit/native-main → intake → workspace → review-content，已有原件对照、人工复核及重审 | 可作为组件和行为参考，目标工作区可以重组路由、布局和交互；旧页面不决定新旅程 |
| Deep 结果仅向产品投影 findings/coverage，缺少 Hole 与候选合同；规则归一化会丢弃未声明 appendix | 贯通核心输出、结果保存/读取、语义确认、规则正文/附录与新计算输入，不能只改页面或加一个 MCP 方法 |

主要源码入口：[mcp_tools.py](../../apps/api/src/api/mcp_tools.py)、[mcp_server.py](../../apps/api/src/api/mcp_server.py)、[mcp_gateway.py](../../apps/api/src/api/mcp_gateway.py)、[auditor.py](src/agent/auditor.py)、[intake.tsx](../../apps/web/src/audit/intake.tsx)、[workspace.tsx](../../apps/web/src/audit/workspace.tsx)、[review-content.tsx](../../apps/web/src/audit/review-content.tsx)。

当前 `/mcp/deep` 使用窄协议适配，并与 Web 共用规则变更应用操作。回环 HTTP 验收使用独立客户端、真实 OAuth、PostgreSQL、Worker、guest 和求值器；只在模型、身份供应商和对象存储边界使用受控输入。外部宿主兼容及真实模型理解质量分别验证。

迁移可以保留兼容入口，但目标只保留一套业务语义和事实。替换旧路径时一起迁移调用者、权限校验与测试，不让兼容层成为永久的第二套产品。

## 10. 产品审查与验收

用一次完整演示审查，而不是逐页展示功能清单：

1. 用户提交规则与多份文件，直接开始审核。
2. 系统找到真实歧义，在相关原件旁给出可理解的候选和影响。
3. 用户纠正解释、明确范围，核对一句自然语言补充说明，一次提交继续分析。
4. 界面诚实显示新输入正在分析，随后说明什么变了、什么仍未确定。
5. 用户关闭工作区，再从 Web 或 MCP 回来，仍能理解同一个问题、已作出的决定与结果依据。

若必须讲解内部架构才能完成上述流程，或用户反复确认同一内容、来回寻找证据、猜测保存是否生效，产品设计尚未通过。

验证必须包含：新规则与旧 checker 无关的概念解释；跨文件冲突；确认范围不泄漏；所有候选均被否定；普通确认与标准修改/人工改判区分；一次保存并分析的成功及部分失败；过期问题与权限变化；关闭/刷新/跨入口恢复；重复请求与读回；不同协议能力的实际路径；手机对照、键盘和焦点。

体验评估同时看判断质量和用户负担：澄清前后未知比例、需要用户决定的问题数、重复确认次数、找到原文的操作数、完成一次纠正的时间、误应用范围、重试与 token 用量。局部确认不自动成为整轮审核 gold。

实现与验收沿用现有 owner：`tests/e2e/test_deep_feedback.py` 验证真实浏览器旅程，`tests/integration/product/test_mcp_deep_feedback.py` 验证独立 HTTP 客户端与能力组合。候选提交、实际命令、数量与证据边界记录在 #223–#225；测试回答不作为人工确认或训练金标。外部 host 对协议、Tasks、Elicitation 与 Apps 的支持仍按实际操作验证。
