# PPAP 语义审核

交付可复核的规则结果。本轮已发布的有效规则正文决定审核要求；原始附件只用于溯源。此 Skill 提供读取、表示和执行方法，不内置某客户的审核标准。

## 选择阶段

- **编译规则**：只加载规则来源和 `references/rule-plan.md`，按调用方的规则计划 schema 返回结构化结果后结束。输入只需规则文件，不需要供应商待审文件。计划的条件不含当前供应商的缺列、坐标或检查结论。
- **执行已有计划**：用户提供或已确认的计划是本阶段输入。核对其来源版本，直接进入步骤 2；仅对变化或歧义影响的条款回看原文。复用已确认且源哈希匹配的快照/绑定，检查必要的有效性条件后执行。
- **首次完整审核**：先执行步骤 1 并保存计划，再进入步骤 2。需要稳定阶段边界或批量复用时，将编译和执行分成两个独立调用；第一调用只提供规则来源，第二调用提供计划和待审文件。

## 工作顺序与产物

### 1. 编译规则，先确定检查什么

读取 [规则计划](references/rule-plan.md)，把本次生效规则写为 `rule_plan.json`。逐条保留来源、前置条件、数据范围、判定表达式、缺失与空集合处理及未解决歧义。

- 以本轮发布的有效正文为准。`kind=published_rule` 的 JSON 来源包含完整 `rule_body.rules`，且 `clauses` 与之相同；每个有效条款都必须编入计划。`published_clause` 只引用 `clause_id`，不表示原件 DOCX/PDF 坐标。原始附件只能作来源说明，不能覆盖已发布修订。
- 区分字段概念与强制格式。通常“某列”指业务字段，映射可跨语言、换行和多层表头；原文明示“包含有效字符”、指定精确标签或拼接格式时保留这个约束。歧义写入计划，分别说明严格文本解释和语义解释的影响。
- 规则里的示例用于解释谓词，不作为待审文件内容或额外必填条件。
- 先按当前 `QueryProgram` 的真实能力选程序：它只支持同一记录上标量谓词的 AND，以及 `forall/exists` 量词。条件筛选、缺少必需列即 NG、跨文件关联等任一规则分支无法由此完整表达时，整条规则使用 semantic program。`scope` 只说明范围依据，不会执行筛选。
- 完成条件：每个生效规则都有唯一 ID 和表达式，规则原文要求的全部条件都有去处。此时尚不依赖某供应商行列位置。
- 每条计划填写 `empty_scope_status` 与 `empty_scope_basis`。有效正文明确允许零适用对象通过时才写 `PASS`；明确规定不适用时才写 `NA`，并在 basis 说明来源条件。原文未给空范围结论时写 `UNABLE`，说明未决歧义。字段、文件或表缺失已被原文规定为 NG 时，仍按该前置分支判 NG。

### 2. 一次读取，建立当前文件的映射

先读 [通用表格读取](references/table-reading.md)。优先使用 manifest 中已生成的快照，按需查看片段。只有缺少所需观察时才用 document_tools.py 补充读取。命令见 [工具用法](references/commands.md)。

为每个目标表写 `bindings/*.json`：文档身份、表区、表头行、正文行、排除行及理由、业务字段对应的物理列与映射依据。坐标是本次观察结果，不是 Skill 的固定配置。相同字段在同一文件的所有规则中复用同一个映射。

- 合并区域只在真实合并范围内继承锚点值；普通空白保持空白。
- 保留多层表头路径，区分父标签和子标签。通常正文在完整表头之后；修订卡等反向排列可位于表头上方，按记录结构确认方向。
- 用正文结构与上下文确定边界；排除标题、重复表头、修订履历和脚注时记录理由。不能为了去掉违规空值而排除数据行。
- 字段标签存在和字段值存在分别记录；数字 `0` 与 `False` 不是空值。
- 文件组来自提交上下文或身份依据。身份缺失时可提出候选关联，涉及该关联的结论保留其不确定性。
- PDF：先使用文本及几何证据；表格关系、勾选或图像内容无法从文本确定时渲染相关页。按需读 [PDF 建模](references/pdf-reading.md)。

完成条件：规则需要的数据已映射到来源，缺列、空值、解析未知三种状态明确分开。多个规则共用的数据只提取一次。

### 3. 执行计划，保存反例和覆盖数量

确定性条件用 SQL、[窄字段检查](references/commands.md#局部字段检查)或短 Python 计算；语义条件用有来源的窄判断。将查询保存为 `queries.json`，执行结果保存为 `query_results.json`。语义判断保存对应记录、依据和未解决项。

- `FOR ALL`：保存总数、适用数、违规数、未知数。NG 可以由一个确证反例支持；PASS 需要覆盖完整集合。
- `EXISTS`：保存命中记录；全量扫描后才能声称不存在。
- `SUBSET / JOIN`：使用 semantic program，确认文件组和连接键，保留未匹配项；注意重复项和一对多关系。
- 前置条件成立后才解释查询。缺少所需列、未知分类或空范围，不得因为查询返回零行就自动通过。
- semantic proof 的每条 `records` 标明 `role`：`prerequisite` 是文件、表、列、身份、范围边界等前置观察；`applicable` 是本条实际判定的业务对象（正文行、跨文件对应项，或本身受审的页眉/存在性要求），填 `applicability_basis` 说明如何满足触发条件并引用来源；`excluded` 是已核实不触发的候选对象，填 `exclusion_basis` 与来源，其状态为 `NA`，触发条件仍未知时为 `UNABLE`。前置观察不填两种行级 basis。`scope_basis` 写明候选范围、适用集合、排除项及未知项的依据；前置与排除记录均不证明适用集合非空。
- 零条 `applicable` 时，先保留已证实的前置 NG 或未知 UNABLE；其余按计划的 `empty_scope_status` 处理。`NA` 需要可核对的适用性依据。只有计划依据有效正文明确授权时才可为空范围给 PASS。结构字段只使这一决定可审查，不自动证明条款解释正确。
- `PASS / NG / UNABLE / NA` 遵守规则计划的分支。原文明确规定缺资料 NG 时执行该规定；解析失败或未解决的语义影响结论时给 UNABLE。若有效规则本身未说明空范围或触发条件的结论，UNABLE 的 `diagnostic` 用 `rule_ambiguity`，不要用 `parser_unknown` 冒充解析失败。NA 需要适用性依据。
- proof kind 必须与计划的 predicate kind 相同。审核阶段执行既定 query 或 semantic program，不切换程序类型，也不借 `scope` 文本补充 query 过滤。`trace.bindings` 只包含实际被 QueryProof 引用的 binding。

优先批量查询、聚合和打印反例。完整结果留文件，避免反复将整个文档打印进上下文。遇到读取失败，只切换与失败原因相关的读取方法。

### 4. 完成验收

按 [执行产物](references/execution-trace.md) 返回 AuditTrace：被查询引用的 bindings，以及每个目标/条款唯一的 query proof 或逐记录 semantic proof。可信代码从这些事实派生公开报告、状态、计数和引用。

若调用方提供先前的 schema-valid AuditTrace 和校验反馈，本调用是一次受限修复：复用已有 snapshots 和 plans，按反馈修正并重新返回完整 AuditTrace。计划已决定 proof kind；修复调用不能在审核阶段改换类型。一次修复仍失败时保留真实失败，不自行递归重试。

通过调用方指定的结构化输出 schema 返回执行记录，并为每项保留规则 ID、实际覆盖范围和限制。语义观察保存原始判定理由及决定性来源；公开报告直接使用这些理由与来源。证据使用 output schema 中的 typed locator，不自行生成 quote。段落、页、表和 PDF block 都从 1 开始；每个 UNABLE 观察必须给实际原因的结构化 diagnostic；已知观察不填 diagnostic。检查目标文件与规则组合无遗漏、重复或越界；最终结论能回指计划和查询/语义判断。

在时间或轮次耗尽前返回完整结构化结果；重读 `rule-sources.json`、`clauses.json`、`obligations.json`、`plans.json` 和 `documents.json` 恢复完整范围。未完成的条款给 UNABLE 并写原因。结束时报告真实完成范围。CLI 成功退出、合法 JSON 和有证据字段都不等于审核完成或证据正确。

## 经验复用

规则计划按规则源哈希保存；字段映射和读取脚本按确认后的文档族保存。规则变化时重编译受影响条款；新文件复用映射前验证必需字段、多层表头关系、正文边界和身份关系仍成立。固定读取结果不能代替对新文件的验证。
