# Typed Evidence Hole：局部字段绑定实验

研究问题：能否用少量明确的返回类型，让多条规则共享原件解释，减少重复读取，同时保留证据来源、未解决项和未来训练所需的数据？

这是可丢弃的研究原型。实验已执行，不接入产品运行路径，不修改原件或业务标签。结论是：**优先研究一次共享绑定；先分清源记录范围与规则适用范围，再决定是否需要多阶段求解。** 当前证据不支持引入通用依赖图、动态调度器或模板资产平台。

后续运行已按用户要求切换为 `grok-4.7`、reasoning=`medium`。两个实验入口共用 `hole_experiment.py` 中的模型与推理强度常量；`.env` 仅提供接口与凭据。下面的 24 次历史实验及统计仍属于 `grok-4.6` / `low`，不因配置修改而改写。

已用新配置完成 1 次继峰 shared 绑定验证：服务端返回 `grok-4.7-build`，结构有效，四项绑定均与本次参考一致。记录在 `output/grok47-medium-smoke-01/`；这不是完整对比实验的重跑。列探测会复用输入目录中的旧结构提案，因此若输入旧实验目录，就仍包含旧模型的上游结果。

## 最小架构建议

```text
RulePlan（规则、需要的字段、缺失时如何处理）
    ↓
Binding（原件记录、字段位置、来源与未解决项）
    ↓
AuditResult（按规则计算、逐项结果、覆盖范围）
```

Typed Evidence Hole 是 Binding 中尚未确定的有类型字段，不必成为第四个运行子系统。开始只区分两种返回类型：记录集合返回行引用，字段绑定返回列或单元格引用。不要让一个对象同时接受 rows 和 columns，再靠文字约定其中一个必须为空。

多条规则对同一原件、同一语义字段的需求合并成一次求解；类型不同不等于必须分别调用模型。模型提出绑定，代码从冻结原件读取值并执行可计算的规则。若局部证据不足，保留该字段 unresolved；需要读图片时才扩大局部读取。政策未定义不能由模型补全。

这里有两条不能省略的边界：

- **源记录集合不随当前规则的数值需求而缩小。** “符合检具”可以是源记录，是否适用某条数值规则应另行判断。非数值不能自动变成 NA；政策未知不能自动变成 PASS。该项未解决不妨碍其他有充分证据的项继续执行。
- **引用存在、类型有效、字段含义正确、记录覆盖完整是不同的事实。** 一份 Binding 可以复用，但共享错误也会影响多条规则。需要独立标注来验证含义和覆盖；再调用同一模型复述理由不能替代它。

已有实现可复用：`semantic/models.py` 的 RulePlan 和来源地址，`semantic/trace.py` 的 Binding，`semantic/document_tools.py` 的原件读取，`semantic/checker_tools.py` 的局部确定性计算。这个原型没有改动这些模块。原型的多列范围也不能直接替换当前字段绑定接口，仍需明确合并单元格与实际值位置。

## 已执行的实验

2026-10-27，配置模型名 `grok-4.6`，reasoning=`low`，每次输出上限 2400 tokens，超时 90 秒，无自动重试，`store=false`。主实验 20 次请求，发现问题后增加 4 次定向探测，共 24 次。所有调用均有用量记录，没有失败后换分母。

使用仓内 3 个 XLSX 原件和 1 个坐标平移观察，共 **2 个模板族**：

| 输入 | 观察范围 | 特征 |
| --- | --- | --- |
| 继峰原件 | 表单 A44:M51 | 表头在数据下方；D45–D49 有未读图片 |
| 上海亚大原件 | Sheet1 A33:M38 | 合并表头；第 37 行为“符合检具” |
| 继峰错误原件 | 表单 A44:M51 | L50=767，超过上界 766.9 |
| 继峰平移观察 | 表单 C51:O58 | 坐标加 7 行、2 列，内容不变 |

平移仅变更观察中的坐标、合并范围和图片锚点，不是工作簿转换。原件名称和 SHA-256 保存在本地参考文件中。继峰原件、错误变体和平移变体属于同一来源组。模型只收到选定范围的原生值、合并范围和图片锚点，未看到图片内容、外部范围、参考坐标或人工业务标签。输入已裁去供应商和人员信息所在区域，但仍包含原件业务数据。

三种策略使用相同观察及原规则：

- `independent`：R3 公差/判定与 R5 同行重复值分别提出所需绑定，每例 2 次。
- `shared`：两条规则共同提出记录、规格、实测值、判定四项绑定，每例 1 次。
- `staged`：先表头和记录，再字段绑定，每例 2 次。

| 策略 | 请求数 | 输入 / 输出 tokens | 累计请求秒数 | 共同项与参考一致 | 全部共同项一致的样本 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 各规则独立 | 8 | 25,196 / 8,431 | 127.6 | 15/16 | 3/4 |
| 一次共享 | 4 | 12,838 / 4,021 | 61.4 | 16/16 | 4/4 |
| 先结构后字段 | 8 | 26,797 / 5,582 | 83.1 | 12/16 | 2/4 |

共同项是每例的 records、specification、measured、judgment；独立策略中重复消费者必须都与参考一致，该项才记为一致。结构无效的返回计为不一致。参考来自本次 agent 原件检查，**不是独立人工标准答案，也不是准确率**。原始报告按各策略请求记录的是 23/24、16/16、16/20；这些原始分母不同，不能直接比较比例。

在本次局部输入中，共享方案少一半请求，输入 tokens 少约 49%。秒数是顺序请求的实际耗时之和，不是稳定性能基准，也不是费用估算；独立策略在产品中可能并行。每个组合只运行一次，未随机化顺序，也未比较其他模型。

## 两个失败教会了什么

**返回类型过宽。** 继峰 staged/fields 返回的三组列都与参考一致，但还附带了 rows，违反“列类型的 rows 必须为空”的约定。运行器正确拒绝了它。不能把这解释成三个字段都读错。

后续探测保留四例原来的结构提案和字段任务，只改列专用 schema 与配套 system 指令。列类型不再有 rows 字段。4 次返回均结构有效，12 个列绑定均与参考一致。这支持进一步采用更窄的类型，但没有隔离 schema、提示变化和随机性各自的作用；也没有重跑上游记录识别。新增调用用了 16,214 tokens，不能把它当作完整 staged 策略的成本。

**记录范围与适用范围混在一起。** 亚大 independent/duplicates 和 staged/structure 选择第 34–36 行，排除第 37 行“符合检具”；参考包括第 34–37 行。原提示要求“尺寸数据行”并排除“非尺寸记录”，本身给了模型分类空间。这里是接口语义分歧，尚不能认定为模型漏行。共享方案碰巧与参考一致，也不能因此证明其解释正确。

后续列探测还保留了一个语义警报：继峰两次理由把 D45–D49 称为空的合并子单元格，而这些位置是带有未读图片的合并锚点。**坐标匹配不能证明理由忠实，也不能证明证据缺失。** 没有把这些记录升级为训练标签。

## 确定性计算和机制演示

`evaluate_rows.py` 从已记录绑定读取原生值，用 Decimal 计算所选数值行的公差、判定文字和重复值。R3 只接受 OK/合格，不接受 PASS/正确；R5 同行数值重复则 NG。独立策略保留两条规则各自的绑定，不会用后一次答案覆盖前一次分歧。

每种策略检查 6 个数值行，共 18 组行结果；17 组与原件检查一致，剩余一组因上述结构失败而 UNABLE。错误原件的 767 被识别为超差。图片规格行和非数值行均明确排除在此计算器能力之外，因此这不是完整 R3/R5 或整份文件的验收，也没有验证第 37 行争议。

`demo.html` 是独立的单文件机制演示，页面不联网、不保存状态。可操作六种情形：局部数值符合、真实超差、坐标真实但字段错、遗漏行、图片未读、政策未定义。已在真实浏览器逐项操作，并检查未解决项不会变成 PASS。演示的语义与覆盖检查由情形设定，不能充当模型评测或人工标签。

离线机制检查另验证了合法结构、越界地址、虚构引用、缺少字段四种情况。Python 编译、Ruff 和浏览器操作均通过；本研究没有修改产品代码，所以没有重跑产品集成验收。

## 为训练保留什么

24 次结构化求解记录已保存在忽略目录 `output/` 中。主实验和后续探测分别保存，不覆盖原失败。每条记录包含局部观察、任务、返回、来源与类型检查、错误、模型名、请求指纹、用量、耗时、原件指纹、模板族和派生关系；运行前还保存了请求计划、schema/提示或其指纹。保留短的可观察理由，不收集完整思维链、密钥或完整 SDK 响应。

当前所有记录的 `label.eligible=false`，可直接用于有监督训练的独立金标准数量为 **0**。结构通过和代码计算通过都不会自动产生字段语义标签。后续最有价值的标注是：独立确认源记录范围和字段位置，修正候选答案，记录为何 unresolved 或 absent，并把业务结论与绑定标注分开。

训练任务首先可以限定为“给定局部原件与需求，返回有来源的绑定或拒答”。本轮没有证明动态选择读取动作、图片理解、规则编译或任意文档泛化，因此不能把这些能力写成数据标签。多个正确答案、修正记录和人工意见也应保留，不强行压成一个 PASS/NG。

将来划分训练与测试集时，按原始来源及模板族分组；同一文档的 PDF/XLSX、错误版本、坐标平移不能跨集合。所有本轮输入都是开发探测，不能再包装成独立测试集。原始业务数据目前只保留在本地忽略目录，尚未导出或用于训练；真正导出时再按来源权限、去标识要求和用途筛选。

## 复现

在仓根运行；使用已经安装项目依赖的 Python。`--settings-root` 仅用于加载现有 `.env`，不复制或输出凭据。每次输出目录必须不存在。以下命令的 live 模式会实际调用模型。

```bash
python packages/ppap_deep/prototypes/typed_evidence_holes/hole_experiment.py \
  --offline --output /tmp/typed-holes-offline-new

python packages/ppap_deep/prototypes/typed_evidence_holes/hole_experiment.py \
  --live --max-calls 20 --settings-root /path/to/configured-repo \
  --assets-root . --output /private/new-comparison

python packages/ppap_deep/prototypes/typed_evidence_holes/evaluate_rows.py \
  /private/new-comparison --assets-root .

python packages/ppap_deep/prototypes/typed_evidence_holes/probe_column_type.py \
  /private/new-comparison --live --settings-root /path/to/configured-repo \
  --assets-root . --output /private/new-column-probe
```

本次完整记录位于 `output/live-comparison-01/` 与 `output/typed-columns-01/`，均被 Git 忽略。实际请求与观察由 JSONL 保存；`cases.py` 在主实验运行期间做过不改变输入的导入排序、格式和字符串分行，旧运行计划记录的文件字节指纹因此与提交版本不同。

下一项最值得验证的问题是：固定“源记录集合”的定义后，在新的模板族和未读图片上，共享绑定是否仍能保持覆盖并正确拒答。先解决这个问题，再决定是否增加求解阶段或训练模型。
