# 规则 OWL 形式化

目的是**发现规则缺陷**。把条款写成 OWL 时，每一处写不下去、要替规则做选择、或推理报出问题的地方，都是一条候选缺陷。OWL 文件只是证据，不交付、不入库、不提交。

不做：CNL、CLIF、替规则做选择、直接修改 `rules.json` 或 `assets/` 下的规则原件。

## 输入与产出

- 输入：一个规则文件（如 `packages/audit/src/audit/checkers/li/L05/rules.json`，取 `rules[].id` 与 `rules[].rule_to_check`），可只做用户点名的条款。
- 工作目录：`.local/rule-owl/<类型>/`（已被 Git 忽略）。每条条款一个 `<条款序号>.ofn`，如 `L05-1.ofn`。
- 产出：`.local/rule-owl/<类型>/report.md` 缺陷报告，并在对话里给用户看摘要。

## 步骤

### 1. 读条款，先列词汇

逐条读原文，列出其中的文件、工作表、字段、标签、取值、判定词（通过/不通过）。同一个东西在条款里换了说法，或同一个说法指了不同的东西，先记下来。

### 2. 写 OWL 2 Functional Syntax

模板：

```
Prefix(:=<https://ppap.example/rules/L05#>)
Prefix(owl:=<http://www.w3.org/2002/07/owl#>)
Prefix(rdfs:=<http://www.w3.org/2000/01/rdf-schema#>)
Prefix(xsd:=<http://www.w3.org/2001/XMLSchema#>)
Ontology(<https://ppap.example/rules/L05/1>
  Annotation(:clause "packages/audit/src/audit/checkers/li/L05/rules.json#L05:1")
  Declaration(AnnotationProperty(:clause)) Declaration(AnnotationProperty(:quote))
  Declaration(Class(:Pass))  Declaration(Class(:Fail))
  DisjointClasses(:Pass :Fail)
  ...
)
```

- **原文对齐。** 本体上的 `:clause` 指向规则文件和条款 id；每段原文都要用 `:quote` 逐字引用在对应的类或公理上（`AnnotationAssertion(:quote :X "原文片段")`，或公理注解 `EquivalentClasses(Annotation(:quote "原文片段") ...)`）。脚本会报出没被引用的原文片段，以及与原文不符的引用。OWL 写不出的片段也要引用，并按第 3 步“表达局限”的三类标注，不能不引用。
- **互斥要写明是否穷尽。** 一组互斥的类（如取值“达标/低于/缺值”）放在同一个父类下：原文穷尽了就写 `DisjointUnion(:父类 :A :B :C)`；否则写 `SubClassOf(:A :父类)` 加 `DisjointClasses(:A :B :C)`，脚本会自动查“属于父类但不属于任何一类”的情况，报出就是候选缺陷。

- 同一文件类型的条款共用一个前缀，共用词汇用同一个 IRI；这样第 7 步合并后能发现条款间冲突。
- 名称用英文驼峰，加 `rdfs:label` 写条款原词；原文片段写在 `:quote` 上，自己的说明写在 `rdfs:comment` 上。
- 被审的对象（文件、工作表、行、字段值）建成类；判定写成条件类表达式，用 `SubClassOf(<条件> :Pass)` / `SubClassOf(<条件> :Fail)` 连到结论。
- 只用标准 OWL 2 构造，保持在 OWL 2 DL 之内。

写的时候遵守：

- **只看原文，当逻辑题做。** 只分析条款字面的量词范围、未定义的谓词、条件怎么组合、每个分支得出什么结论。不引入原文没提到的东西，如表里的判断栏、文件惯例、“客户大概的意思”。
- **不替规则做选择。** 原文没写明的，不按“行业惯例”或“显然的意思”补；写成缺陷，并按第 4 步把每种理解都写出来对比。
- **比较默认不归一化。** `010` 不等于 `10`，`ok` 不等于 `OK`，除非原文写了怎么处理。
- **每个“如果……则……否则……”都要落到具体情况。** 写不出某个情况的结论，就是缺陷。

### 3. 记录缺陷（核心）

写作中遇到下列情况立刻记一条，不要等到最后：

| 类型 | 典型问题 |
|---|---|
| 量词 | 全部还是存在一个；恰好一个还是至少一个；多个工作表/多行都匹配时取哪个 |
| 比较 | 精确相等还是包含；大小写、空格、全半角、数字格式是否归一化 |
| 空与缺失 | 字段不存在、值为空、无法识别时判什么 |
| 范围 | 前置条件是必须满足的要求，还是选定检查范围的条件（不满足时判不通过还是不检查） |
| 覆盖缺口 | 某种情况既没写通过也没写不通过 |
| 冲突 | 同一情况同时满足通过与不通过的条件；条款之间给出相反结论 |
| 术语 | 同一对象多种叫法，或同一叫法多种对象；标签与工作表名混用 |
| 顺序与停止 | 多步检查的先后、哪一步失败即停止没写清 |
| 无判定标准 | “合理”“完整”“清晰”等没有可程序化标准的要求 |
| 表达局限 | OWL 写不出的部分（开放世界下的“找不到”、跨记录取值相等、计数、字符串运算、读取位置） |

“表达局限”本身不一定是规则缺陷：它说明这部分只能靠检查程序实现，但原文是否写清楚了仍要检查。抽象掉的部分最容易藏住歧义，所以按三类分别处理，在引用上用元注解标出类别：

```
AnnotationAssertion(Annotation(:limit "predicate")
    Annotation(:open "目标值本身写成带比较符号的条件（如“>1.67”）时怎么比较")
    :quote :ValueMeets "的CPK、PPK的结果值都大于等于目标值")
```

| 类别 | 例子 | 处理 |
|---|---|---|
| `predicate` 写不出的谓词：比较、跨记录相等、计数、字符串运算 | “结果值都大于等于目标值” | 抽象成类，放进穷尽（`DisjointUnion`）或受完备性检查的互斥组。再做一张谓词卡：列出谓词的输入，逐一过各种情况（两边都有值、一边缺值、不是数字、带符号或单位、恰好相等、多个值时取哪个），原文没定义的每种情况写一条 `:open`；都有定义就写 `:open "无"`。`:open` 的情况按第 3 步记成缺陷，会改变结论的放进第 4 步的读法对比。 |
| `open-world` 开放世界：“不存在”“找不到” | “是否存在……清单表格，不存在则不通过” | OWL 推不出“没有”，在第 5 步的真实文件里把事实写封闭。“什么算存在”仍按原文检查。 |
| `output` 不影响判定的要求 | “判定依据需提醒用户进行人工复核” | 不写进判定，报告里列为对检查程序的要求。只有要求本身不清楚时才记缺陷。 |

脚本会列出全部表达局限：谓词没进穷尽或受检查的互斥组、没写 `:open`，都会报出；每条原文没定义的情况各算一条发现。

每条缺陷写：条款 id、原文片段、类型、两种（或几种）理解、**一个能让不同理解得出不同结论的具体文件情况（反例）**、建议改写（尽量少改原文）。

### 4. 多读法对比

一份 OWL 只能表达一种读法，推理机只在这一种读法内部检查，查不出“一句话有两种读法”。所以第 3 步记下的每一处歧义，都按下面的约定把各种读法写进同一个 `.ofn`，由脚本展开、比较：

- **歧义点。** 判定只引用一个不加定义的类，如 `:Remedy`（“反应计划或备注不为空”）。
- **读法。** 每种读法是一个类 `<歧义点>__<歧义编号><读法字母>`，如 `:Remedy__3A`、`:Remedy__3B`，各自用 `EquivalentClasses` 定义，`rdfs:comment` 写明对应的理解。一处歧义可以涉及几个歧义点（如 `:RowOK__4C`、`:RowBad__4C`），每个歧义点都要有该歧义的全部读法；一个歧义点只属于一处歧义。读法里可以引用其他歧义点。
- **判定。** 只写一个 `:Pass` 和一个 `:Fail`，不要按读法各写一份。

脚本把所有歧义的读法做笛卡儿积，每个组合生成一份判定（只复制依赖歧义点的类，事实类共享），然后：

- 对只差一处读法的每对组合，检查“这个组合判通过、那个组合判不通过”是否可能，按歧义汇总成 `[歧义 n] A 判通过、B 判不通过：可能（1A·2*·3*·4*）`。`2*` 表示歧义 2 取哪种读法都一样，`4A|B` 表示歧义 4 取 A 或 B。
- 自己写的 `Probe_` 探针在每个组合里各查一次，报出它在哪些组合下仍可能，例如 `Probe_Uncovered` 只在某几种组合下出现缺口。这样能发现几处歧义叠加才出现的问题，不用手工拼组合。

结果怎么用：

- 可能：两种读法确实会给出不同结论，歧义确认。按第 3 步写出让它们分歧的具体文件情况。
- 两个方向都已排除：这几种读法在逻辑上等价，不是会改变结论的歧义，从缺陷清单删掉或降为措辞问题。
- 缺口只在部分组合下出现：说明是这几处歧义的组合决定是否有缺口，一并写进相关缺陷。

提出“哪里有几种读法”仍靠第 1～3 步的人工分析，推理机只验证这些读法是否真的分歧。

### 5. 写入真实文件

把会被条款影响的真实文件（尤其是有真值的语料文件）写成**类**，不要写成个体：带上个体后 HermiT 每次检查都要带着它们算，慢几十倍。

```
Declaration(Class(:Case574))
AnnotationAssertion(:case :Case574 "574-PPK (1) (1).pdf")
AnnotationAssertion(:truth :Case574 "PASS")
EquivalentClasses(:Case574 ObjectIntersectionOf(:File :HasSummaryTable ObjectComplementOf(:Unidentifiable)
  ObjectSomeValuesFrom(:hasRow ObjectIntersectionOf(:CharacteristicRow :ValueMissing))
  ObjectAllValuesFrom(:hasRow ObjectIntersectionOf(:CharacteristicRow :ValueMissing))))
```

- 事实要封闭：列出存在的行（`ObjectSomeValuesFrom`），再用 `ObjectAllValuesFrom` 说明没有别的行；判定用到的否定事实（如“可辨识”）也要写明，否则开放世界下推不出结论。
- 只写文件里实际有的事实，不写判定结论。
- 脚本给每个文件在每个组合下分类：`PASS`、`NG`、`无结论`（条款对它没给结论）或`事实与条款矛盾`，并和 `:truth` 对比，报出与真值一致的组合。真值只代表当前的判定，不用它判断哪种读法正确。

### 6. 用 ROBOT 检查单条

Java 取自 `JAVA_HOME`（没设才用 `PATH` 里的 `java`），需 11 及以上；首次运行会下载固定版本的 ROBOT jar 到本 skill 的 `bin/`。

```bash
python3 .claude/skills/rule-owl/scripts/check.py .local/rule-owl/L05/L05-1.ofn
```

脚本依次做原文对齐、读法展开、OWL 2 DL 校验、推理（一致性、不可满足类、探针、完备性、读法分歧、文件分类）。展开后的本体留在 `<文件名>.robot/`：有歧义时每对比较的组合一个 `expanded-<n>.ofn`，并行推理，U06:3 这种 4 处歧义、24 种组合的条款约一分钟以内。脚本只列出不可满足的类，不生成解释；要看某个类为什么不可满足，用脚本输出里给的 `robot explain` 命令单独查。也可以直接用 `.claude/skills/rule-owl/scripts/robot <命令>` 调 ROBOT。

**探针**：把要查的情况声明为名字以 `Probe_` 开头的类，用 `EquivalentClasses` 定义。探针不可满足表示条款排除了这种情况；仍可满足表示条款没有排除，是候选缺陷。常用两种：

```
# 冲突：同时满足通过条件和不通过条件的情况
EquivalentClasses(:Probe_PassAndFail ObjectIntersectionOf(<通过条件> <不通过条件>))
# 缺口：在检查范围内，却既不满足通过条件也不满足不通过条件
EquivalentClasses(:Probe_Uncovered ObjectIntersectionOf(<范围> ObjectComplementOf(<通过条件>) ObjectComplementOf(<不通过条件>)))
```

探针里只放条件，不要把探针本身连到 `:Pass`/`:Fail`。

结果怎么用：

- 读取失败：是自己的语法错误，改文件，不算规则缺陷。
- 超出 OWL 2 DL：看是不是条款本身要求了 DL 表达不了的东西；是就记为表达局限并改写到 DL 内，否则改自己的写法。
- 原文对齐报出片段：补写或补 `:quote`；与原文不符的引用要改成逐字一致。
- 整体矛盾、不可满足的类：用 `robot explain` 查解释，按其中的公理和 `:quote` 对回原文，是条款自相矛盾就记缺陷，是自己写错就改。读法类定义成 `owl:Nothing`（如“缺值永不算满足”）是有意的，脚本不报。
- 完备性报出：按第 2 步判断原文是否穷尽。
- 探针仍可满足：按第 3 步写出反例，记缺陷。

### 7. 合并检查同一类型的全部条款

```bash
python3 .claude/skills/rule-owl/scripts/check.py .local/rule-owl/L05/*.ofn --out .local/rule-owl/L05/merged.robot
```

合并后再加跨条款探针（例如条款 1 判通过、条款 3 判不通过的同一情况）。条款间冲突和术语不统一只有这一步能发现。

### 8. 写报告，交给用户决定

`report.md` 包含：每条条款的结论（无问题 / 有歧义或缺口）、歧义清单（注明是否确认会改变结论、哪些真实文件会因此改变结论）、需要用户回答的问题、对检查程序的要求、建议改写。

报告给产品负责人看，**只用条款和业务的词，不出现任何技术词汇**：不写 OWL、本体、类、公理、探针、推理机、ROBOT、可满足/不可满足、读法组合编码（如 `1A·2*`）、英文类名。脚本输出里的结论要翻译成白话：

- 读法用一句话说清楚，如“缺值的行不算达标，判不通过”，不写“读法 A”的内部编号也能看懂；可以编号，但每次出现都要写明是哪种理解。
- 组合效应写成条件句，如“只有当低于目标的行在反应计划或备注不为空时算满足，这一处才会改变结论”。
- 覆盖缺口写成“这种情况原文没有给出结论”；完备性写成“原文没说取值只有这几种”。
- 表达局限不用这个词，写成两部分：“原文没定义的情况”（谓词卡的 `:open`）并入歧义分析；“对检查程序的要求”单列。
- 真实文件的结论写成“按哪种理解通过、按哪种理解不通过”。

每条条款按下面的格式写：

- **规则文件**：规则文件标题：规则名字（编号），如 `过程能力研究审核规则：能力不足项是否有措施计划（U06:3）`
- **规则原文**：逐字引用
- **歧义分析**：逐条列歧义；提到具体文件时用不带路径的完整文件名，如 `574-PPK (1) (1).pdf`
- **需要回答的问题**：每个问题能用一句话回答
- **对检查程序的要求**：不影响判定、但检查程序要做到的事

缺陷和问题交给用户决定，不用模型判断哪种理解正确。用户确认后，规则修改按正常的规则交付流程进行；已入库的规则版本不改写。ROBOT 检查全部通过只说明 OWL 写法里没发现问题，不说明规则正确。
