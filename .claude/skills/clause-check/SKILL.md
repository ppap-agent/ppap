# 条款检查

目的是**发现条款原文的缺陷**，交给用户决定。你只把原文说了什么写成形式化文件；每种情况得出什么结论、哪里冲突、哪里没有结论、几种理解是否真的不同，都由脚本推出来。交给用户的是脚本生成的白话报告。形式化文件只是证据，不交付、不入库、不提交。

不做：替规则选择理解、补原文没有的意思、直接修改 `rules.json` 或 `assets/` 下的规则原件。

## 输入与产出

- **输入**：一条条款（规则文件里 `rules[].id` 与 `rules[].rule_to_check`）。调用方可能另给几份真实文件，也可能不给。
- **只用给定的输入**：不参考检查程序的实现和测试、真值表和判定理由、以前的检查结果。它们是别人对条款的理解，会替你做掉本该交给用户的选择。
- **工作目录**：调用方指定的目录；没有指定时用仓库根目录下的 `.local/clause-check/<类型>/`（已被 Git 忽略）。下文记作 `<工作目录>`。一条条款一个 `<条款序号>.ofn`，如 `X01-1.ofn`。
- **产出**：`<工作目录>/<条款序号>.report.md`，**由脚本生成，不手写、不手改**；在对话里给用户看摘要。
- **脚本**：`python3 <技能目录>/scripts/check.py <工作目录>/<条款序号>.ofn`，`<技能目录>` 是本文件所在的目录。Java 取自 `JAVA_HOME`（没设才用 `PATH` 里的 `java`），需 11 及以上。
- **完整示例**：`<技能目录>/examples/X01/X01-1.ofn` 和同目录的虚构规则文件，可以直接运行。先读它，再照着写。下文的例子都来自这条虚构条款：

> 识别封面签字栏中编制、审核、批准是否都已签名并填写日期，都已签名并填写日期则通过，任一为空则不通过；批准日期不得早于编制日期；签字栏不存在则不通过，并提示用户补签。

## 脚本做什么

你写的是**原文的条件**，结论由脚本推：

- `:Judged` 是条款判定的对象（如文件）；`:PassWhen` 是原文说“通过”的条件，`:FailWhen` 是原文说“不通过”的条件。原文没说什么情况通过，就写 `EquivalentClasses(:PassWhen owl:Nothing)`，不要替它编。**不要**写“通过和不通过互斥”。
- 每个被判定的东西得到四种结论之一：**通过**（只满足通过条件）、**不通过**（只满足不通过条件）、**没有结论**（都不满足，原文的缺口）、**既通过又不通过**（都满足，原文的冲突）。
- 有歧义时，脚本把每处歧义的各种理解组合起来，每种组合各推一遍：
  - 缺口和冲突：每种组合下都查是否存在。存在时，要你用 `:Gap__<k>` / `:Conflict__<k>` 写出这些情况；脚本核对你写的确实是缺口或冲突，并且全部写到了。
  - 歧义：只差一处理解的两种组合，若有东西在两边结论不同（包括“通过”对“没有结论”），这处歧义才算会改变结论。各种理解对任何东西结论都相同，就不算歧义。
  - 例子和真实文件：按每种组合推出结论。例子必须在几种理解下结论不同。
- 退出码：`0` 检查完整（发现写在报告里）；`1` 检查未完成，报告顶部写明原因，按下面“输出怎么处理”改完再跑；`2` 文件没法用（语法、约定缺项）。**只有退出码为 0 的报告才能交给用户。**

## 约定速查

| 写法 | 含义 |
|---|---|
| `Annotation(:clause "<规则文件路径>#<条款 id>")` | 本体对应哪条条款；路径相对仓库根目录、`.ofn` 的上级目录，或绝对路径 |
| `:quote` | 逐字引用一段原文，挂在表达这段原文的类或公理上；全部原文都要被引用 |
| `:Judged`、`:PassWhen`、`:FailWhen` | 判定的对象、原文说通过的条件、原文说不通过的条件（都必须有） |
| `<歧义点>__<编号><字母>` | 歧义点的一种理解，如 `:Signed__1A`；带 `rdfs:label`（短名）和 `:says`（完整说法） |
| `:issue`、`:question` | 写在歧义点上：歧义的标题、要用户回答的问题 |
| `:Example__<编号>` | 这处歧义的例子：一个具体的被判定对象，事实写封闭，带 `:says` |
| `:Gap__<k>`、`:Conflict__<k>` | 脚本查出缺口、冲突后，你写出的具体情况，带 `:says`（名词短语） |
| `:limit "predicate" \| "open-world" \| "output"`、`:open`、`:says` | 写在 `:quote` 上的元注解：写不出的部分的类别、原文没定义的情况（问句）、对检查程序的要求 |
| `:case` | 真实文件类：文件名 |
| `:chosen`、`:answered`、`:rewrite` | 用户答复后回填 |

每个类和属性都要 `Declaration`，漏了脚本会按名字报出。技能自己的注解属性（`:quote`、`:says` 等）不用声明，脚本会补。

## 步骤

### 1. 逐句读条款

- 列出原文提到的对象、字段、取值和判定词。同一个东西换了说法，或同一个说法指不同的东西，记下来。
- 逐句列出每个判定句（“……则通过”“……则不通过”“……则继续……”）：条件是什么、说的是谁、结论是什么。条件或主语缺失（如“如果无法辨识”没说什么无法辨识）、写了要求却没写违反的结论（如“不得早于”），都是原文没定义的情况。

### 2. 写判定

照着示例写 `:Judged`、`:PassWhen`、`:FailWhen` 和它们用到的词汇，并用 `:quote` 引用对应的原文。

- **只看原文，当逻辑题做。** 只写字面的量词、条件和结论。不引入原文没有提到的栏位、结论、文件、依据或格式，不按文件惯例、行业惯例或“客户大概的意思”补。真实文件里有这些东西，也只在它们影响原文某个词的认定时才提，而且以原文的词为题。反例：“签字栏旁边另有审批流程截图时，以哪个为准？”——原文没提审批截图，不该问。
- **不替规则做选择。** 一句话能有几种理解，就按第 3 步把每种都写出来，不要挑一种写进判定。
- **取值不要写死成穷尽。** 原文没说只有这几种的，用 `SubClassOf(:A :父类)` 加 `DisjointClasses(:A :B :C)`，脚本会问“还可能是别的样子吗”。只有按定义就穷尽的（如“早于 / 不早于 / 没法比较”），才写 `DisjointUnion(:父类 :A :B :C)`。
- **比较默认不归一化。** `010` 不等于 `10`，`ok` 不等于 `OK`，除非原文写了怎么处理。

写不出的部分（逐字的比较、计数、“不存在”）也要引用，并在引用上标类别：

| 类别 | 例子 | 处理 |
|---|---|---|
| `predicate` 写不出的比较、计数、字符串运算 | “批准日期不得早于编制日期” | 抽象成几个类，放进穷尽的或受完备性检查的互斥组；逐一过各种情况（两边都有值、缺值、不是数字、带符号、恰好相等、多个值），原文没定义的每种情况写一条 `:open` 问句；都有定义就写 `:open "无"` |
| `open-world` “不存在”“找不到” | “签字栏不存在则不通过” | 用 `:says` 写一句对检查程序的要求；“什么算存在”仍按原文检查 |
| `output` 不影响判定的要求 | “并提示用户补签” | 用 `:says` 写成对检查程序的要求 |

### 3. 写歧义

- **歧义点**：判定只引用一个不加定义的类，如 `:Signed`（“已签名”）。
- **理解**：每种理解一个类 `<歧义点>__<编号><字母>`，用 `EquivalentClasses` 定义，带短名和完整说法。一处歧义可以有几个歧义点，每个歧义点都要有这处歧义的全部理解；一个歧义点只属于一处歧义。理解里可以引用别的歧义点。
- **例子**：每处歧义写 `:Example__<编号>`，一个具体对象，事实写封闭，几种理解在它上面结论不同。
- **同一处问题只写一次**：能写出几种理解的，写成歧义；写不出理解、只能提问的，写成 `:open`。

### 4. 写真实文件（有的话）

把给定的真实文件写成**类**（不要写成个体，个体会让推理慢几十倍），带 `:case "文件名"`：

- 只写文件里实际有的事实，不写结论。
- 事实要封闭：用 `ObjectSomeValuesFrom` 列出有的东西，再用 `ObjectAllValuesFrom` 说明没有别的；判定用到的否定事实（某栏为空、某项不存在）也要写明。推不出结论时，脚本会报“事实没写全”。

### 5. 运行并处理输出

```bash
python3 <技能目录>/scripts/check.py <工作目录>/<条款序号>.ofn
```

| 输出 | 怎么处理 |
|---|---|
| `[约定]` | 缺了 `:Judged` / `:PassWhen` / `:FailWhen`、理解没声明，或用了已不用的写法：按提示补 |
| `[原文对齐]` | 补写或补 `:quote`；引用要和原文逐字一致 |
| `[超出 OWL 2 DL]` | 多半是用了没声明的名字；否则改写法 |
| `[写法错误]`、`[整体矛盾]` | 词汇或文件描述自相矛盾，是你写错了：用提示里的命令查解释后改。条款本身的冲突不会以这种方式出现，它表现为“既通过又不通过” |
| `[原文没有给出结论]`、`[原文同时给出通过和不通过] 还有情况没写出来` | 用 `:Gap__<k>` / `:Conflict__<k>` 写出具体情况，直到写全 |
| `[情况写错]` | 写出的情况其实有结论（或不是冲突），按条款改写 |
| `[歧义 n] 几种读法对任何文件结论都相同` | 不是会改变结论的歧义：改成 `:open` 或删掉；也可能是理解没接到判定条件上 |
| `[例子缺项]`、`[例子不分歧]`、`[事实没写全]` | 补例子、换例子，或把事实写封闭 |
| `[完备性]` | 原文确实穷尽就改成 `DisjointUnion`；否则保留，报告会问用户 |
| `[重复]` | 同一处问题只留一种写法 |
| `[白话缺项]`、`[白话质量]` | 按下一步补写 |

### 6. 写白话说明，直到检查完整

报告只会写进条款原文和你写的白话说明，所以白话说明**不能有任何技术词汇**（OWL、本体、类、公理、推理、读法编码、英文名称），只用条款和业务的词，不补原文没有的意思。

| 注解 | 写在哪里 | 写什么 | 例子 |
|---|---|---|---|
| `:issue` | 歧义点 | 歧义的标题 | “已签名”包括哪些签法 |
| `:question` | 歧义点 | 要用户回答的问题，一句话能答，以“？”结尾 | 电子签名算不算“已签名”？ |
| `rdfs:label` | 每种理解 | 短名，12 字以内 | 只认手写签名 |
| `:says` | 每种理解 | 完整说法，以“。”结尾 | 只有手写签名才算已签名。 |
| `:says` | 每个例子 | 例子的情况，以“。”结尾 | 三栏都填了日期，批准是电子签名。 |
| `:says` | 每个 `Gap`、`Conflict` | 情况的名词短语，不加句末标点 | 签字栏里缺了某一栏的封面 |
| `rdfs:label` | 受完备性检查的父类和成员 | 白话名称 | 一栏签名 / 手写签名 |
| `:open` | `:quote` 的元注解 | 原文没定义的情况，问句 | 日期只写到月份时怎么比较？ |
| `:says` | `open-world`、`output` 引用的元注解 | 对检查程序的要求，以“。”结尾 | 判定不通过时，提示用户补签。 |

一种理解怎么写都说不清，问题不在措辞，回到第 3 步重新拆。反复运行到退出码为 0，再通读报告一遍，交给用户。

报告包含：规则原文和结论；原文没说清的地方（每处歧义的几种理解、会让同一份文件怎样得出不同结论、例子、受影响的真实文件，以及原文没定义的情况）；原文没有给出结论的情况；原文同时给出通过和不通过的情况；真实文件按原文的结论；需要回答的问题；对检查程序的要求。缺陷和问题交给用户决定，不用模型判断哪种理解正确。

### 7. 回填答复，核对缺口是否补上

用户回答后，把答复写回 `.ofn` 重跑。`:chosen`、`:answered` 只能来自用户本人在对话里的答复，不能推断或代填。

- **歧义的答复**：在该歧义的任一歧义点上写 `AnnotationAssertion(:chosen :Signed "A")`，并用 `:answered` 逐字记下用户的原话。脚本只保留这一种理解。用户的答复不在已列的理解里，先按答复新增一种理解再选它。
- **原文没定义的情况的答复**：在对应的 `:open` 上加 `Annotation(Annotation(:answered "用户原话") :open "……？")`，**并按答复改写判定或词汇**，让推理用上它。脚本只看得到“已答复”，看不出判定有没有按答复改；改没改由你负责，报告里的结论只反映你改后的判定。
- **建议改写**：全部答复后，按答复写出建议改写的条款原文，放在 `Annotation(:rewrite "……")` 上，尽量少改原文。

重跑后报告多出“答复核对”：还有几个问题待答复、是否仍有缺口或冲突、每份真实文件按答复的结论。核对通过后，建议改写交给用户；规则修改按正常的规则交付流程进行，技能不直接改 `rules.json` 或规则原件。
