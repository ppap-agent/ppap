# 条款检查

目的是**发现条款原文表述的不足**，交给用户决定。方法是试着把原文写成形式化：写的时候卡住的地方，就是原文没说清的地方——

- 一个词能有几种理解，不选一种就写不下去：**歧义**；
- 一种情况原文没定义，写不出来：**原文没定义的情况**；
- 某种文件按原文既不通过也不不通过：**原文没给结论**；
- 某种文件按原文既通过又不通过：**冲突**。

形式化是手段，不是产出。**不追求把整条条款写完整、写严密**；写到能把卡住的地方说清楚、用例子确认就够了。每处发现配一个具体例子，脚本推一遍，确认它真的会让结论不同。交给用户的是脚本生成的白话报告；形式化文件不交付、不入库、不提交。

不做：替规则选择理解、补原文没有的意思、直接修改 `rules.json` 或 `assets/` 下的规则原件。

## 输入与产出

- **输入**：一条条款（规则文件里 `rules[].id` 与 `rules[].rule_to_check`）。调用方可能另给几份真实文件，也可能不给。
- **只用给定的输入**：不参考检查程序的实现和测试、真值表和判定理由、以前的检查结果。它们是别人对条款的理解，会替你做掉本该交给用户的选择。
- **工作目录**：调用方指定的目录；没有指定时用仓库根目录下的 `.local/clause-check/<类型>/`（已被 Git 忽略）。下文记作 `<工作目录>`。一条条款一个 `<条款序号>.ofn`，如 `X01-1.ofn`。
- **产出**：`<工作目录>/<条款序号>.report.md`，**由脚本生成，不手写、不手改**；在对话里给用户看摘要。
- **脚本**：`python3 <技能目录>/scripts/check.py <工作目录>/<条款序号>.ofn`，`<技能目录>` 是本文件所在的目录。Java 取自 `JAVA_HOME`（没设才用 `PATH` 里的 `java`），需 11 及以上。
- **完整示例**：`<技能目录>/examples/X01/X01-1.ofn` 和同目录的虚构规则文件。先读它，再照着写；要运行它，用 `--out`、`--report` 把输出放到工作目录（技能目录可能是只读的）。下文的例子都来自这条虚构条款：

> 识别封面签字栏中编制、审核、批准是否都已签名并填写日期，都已签名并填写日期则通过，任一为空则不通过；批准日期不得早于编制日期；签字栏不存在则不通过，并提示用户补签。

## 脚本做什么

- `:Judged` 是条款判定的对象（如文件）；`:PassWhen` 是原文说“通过”的条件，`:FailWhen` 是原文说“不通过”的条件。原文没说什么情况通过，就写 `EquivalentClasses(:PassWhen owl:Nothing)`。**不要**写“通过和不通过互斥”：两者都满足就是原文的冲突。
- 一个具体的东西得到四种结论之一：**通过**、**不通过**、**没有结论**（两个条件都不满足）、**既通过又不通过**。
- 脚本只判你写的**例子**和**真实文件**，不对“所有文件”下结论：
  - 歧义的例子：在这处歧义的每种理解下各推一遍，结论必须不同。其他歧义保持未定：只用它们各种理解共同认可的部分，所以例子要选得只受这一处影响；做不到时用 `:under` 写明假定的理解。
  - 没结论、冲突的例子：推一遍，确认确实没有结论、确实既通过又不通过。
  - 真实文件：推出按原文的结论，以及随哪处歧义改变。
- 退出码：`0` 报告里每处发现都已确认；`1` 有发现没确认（例子不分歧、例子推不出结论、写的没结论例子其实有结论、白话缺项），报告顶部写明，改完再跑；`2` 文件没法用（语法、约定缺项）。**只有退出码为 0 的报告才能交给用户。**
- 脚本还会给两种**提示**，不影响退出码：原文有句子没被引用（回去看看那句有没有卡住的地方）；各处都不定时可能存在没结论或冲突的文件，而你没写例子（想一想是哪种文件，确有就写，没有就不用管）。

## 约定速查

| 写法 | 含义 |
|---|---|
| `Annotation(:clause "<规则文件路径>#<条款 id>")` | 本体对应哪条条款；路径相对仓库根目录、`.ofn` 的上级目录，或绝对路径 |
| `:quote` | 逐字引用一段原文，挂在表达这段原文的类或公理上 |
| `:Judged`、`:PassWhen`、`:FailWhen` | 判定的对象、原文说通过的条件、原文说不通过的条件（都必须有） |
| `<歧义点>__<编号><字母>` | 歧义点的一种理解，如 `:Signed__1A`；带 `rdfs:label`（短名）和 `:says`（完整说法） |
| `:issue`、`:question` | 写在歧义点上：歧义的标题、要用户回答的问题 |
| `:Example__<编号>` | 这处歧义的例子：一个具体的被判定对象，事实写封闭，带 `:says` |
| `:Gap__<k>`、`:Conflict__<k>` | 原文没给结论、同时给出通过和不通过的具体文件，带 `:says`（名词短语） |
| `:under "2B"` | 写在例子、`Gap`、`Conflict` 上：它假定第 2 处按理解 B；可写多个 |
| `:open` | 写在 `:quote` 上的元注解：这段原文没定义的情况（问句） |
| `:case` | 真实文件类：文件名 |
| `:chosen`、`:answered`、`:rewrite` | 答复后回填（对话或规则确认页） |

每个类和属性都要 `Declaration`，漏了脚本会按名字报出。技能自己的注解属性（`:quote`、`:says` 等）不用声明，脚本会补。

## 步骤

### 1. 逐句读条款

- 列出原文提到的对象、字段、取值和判定词。同一个东西换了说法，或同一个说法指不同的东西，记下来。
- 逐句列出每个判定句（“……则通过”“……则不通过”“……则继续……”“否则……”）：条件是什么、说的是谁、结论是什么。条件或主语缺失（如“如果无法辨识”没说什么无法辨识）、写了要求却没写违反的结论（如“不得早于”），都是卡住的地方。

### 2. 写判定，记下卡住的地方

照着示例写 `:Judged`、`:PassWhen`、`:FailWhen` 和它们用到的词汇，用 `:quote` 引用对应的原文。写的过程中每次卡住，按第 3 步记下来。

- **只看原文，当逻辑题做。** 只写字面的量词、条件和结论。不引入原文没有提到的栏位、结论、文件、依据或格式，不按文件惯例、行业惯例或“客户大概的意思”补。真实文件里有这些东西，也只在它们影响原文某个词的认定时才提，而且以原文的词为题。反例：“签字栏旁边另有审批流程截图时，以哪个为准？”——原文没提审批截图，不该问。
- **不替规则做选择。** 一句话能有几种理解，就把每种都写出来，不要挑一种写进判定。
- **每种理解都保留原文所有的结论句。** 理解只改变某个词怎么认定，不能丢掉或削弱“则通过”“则不通过”“否则……”。“……则通过，否则不通过”的不通过条件就是“不满足通过条件”（`ObjectComplementOf`），这类文件不会没有结论。
- **“读哪一个”没说清是歧义，不是没结论。** 原文没说有多张表、多处标签、多个值时读哪一个，写成几种读法（如“读第一张”“每张都要满足”“任一张满足即可”），不要写成原文没给结论。
- **“无法辨识”是一种取值。** 读不出来的值谈不上满足：把“看不清”和其他取值并列、互斥，通过条件只认“达标”。兜底句（“如果无法辨识则不通过”）管到哪些取值，没说清就是一处歧义。
- **比较默认不归一化。** `010` 不等于 `10`，`ok` 不等于 `OK`，除非原文写了怎么处理。
- **写不出的就不写。** 逐字的比较、计数、字符串运算、“不存在”这类写不出来的部分，抽象成一个类就行；它们原文没定义的情况（两边缺值、不是数字、恰好相等、只到月份……）用 `:open` 问出来。写不出本身不是发现，原文没定义才是。
- **只写到够用。** 取值不用列全，判定不用覆盖每种文件。一处发现能用例子说清，就不必为它把其余部分写严密。

### 3. 写发现

每处发现写一次，按能不能举出例子分三种：

- **歧义**（几种理解会让结论不同）：
  - 歧义点：判定只引用一个不加定义的类，如 `:Signed`（“已签名”）。
  - 理解：每种理解一个类 `<歧义点>__<编号><字母>`，用 `EquivalentClasses` 定义，带短名和完整说法。一处歧义可以有几个歧义点，每个歧义点都要有这处歧义的全部理解；一个歧义点只属于一处歧义。
  - 例子：`:Example__<编号>`，一个具体文件，事实写封闭，几种理解下结论不同。举不出这样的例子，它就不是会改变结论的歧义：改成 `:open` 问题或删掉。
- **原文没给结论、冲突**：写出具体的文件 `:Gap__<k>` / `:Conflict__<k>`，依赖某处理解时加 `:under`。先核对它是不是第 2 步的结论句漏写了、或是“读哪一个”的歧义。
- **原文没定义的情况**（问得出、举不出分歧的例子）：在对应原文的 `:quote` 上写 `:open` 问句。

同一处问题只写一种。不问“还可能是别的样子吗”这类不指向原文具体措辞的问题。

### 4. 写真实文件（有的话）

把给定的真实文件写成**类**（不要写成个体，个体会让推理慢几十倍），带 `:case "文件名"`：只写文件里实际有的事实，不写结论；事实要封闭（`ObjectSomeValuesFrom` 列出有的，`ObjectAllValuesFrom` 说明没有别的，判定用到的否定事实也写明）。推不出结论时，报告写“要等几处问题都答复后才能确定”。

### 5. 运行并处理输出

```bash
python3 <技能目录>/scripts/check.py <工作目录>/<条款序号>.ofn
```

| 输出 | 怎么处理 |
|---|---|
| `[约定]`、`[读法]` | 缺了 `:Judged` / `:PassWhen` / `:FailWhen`、名字没声明、理解没写全、`:under` 写错：按提示补 |
| `[超出 OWL 2 DL]`、`[整体矛盾]`、`[写法错误]` | 写法问题，不是条款的冲突：按提示查解释后改 |
| `[例子缺项]`、`[例子没写全]`、`[例子不分歧]` | 补例子、把事实写封闭、换只受这一处影响的例子或加 `:under`；换不出就改成 `:open` 或删掉 |
| `[情况写错]` | 写的没结论或冲突的文件其实有结论：改例子，或删掉这条 |
| `[重复]` | 同一个问题只问一次 |
| `[白话缺项]`、`[白话质量]` | 按下一步补写 |
| `[原文对齐]`、`[提示]` | 不必改；回去看看那句原文、那种文件有没有卡住的地方 |

### 6. 写白话说明

报告只会写进条款原文和你写的白话说明，所以白话说明**不能有任何技术词汇**（OWL、本体、类、公理、推理、读法编码、英文名称），只用条款和业务的词，不补原文没有的意思。

| 注解 | 写在哪里 | 写什么 | 例子 |
|---|---|---|---|
| `:issue` | 歧义点 | 歧义的标题 | “已签名”包括哪些签法 |
| `:question` | 歧义点 | 要用户回答的问题，一句话能答，以“？”结尾 | 电子签名算不算“已签名”？ |
| `rdfs:label` | 每种理解 | 短名，12 字以内 | 只认手写签名 |
| `:says` | 每种理解 | 完整说法，以“。”结尾 | 只有手写签名才算已签名。 |
| `:says` | 每个例子 | 例子的情况，以“。”结尾 | 三栏都填了日期，批准是电子签名。 |
| `:says` | 每个 `Gap`、`Conflict` | 文件的名词短语，不加句末标点 | 签字栏里缺了某一栏的封面 |
| `:open` | `:quote` 的元注解 | 原文没定义的情况，问句 | 日期只写到月份时怎么比较？ |

反复运行到退出码为 0，再通读报告一遍，交给用户。缺陷和问题交给用户决定，不用模型判断哪种理解正确。

### 7. 交客户确认（规则确认问卷）

问题要交给客户答复时，不在对话里转述，用规则页的「待确认问题」收集。线上只存问题卡片和答复，不存形式化、不调用模型、不改规则。

1. 写整理文件 `<工作目录>/问卷整理.json`，决定每处发现放在哪里；没提到的发现各成一张逐条问题卡：
   - `customer_id`、`rule_version`、`title`：客户编号（如 `uaes`）、规则版本（如 `规范性条款 v1.0`）、规则全名；
   - `common`：共性问题，每个写 `title`、`question`、`why`、`options`（没有选项时写 `expect`）和它管的发现 `items`（如 `CP:8#1`、`CP:8#8.1`、`CP:8#G1`）；
   - `relayed` 与 `applied`：已经转达过的客户答复（`answer`、`source`、`date`）和按它处理掉的发现（`relayed`、`result`），卡片上显示“按共性答复处理为……，请确认”；
   - `conclusion`：交客户补结论的卡片；`general`：通用判定说明自身的问题；`clause_order`：逐条问题的条款顺序（可选）。
2. 生成导入文件，报告必须都是退出码 0 的版本：

   ```bash
   python3 <技能目录>/scripts/questionnaire.py build <工作目录> <工作目录>/问卷整理.json <工作目录>/问卷导入.json
   ```

3. 直接写进数据库，给一个企业（飞书租户编号）用。产品本身不能导入、关闭或导出问卷，这三步都用数据库的迁移身份（`ppap_migrator`）以 `psql` 执行：

   ```bash
   python3 <技能目录>/scripts/questionnaire.py load <工作目录>/问卷导入.json <租户编号> > 导入.sql
   psql -f 导入.sql
   ```

   同一企业同一规则版本只能导入一次，卡片导入后不能改。导入后该企业成员在规则页该客户下看到「待确认问题」，逐张作答，每人的答复分开记录，没有“最终答复”；其他企业看不到。
4. 收答复时导出，答完后关闭（关闭后只读）：

   ```bash
   python3 <技能目录>/scripts/questionnaire.py export <工作目录>/问卷导入.json <租户编号> > 导出.sql
   psql -At -f 导出.sql > <工作目录>/问卷导出.json
   python3 <技能目录>/scripts/questionnaire.py close <工作目录>/问卷导入.json <租户编号> > 关闭.sql
   psql -f 关闭.sql
   ```

### 8. 回填答复

把答复写回 `.ofn` 重跑。`:chosen`、`:answered` 只能来自答复人本人的答复：用户在对话里的原话，或规则确认页的答复；不能推断或代填。

- **来自规则确认页**：先把导出文件整理成按条款的回填清单，再逐条回填：

  ```bash
  python3 <技能目录>/scripts/questionnaire.py answers <工作目录>/问卷导出.json <工作目录>
  ```

  `:answered` 记原话，并记下答复人和时间，如 `"按缺件判不通过（张三，2026-11-21，规则确认页）"`。同一处有几个人答复且不一致时，不替客户选，交产品负责人决定。
- **歧义的答复**：在该歧义的任一歧义点上写 `AnnotationAssertion(:chosen :Signed "A")`，并用 `:answered` 逐字记下原话。这处歧义就按这种理解推；答复不在已列的理解里，先按答复新增一种理解再选它。
- **原文没定义的情况的答复**：在对应的 `:open` 上加 `Annotation(Annotation(:answered "原话") :open "……？")`，并按答复改写判定。
- **建议改写**：全部答复后，按答复写出建议改写的条款原文，放在 `Annotation(:rewrite "……")` 上，尽量少改原文。

规则修改按正常的规则交付流程进行，技能不直接改 `rules.json` 或规则原件。
